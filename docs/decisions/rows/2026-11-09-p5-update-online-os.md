needed-by: P5 task 10, built 2026-11-09 (AP-1; K reviews)
decision: `updated` streams the next release into the idle slot over TLS on a `NetDest` of its own, and takes the update snapshot after the checks and before the slot can boot.
---
The OS half of P5 task 10, on `updatenet` (#694) and the shared ring-3 client `user::tls` (#753). `step=online` runs the update disk's flow on the network: the root is the newer of the slot's own and `/system/trust`'s, `kaituf` refreshes the metadata from the repository's Pages host, the release must be newer than every release this machine has committed and fit the idle slot (in slot R, `into=A` or `into=B` names it: `:reinstall`), and the image comes in 2 MiB chunks by `Range` through GitHub's redirect to its release-assets host, each checked against the signed chunk list before it is written. A record of the last chunk checked in `/system/updates` lets a later run resume. `updated` moves to the hard-float programs, as `pkg` did. Two changes in `updatenet`: `stage` takes a `recheck` that asks the signed metadata again once the image has checked out (a long download can span a newer release or an expired timestamp; C's review of #694), and `Boot::before_trial` runs after the checks and before `stage_end`, so the update snapshot of the system volume (ADR 0008 §10) is taken while the slot still cannot boot, never between the trial and the restart. The cases serve this build as release 2 from the HTTPS mock, signed by the run's test root: an update and its refusal by anti-rollback after the reboot, a flipped byte (its chunk is refused and nothing of it is written, the slot stays Updating), and an expired timestamp (refused by name). As for `pkg`, the plan line says which repository (`online=test`, the mock's three hosts on port 443, its test CA the bundle's `netroots/1.der`), and the shipping system's waits for the follow-up that gives `updated` a request for it. The mock's CA is now one per xtask run, so an image can carry it before its mock starts. TLS is linked into `updated` itself, as into `pkg`, and not routed through T's `fetch` (the manager, 2026-11-09; the `p5-pkg-online-os` row has the reasons). The memory cost, on debug builds: `updated`'s loaded segments went from 1.22 MiB (soft-float) to 2.53 MiB (hard-float with rustls and the crypto), +1.31 MiB, resident in every desktop boot; the desktop cases' 1024 MiB floor (main's since #771, for `fetch`) covers it with `pkg`'s. Speed: `update-online` prints the MB/s of the image's download (bytes fetched over the whole stage: the chunks, their checks, the writes and the read-back). `kainet` sends `Connection: close` on every request (`kainet/src/http/head.rs`), so a chunk of 2 MiB is a TLS connection of its own and a 2.5 GB image would be about 1,250 handshakes; keep-alive in `kainet` is the lever, and the figure from `full-ci` is in the pull request. The audit of 2026-11-10 added three things. A rolled-back timestamp: `update-online-rollback` takes metadata at version 2 of the timestamp and the snapshot in boot 2, and in boot 3 the repository serves a timestamp at version 3 naming snapshot 1, which `/system/trust` refuses by name ("bad version: timestamp names an older snapshot"). A resume: `updated` tries a network stop again (three times, 2 s or the server's wait, or `retries=N`), and `update-online-retry` cuts the connection once inside chunk 3, so the second call of the same boot keeps the three checked chunks after reading them back and fetches the rest. Across a reboot, `update-online-resume` stops the run at the cut (`retries=0`; the failure restarts into the running slot) and boots again with slot B as the boot left it (`TestCase::keeps_slot_b`, `slots::build_keeping_b`: every other boot's slot disk is rebuilt from its bundle, which would mask the chunks) and the mark in `/system/updates` (the data disk carries over), so the second boot keeps the same three chunks and fetches the rest. `:reinstall` in slot R stays host-tested too: the code is `into=A` or `into=B` through `Machine::slot`, which `updatenet`'s tests cover for a boot in R, and no case here holds the machine in R with `updated` running. If the last `set` fails, `pending` stays as `before_trial` wrote it (K's review of #754): `stage` has stored `stage_end` by then, so the slot is a trial with tries left whether or not the restart was stored, and `reconcile` settles every outcome (held, never booted, or failed and restored); `step=update` can clear it because it stores `stage_end` and the restart in one `set`. `bootslot`'s tests pin the three readings `reconcile` relies on. The authority is in one process by ADR 0008 section 9: `updated` holds slot-write, boot-record and network authority and parses TLS and HTTP from the network, so a later split (the fetch in a lesser process, the staging in `updated`) remains an option. A `test=update` boot hands `updated` only the `updated.<key>=` words on the kernel's `UPDATED_TEST_WORDS` (#822 filters the rest, so that a command line cannot widen the line): `retries` and `into` are on it, and a host test in `xtask` checks every case's `updated.` words against the list, since a word the list lacks is dropped without a sign (`update-online-resume`'s `retries=0` was, and `updated` tried the cut again).
