needed-by: P5, built 2026-11-19 (lane K, audit K #17; the manager chose the test-network rule)
decision: A name's answer never leads an app to a private network; QEMU's 10.0.2.0/24 is the one exception, only on boots with `online=test`, which a release image cannot carry
---
Until now a NetDest record kept any address a name resolved to except this machine, the link, nothing, everyone and multicast. The row `2026-11-09-netdest-hosts-any` left RFC 1918 to TLS name checks. The audit showed that a name pointing at 192.168.1.1, or at the VM host's 10.0.2.2, still let an app probe the person's network on its ports, and that rustls's error text could return a device's certificate names. Now `net::dest::special` also refuses 10/8, 172.16/12, 192.168/16, 100.64/10, 0/8 and 240/4 for resolved answers, and RESOLVE_ON leaves them out of what it returns and keeps. An answer that leads nowhere else is Network, and `fetch` reports "the host's name leads to a private address". A record that names an address literally (`addrs:`) still reaches it. Apps see a fixed error kind for TLS failures, never rustls's Debug text.

The boot cases reach their mock DNS's fixtures and the HTTPS mock by name, on QEMU's user network, so the rule has one exception. With `online=test` on the kernel command line, 10.0.2.0/24 counts as reachable, and only that subnet, never all private ranges. xtask puts `online=test` beside `dns=` for the cases that use the mock DNS. `xtask::image::slots::build_release` refuses any command-line word starting `online=` or `test=`, and a host test pins that the release image's `limine.conf` never carries `online=`. Production boots therefore get the full rule.
