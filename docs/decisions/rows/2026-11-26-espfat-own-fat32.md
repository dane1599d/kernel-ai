needed-by: P8, built 2026-11-26 (row G43; S-io)
decision: The on-device ESP writer is our own no_std `espfat` crate, not fatfs 0.3.6, which ADR 0008 §12 and ADR 0004 name
---
P8 writes a signed Limine per slot to the ESP from the device, so ring 3 needs a FAT32 writer that builds without std. ADR 0008 §12 and ADR 0004 named rust-fatfs 0.3.6 (MIT) for it. Without std, fatfs 0.3.6 depends on `core_io` 0.1. On 2026-11-26, `core_io` 0.1.20210325's build script failed on our pinned nightly-2026-10-14 for `x86_64-unknown-none` with "Unknown compiler version, upgrade core_io?". It only knows the nightlies it was cut for. crates.io has no newer fatfs. 0.4 exists only on rafalh/rust-fatfs's git master, and pinning an unreleased git source is a supply-chain risk neither ADR covers, so it was not taken. `espfat` is about 1,050 lines with no dependencies, and is the reading counterpart of `xtask/src/image/fat32.rs`. Its scope is what P8 needs. It mounts FAT32 with 512-byte sectors, reads files by long or 8.3 name, and replaces an existing file's contents. It never formats a volume, creates a directory or file, or writes a name, so it writes no long names. The replace is crash-safe by design, with a flush between each phase: new clusters, both FATs' chains, one sector switching the directory entry, then the old chain freed and FSInfo's count. A cut anywhere leaves the old file or the new one, read the same through either FAT copy; host tests cut after every sector write and at random subsets of each flush's writes. Hostile volumes (a bad BPB, chains that loop, leave the volume or do not fit the file's size, directories past FAT's 65,536 entries) are refused with an error, never a panic. Files written by either side read back byte-identical through the other's reader. **Limit:** a cut can leak clusters (marked used, named by no file) in one or both FATs. That costs space, never data. `Volume::reclaim` frees them, and `Volume::check` counts them. Clusters marked bad are never freed or counted free. Before every replace, the whole tree is walked: each chain must be sound, the same in every FAT copy in use, and named once, or nothing is written. **An unsound volume:** one bad chain anywhere on the ESP blocks every replace and reclaim, and espfat has no repair. The device then writes nothing to the ESP, so the slot it boots and its Limine stay as they were. P8's update reports the error and leaves the new slot unbootable, and the ESP is fixed only by rewriting it whole from the host, as the installer first wrote it. A repair on the device is not built, since guessing which of two disagreeing chains is right could free the wrong file. The ADRs' fatfs lines stay as they are; this row supersedes them for the device.
