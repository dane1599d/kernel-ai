needed-by: P5 task 14, host half, built 2026-11-19 (lane AG; ADR 0013 section 6; the kernel's per-handle counter is lane K's turn)
decision: An agent's network budget is counted per handle per day by `netdest::DayMeter`: sends and receives both count, a send that would pass the budget is refused whole and charges nothing, a receive is counted when the app reads it (it may pass the budget by its own bytes, then nothing more moves that day), and the day turns forward only
---
The founder decided on 2026-11-18 that an agent gets 10 MB a day unless its manifest asks for more, and never more than 512 MB (`kaiagent::NetBudget`). P5 task 14 has the kernel count those bytes on the agent's `NetDest` handle. `DayMeter` is that rule with no kernel in it: `no_std`, no allocation, 24 bytes a handle. The kernel keeps one per agent handle, made from the manifest's `bytes/day` (`DayMeter::from_mib`). It calls `try_send` before bytes leave, and refuses the send by name when it gets `OverBudget { used, budget }`. It calls `try_receive` when the app reads (since #1433's review, the receive's whole `cap` is charged before the read and the unread part given back, so two receives sharing a meter cannot both pass the budget), and refuses further connects, sends and receives once `has_room` is false (receives since bug hunt 5's H5-18). A receive cannot be taken back, so it is counted and may overshoot by its own size, and the next move that day is refused. A later day starts the count again. An earlier day, a clock gone back, is treated as the same day, so it never buys more bytes. A budget of 0 (`net none`) moves nothing, and the counts saturate, never overflow.
