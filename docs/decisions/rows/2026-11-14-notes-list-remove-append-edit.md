needed-by: the first-time-user audit, item 15 (Notes cannot list, delete or edit), built 2026-11-14 (AP-1; A-core reviews the model-facing rows, fluency and actbench before merge)
decision: Notes gets four actions, `list`, `remove`, `append` and `edit`, each undone by a snapshot, and a Delete button; `find` stays as it is.
---
"Show my notes", "delete the ideas note" and "add milk to my shopping note" all failed because Notes could only add, count, find ids, get and say its version, and the window had no way to delete. `app:notes/actions@1.0.0` (`components/notes/wit/notes.wit`) grows in place, as an app's interface may (only the `kai:` packages are frozen, ADR 0003): `list` returns one line `id: first line` for each note, the first 100, each line cut at 60 characters, a reply that fits one message and is read-only; `remove(id)` takes a note away (declared destructive, so a standing instruction cannot run it unasked, and undone by a snapshot like `add`); `append(id, text)` adds a line at the end of a note; `edit(id, text)` replaces its whole text. The three that change answer with a line (`Removed note 2.`, `Added to note 1.`, `Changed note 3.`), as the Editor's actions do, so the model's second round has something to say. A note holds at most 2000 bytes and the state still at most `MAX_STATE`: a note that would not fit is refused (`a note holds at most 2000 bytes`, `notes are full`) and left as it was. An id that is not there, or nothing to add, is an error naming it, not a trap. Ids are not given again after a removal. The window's build writes each change to its storage as `add` does (`stored::save` already took a removed note's key away), and its editor closes if the note it had open is removed. In the window the Delete button shows only while a note is open and asks first: a person's click is a window event, not an action, so it has no snapshot to undo (the same as the editing it sits beside) and is not bound to a row. The first press changes the button to "Press again to delete" and leaves the note; only a later press of the same note's button, with no other event between and a pause of 600 ms after the press before it, removes it and goes back to "No note open". The pause is on the call's clock (`compsdk::app::now_ms`): a double click (two presses a few hundred ms apart) and a held key (a press every few tens of ms) are one press, and each press inside the pause moves it on, so holding never confirms. `comp_notes::Actions` gets the four as default methods (nothing for `list`, a refusal for the rest), so the older versions that ship for the live-swap and rollback tests, `notes-v1` and `notes-bad`, are untouched and export the new functions with those answers. The lines a person says reach these rows because the OS adds the words that mean the same to a row's function-name cues (`shellcore/src/apps.rs`, `SAME_ASK`): `remove` also answers "delete" and "erase", `list` "show", `edit` "change", "replace" and "rewrite", `append` "add". The app's own `cues=` stay dropped at load, so an app cannot widen what a row is a request for; the OS list is fixed, and each group is one meaning, so "delete eggs from note 2" is not a request for `append`. A line that asks to be told does not ask for a change (ADR 0002): in `agentabi::consent::cued`, a cue after a telling word (`describe`, `explain`, `tell`, `show`, `list`, `summarize`, `report`) in the same clause is not a cue for a row that changes things, so "tell me how to delete note 2" and "can you explain how to remove note 2" run no `remove` and are refused as lines that only ask to be told, while "delete note 2 and tell me when it is done" still runs it and a row that only reads (`list`) is still asked for by "show my notes". The line still names the action, so a complaint beside it takes no vague reading: "tell me how to delete note 2, notes is so slow" is refused, not taken as a want (`named_any` counts a telling clause's cue, from #883). This holds for every row that changes things, the OS's too ("tell me how to switch to round robin" no longer runs the switch); its tests are in `agentabi` and `shellcore`. What this does not do, on purpose: `find` still returns ids only. The audit asked it to return first lines, but changing its result type inside `@1.0.0` breaks the version scenarios that compare its answers across a swap (`livecore`'s `scenario.rs`) and the older versions; `list` is where a first line comes from, and `find` then `get` or `list` is what the model does. Model input changes: nine rows in the apps turn instead of five, and the `apps` arm of actbench has four new tasks (`show me all my notes`, `add eggs to note 1`, `delete note 2`, `change note 3 to buy bread`), reported, not gated. The fluency gate (`fluency-model.yml`, started by hand) and the actbench `apps` arm are the checks the audit asks for before merge: they need A-core's item 3 (the apps turn built from installed packages, not from windows that are open) to show the rows to the model on a fresh boot, so the runs follow that. Not run here.
