**Disk.** `fs` keeps only sealed blobs, which it hashes as they are written, so a finished download is copied from `.partial/` into the store, not renamed. The partial file stays until the copy is kept. A download therefore needs the rest of its partial file, then the whole file again, plus the 256 MiB margin (`modelchan::fetch::disk_need`). Once the partial file is whole, the copy needs the length plus the margin. The 8 GiB release `kai-data` holds Qwen3-4B's 2.5 GB twice with room to spare. A follow-up for `fs` could adopt a verified file as a sealed blob without the copy.

**Memory.** `kabi::Metrics::total_frames` counts frames up to the highest usable address, holes included. QEMU's q35 maps a large guest's memory past its first 2 GiB above the 4 GiB line, so a 4,160 MiB guest tracks about 6 GiB. So it cannot say what memory the VM was given, and `guest_mib` (the size xtask gives a VM for a model) needs that. `Metrics` gains `ram_frames` at its end: the memory map's RAM kinds (usable, the kernel and modules, bootloader- and ACPI-reclaimable, ACPI NVS), in use or not. The kernel logs it at boot. `modelchan::fetch::guest_mib_of` rounds it up to the 64 MiB step VMs are sized in. METRICS now takes the caller's buffer size in its second argument. A size of 0, which every program built before this passes, fills ABI 1.3's bytes and no more, so an older program is never written past its buffer. That makes it an addition: ABI 1.4. The `handles` case checks the 1.3 size and prints the RAM.

**Offers.** `updated` answers `models offers` with `kai-offers 1`: each signed target with a pinned source on a host models come from, largest first, and whether it is stored, fits, or is short of memory or disk, with the numbers. The largest that fits is recommended. It has at most 64 lines, and a line that does not parse refuses the whole answer. `models ask <id>` answers `ok Download <size> from <host>` or why not. Both read METRICS, the store volume's `Df`, and what `.partial/` holds of each target.
