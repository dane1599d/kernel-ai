needed-by: P8 row 5 (G51; builds on #1503's `sbom.yml`)
decision: The release ships a CycloneDX SBOM, built on both build runners and required byte-identical, checked against NOTICES.txt and deny.toml's licences, and covered by SHA256SUMS
---
`release.yml`'s `build` job (runners a and b) installs cargo-cyclonedx 0.5.9 and runs `.github/release/sbom.sh`, which merges the per-package files into `kernel-ai.cdx.json`: no serial number or timestamp, components sorted by name and version, no checkout path in a `bom-ref`, so one commit gives one file. `cargo xtask notices --check-sbom` then fails when a crate NOTICES.txt lists is not a component, when a Parts line that looks like a crate does not parse, or when a registry component's licence is none or is not one `deny.toml` allows (its own `licences::choose`, with the `clarify` entries; our own crates, with a `file://` purl, are listed and not judged). `assemble` requires both runners' SBOMs to be `cmp`-identical and ships it as `kernel-ai-<version>.cdx.json`, which `SHA256SUMS` covers and the attestation's `release-assets/*` takes. The release has six assets, not five. Unsigned beyond that, like every release file until the signing round. The job is in `release.yml`'s build, not `release-prepare.yml`: `release-prepare` runs only by hand and makes what the founder signs, while the build runners are the pair whose bytes already must match and whose files are the assets. `sbom.yml` (the SBOM on main) still has its own copy of the merge; it can call `sbom.sh` once #1550 lands.
