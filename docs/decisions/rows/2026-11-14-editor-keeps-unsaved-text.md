needed-by: the first-time-user audit, item 8 (the Editor loses unsaved text), built 2026-11-14 (AP-1; the comphost lines are lane C's, in #880)
decision: the Editor tells the host when its window holds text that is not saved, the app does not nap while it does (for 30 minutes at most, comphost's cap), a close with such text asks Save, Discard or Cancel, and a nap keeps the file that was open and the text not saved in it.
---
The founder typed in the Editor, went to the Terminal for two minutes and came back to an empty Editor: the app had napped, its checkpoint held nothing (`V1` had one reserved field), and the close button threw the text away without a word. Four changes. (1) The shared window loop gets the call that was already in `kai:ui/view@0.1.1`: `Sink::set_unsaved` (a default that says nothing, so no other app changes) and `Shown::mark_unsaved`, which sends the flag with the next present, before its commit, once per change, and again for a window opened anew. The Editor marks its window whenever `Files::unsaved` says so: edits the disk does not have, a component's source not built, or a line being typed. The flag reaches `desktop` as `toplevel.set_unsaved`, which is what makes the agent's `window_close` ask the user first (ADR 0005 section 6, until now never exercised by an app). (2) `comphost` holds the nap's lease while any of its windows, shown or hidden, has a last frame that says unsaved (`Ui::unsaved`, next to the lease it already holds for a change or a file in flight), so an Editor with unsaved text does not nap, whatever else is idle; and a close of a window whose frame says unsaved goes to the app as `CloseRequested`, where every other close is a hide. Those lines are in lane C's #880 (its commit 5114d340 took them from this PR), which owns comphost's close and hide; this PR does not touch comphost, so it merges in either order, and the lease and the question both work once #880 is in. (3) A close of that window does not close it: the status line says "Not saved" and a row of Save, Discard and Cancel buttons shows, with the keys S, D and Esc for the same (other keys are not typed meanwhile). Save sends Ctrl-S as typed, so the screen lets go of the line it holds, and closes when the file is written; a refused write keeps the window and says why in the status. Discard closes the window and drops the editor's state, so a window opened again says "No file is open". A component's source has nothing to save, so it has Discard and Cancel only. For this the window's `kai:ui/input` is bound in `editor-window` itself, with the Editor's own OS handle (it can write a file and draw the code view), and not with `comp-ui-bind`'s `input!`, which hands an app `kai:ui/view` alone; `EditorWindow::ui_event` replaces the `OnUi` impl. (4) The checkpoint keeps the file open (`V1` gets optional fields, so a checkpoint the first version saved still imports and an older version reads a newer one): its path (1), its text as it stood when that is not what the disk has, with the line being typed in it (2), and the cursor's line (3). A woken or swapped-in editor reads the file again from the disk, as for Ctrl-O, and puts the text kept over what it read as one edit, so the file reads as unsaved again, a save writes it, and one undo goes back to the disk's. The kept text wins over a disk file that changed meanwhile; if the file is gone or cannot be read, the text is shown as a new file (a save then refuses to write over a file that is there) and the status says so. Three ways the kept text could still be lost are closed. An open by the agent (`editor_open`, `editor_open_file`) while the text is waiting to be put back, whether for the first call or for the file's read, is refused, saying why, rather than taking its place (a path kept with no text is still taken over). A file that cannot be asked for, read, or opened (a refused read, a file that is not text or has grown past what the editor opens, a path the editor no longer asks the door for) shows the text kept as a new file at the path and says why. And a checkpoint taken while the file's read is out keeps the path and the text, from the read that carries them. One guest test each, which fail on the code before. The text is bounded: at most `KEEP_MAX`, the host's 64 KiB checkpoint limit (`kabi::live::MAX_CHECKPOINT`; the 1 MiB suggested at review cannot be, the host refuses a bigger checkpoint) less 2 KiB, and the session itself takes no text over `MAX_BUNDLE`, 60 KiB, so a compile-time assert says every text the editor holds is kept and a checkpoint with it fits; past it only the path would be kept. This exists because comphost's lease on unsaved text ends after 30 minutes and the app then naps. The read is not asked in `import`: the host takes a `kai:files` request only from a call that a transaction wraps, and a migration is not one (it would trap, and the editor would not come back at all). The path waits in the editor and the first call that is a transaction (a key, a click, the wheel, a size, an answer, a status) reads the file; an explicit open, the agent's or Ctrl-O's, takes its place. A file that cannot be read again says so in the status row. A guest test on the real wasm (`a_checkpoint_with_a_file_open_imports_and_reads_the_file_in_the_first_call_after`) fails on the earlier code at the import. What is not kept: a component's source, which is in the edit service and stays there, and the undo history, which starts again. A restart or a crash (no nap, no checkpoint) with unsaved text still loses it; the file comes back as the disk has it. Opening a file of about 58 KB takes more than the default call fuel (5 million) in the guest tests, and still does with this change's unsaved check taken out, so it is the open itself and not this change; the near-limit test gives it more fuel. Not changed here, and worth knowing: a file near the 60 KB limit may fault on open under the default settings. Not covered by a boot case: the lease and the close rule are comphost's, in #880, with no host test (the loop is not testable off the guest); the rest is host-tested (`comp-ui-bind`, `comp-editor-ui` and `comp-editor-window`'s tests, including the three answers, the refused save and the old and new checkpoint). Lane C's `desk-nap-busy` case (the audit's test 3) is where the nap lease belongs under a boot, with a key sent to the Editor's window.
