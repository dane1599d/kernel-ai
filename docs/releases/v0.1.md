# Kernel AI v0.1: release notes

> **Draft until the tag.** These notes become the GitHub Release's notes when `v0.1.0` is tagged. Until then they describe `main`. What is left before the tag is in the [P4 plan, section 3.5](../plans/p4-apps.md#35-the-v01-checklist): the founder's three items (clearing the names, the root ceremony of task 18 and `release/seq`), then fluency and actbench on the tag's commit. Release candidates (`v0.1.0-rc.N`) use the same notes.

v0.1 is "an AI-native OS you can try", in a VM (QEMU or VirtualBox). Kernel AI is a from-scratch x86_64 operating system in Rust. Its assistant, Kai, runs a language model inside the OS, on the CPU, through the project's own inference engine. There is no cloud and no external server.

## What v0.1 does

- **A desktop.** The OS boots to a desktop on virtio-gpu: windows that open, move and close, fonts, input focus, and the `kai>` panel, which is always there. The panel's Apps sheet lists the installed apps and the ones on offer. When Kai needs your answer, an ask card shows it, and standing rules remember the answer if you want.
- **Seven built-in apps.** Terminal, Files, Notes, Settings, System Monitor, Models and the Editor, each a window drawn through `uikit`. Each app declares its actions, so Kai calls them by name: "show me what's using the most memory" sorts System Monitor by memory, and "move the groceries note to my documents folder" moves it through Files, with undo. Settings switches the theme and shows what each app may do.
- **Kai acts, within limits.** Plain-English requests become typed action calls or Rhai scripts. What only reads runs at once. A change you plainly ask for that can be undone runs at once and is logged. Anything else asks first, through the Allow / Deny menu, and some actions never run. Tiers are enforced by code from each action's declaration, never by the model, and text Kai reads from data cannot raise a tier. `undo` puts the last change back.
- **Models are imported and switched.** The model is not in the image. You attach the pinned GGUF file (below) as a disk. Then type `models import` at the console and allow it. Kernel AI checks the file's SHA-256 against the image's signed `models` role and refuses any other file. `models` lists what is stored, and `models use <id>` makes a model the one from the next restart. Kai does the same through its `model_*` rows, and `undo` switches back. The Models window shows which model runs, each one's licence, and what to ask Kai to switch.
- **TempleOS's `c>` prompt.** `:c` switches the terminal to `c>`, where C compiles and runs as you press Enter, through xcc running as WebAssembly in a ring-3 `cc` service. A redefinition switches its callers. `:dis`, `:defs`, `undo` and `:rhai` work. `cc build` turns a folder of C into an app that installs from the device's own signed repository. Kai writes C too: on spike S12-2, Qwen3-4B wrote correct C 78% of the time on the first try and 92% after one repair.
- **Kai builds apps.** Ask "make me a timer app". Kai writes the app's C from a template, builds it with `cc build` and tries it, and repairs it on the compiler's own words up to 3 times. It does this in the background, one build at a time. When it is done, `install timer` (or `install it`) asks once on the trusted path, then the app opens in a window. `show code` shows the source, which is kept in `/home/user/apps/<name>/`. `undo` removes the app and keeps the source. On the gate of 20 app requests run on a GitHub runner, 18 built, opened and passed a scripted click test.
- **Apps are packages.** The built-ins boot as generation 1 from a TUF-signed repository in the image, and a tampered package is refused by name. `install` takes a package from the image or a local mirror, and `undo` puts the previous set back. The usual aliases (`apt install`, `dnf`, `brew`, `winget`, `pacman -S`) are accepted.
- **Files that survive.** A writable `kai-data` disk holds kaifs, with snapshots, undo and a trash. A power cut in the middle of a write leaves the filesystem consistent.
- **Updates with rollback.** A/B slots, a recovery slot, and offline updates from an update disk: a bad update rolls back by itself, and an update never touches your files.
- **The AI tunes the scheduler.** `tune` lets the model choose a scheduler policy for a program. The kernel runs it as a measured trial with guards and reverts it on any regression. On the M10 exit test the editor's p99 latency fell to 0.44-0.67x of the default's across 5 seeds, with background work unharmed.

## What v0.1 does not do

From the [P4 plan, section 3.6](../plans/p4-apps.md#36-what-v01-does-not-wait-for):

- **No networking** (v0.2). No TLS, no downloads from the OS, no online package repository and no internet `install`. The model is downloaded on the host and imported.
- **No existing apps** (v0.2). No Linux layer, no browser and no media. `apt install python3` answers "Linux packages need the Linux layer (v0.2)".
- **No real hardware** (v0.3). v0.1 runs in a VM only.
- **No production features** (v1.0). No installer, Secure Boot, user accounts, disk encryption or third-party publishers.
- **Within packages:** no dependency solver, no `tool` package kind and no delta updates.

## Known limits

- **File speed.** Files move through kaifs at 25 MB/s write and 26 MB/s read (release build, KVM), against a target of 50 MB/s. The founder accepted this for v0.1. About 80% of the time goes to IPC round trips and the client, and that speed work comes after v0.1.
- **Memory.** The VM needs at least 4 GiB, and 6 GiB or more is recommended. Qwen3-4B, the default, needs a guest of about 4.1 GiB, so a host with 8 GB of RAM or more. On a host with 4 to 8 GB, use Qwen3-1.7B, which `cargo xtask setup` offers there.
- **A 2,048-token context.** Kai's action list, the request, the answer and the conversation so far share it. Conversation memory keeps a few hundred tokens of recent turns (at most 512). When a new turn would go over, the oldest half is dropped. Memory lives in RAM until a reboot, a model switch or `new`.
- **CPU only.** The model runs on the CPU, which needs AVX2, FMA and F16C (AVX-512 is used when present). On a Ryzen 7 7700X with 8 vCPUs, Qwen3-4B loads in 5-10 s and answers at 11-12 tokens/s. An app build takes a minute or more, and only one runs at a time.
- **Kai's apps have no actions of their own.** An app Kai builds opens in a window and works with keys and clicks, but Kai cannot call into it by name yet.
- **The Models window only shows.** Switching and importing happen through Kai or the console (`models use`, `models import`). Doing them in the window comes after v0.1.
- **Only the pinned models import.** A release imports only a model its signed `models` role names, by SHA-256. A GGUF file from anywhere else is refused.

## Try it

### Requirements

- **CPU:** x86_64 with AVX2, FMA and F16C (most PCs from the last ten years).
- **Memory:** 4 GiB for the VM at least, 6 GiB or more recommended (see Known limits).
- **Disk:** about 2.5 GB for the model, plus the image. For a build from source, a few GB more.
- **A VM:** QEMU with OVMF, or VirtualBox 7. QEMU needs a hardware accelerator to be usable with the model: KVM on Linux, KVM inside WSL2 on Windows, or WHPX.

### From the release image, in QEMU

The release's assets are the image `kernel-ai-0.1.0-x86_64.img.zst`, a signed `SHA256SUMS`, `NOTICES.txt` and the source tarball. Check the image against `SHA256SUMS`, then unpack it:

```bash
zstd -d kernel-ai-0.1.0-x86_64.img.zst
```

Download the model (above), or run `cargo xtask setup` from a checkout. Boot with the model as a read-only disk with the serial `kai-import`. The image carries its own writable `kai-data` (partition 5, 8 GiB), so no other disk is needed. For example, on Linux with KVM:

```bash
qemu-system-x86_64 -machine q35 -accel kvm -cpu max -smp 4 -m 6G -drive if=pflash,format=raw,readonly=on,file=OVMF_CODE.fd -drive if=pflash,format=raw,file=OVMF_VARS.fd -drive if=none,id=boot,format=raw,file=kernel-ai-0.1.0-x86_64.img -device virtio-blk-pci,drive=boot,serial=kai-boot,bootindex=0 -drive if=none,id=import,format=raw,readonly=on,file=Qwen3-4B-Instruct-2507-Q4_K_M.gguf -device virtio-blk-pci,drive=import,serial=kai-import
```

Use your own copy of `OVMF_VARS.fd`, which the firmware writes to.

1. The first start installs the release into its slots and restarts once by itself. Leave the VM running.
2. No model runs yet. Press Ctrl+Alt+F12 for the console, type `models import` and press `y` to allow it.
3. `models` shows when the model is stored. Then type `models use qwen3-4b-2507` to make it the model from the next restart.

For VirtualBox, make a VDI with `VBoxManage convertfromraw`, or build the same VM from source with `cargo xtask vbox` (below).

### From source

The tooling is developed on Windows; the QEMU path also runs on Linux. You need Rust through [rustup](https://rustup.rs) (the pinned nightly in `rust-toolchain.toml` installs itself), `curl` and `tar`.

```bash
cargo xtask doctor          # checks your PC and changes nothing
cargo xtask setup           # recommends a model, downloads it with resume, checks its SHA-256
```

On VirtualBox (simplest on Windows):

```bash
cargo xtask vbox            # build the release kernel and its boot disk; create or update the VM "Kernel AI"
cargo xtask vbox --start    # boot it in a VirtualBox window
```

On QEMU:

```bash
cargo xtask run --accel kvm --local qwen3-4b-2507   # Linux
cargo xtask run --accel wsl --local qwen3-4b-2507   # Windows, QEMU in WSL2
```

The [README](../../README.md#try-it) has the details of each path.

### Things to try

| Type or say | What happens |
|---|---|
| `help` | The commands. |
| `show me the cpus please` | Kai writes a read-only script; it is shown and runs at once. |
| `show me what's using the most memory` | System Monitor opens, sorted by memory. |
| `make a note called groceries` | Notes gets the note; `undo` takes it back. |
| `models` | The models stored, and which one runs. |
| `:c`, then `I64 Sq(I64 x) { return x * x; }`, then `Sq(7)` | C, run as you press Enter: `= 49`. `:dis Sq` shows its code, and `:rhai` goes back. |
| `make me a timer app` | Kai writes, builds and tries it, then `install timer` asks before it installs. |
| `tune editor` | With `--workload A` from source: Kai proposes a scheduler change, you type yes, and the kernel trials it. `tune undo` reverts it. |

With no model, everything except Kai works, and `:setup` prints the steps.

## Signing and licence

The image and `SHA256SUMS` are TUF targets in [`dane1599d/kernel-ai-updates`](https://github.com/dane1599d/kernel-ai-updates), under the project's root of trust, so an OS that updates from them checks every byte. Two clean builds of the tag give the same image SHA-256, and the source tarball rebuilds offline.

Kernel AI is under the [Mozilla Public License 2.0](../../LICENSE). `kabi/`, `compsdk/` and the interfaces under `wit/` are `MIT OR Apache-2.0`, so apps for Kernel AI may use any licence. What Kai writes for you is yours. Third-party code keeps its own licence, listed in `NOTICES.txt`, which is the same file in the image and the release.
