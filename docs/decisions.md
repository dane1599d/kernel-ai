# Kernel AI: decision log

One place for every project decision. Founder decisions are settled. Open decisions carry a recommended default and the earliest milestone that needs them. Defaults are only recommendations. Each open decision is confirmed with the founder when its milestone starts.

Sources: the five merged memos in `docs/research/`. Milestones are defined in `docs/roadmap.md`.

## Settled by the founder (2026-10-14)

| Area | Decision |
|---|---|
| Product | Our own operating system, a from-scratch x86_64 kernel in Rust, inspired by TempleOS, with a local LLM built in. |
| Kernel base | Our own kernel: Limine bootloader plus rust-osdev crates. Asterinas OSTD is a design reference only; no code is reused. |
| Privilege model | Rings are kept. No single address space. |
| Scripts and live editing | Run in user mode (ring 3) under a restarting supervisor. The kernel stays a static binary with no in-kernel linker. |
| Script runtime | Rhai for the REPL language. Plain WebAssembly modules on wasmi are the live-swappable unit. |
| Shell | Our own framebuffer terminal. |
| LLM placement | Remote only for the POC, on the Mac mini M4 (16 GB). Control plane only: it writes hints, scripts and policy choices, and never sits in the scheduling or reclaim path. |
| Testing | QEMU only. Dev host: AMD Ryzen 7 7700X, RTX 4070 Ti, 32 GB, Windows 11 Home (no Hyper-V). KVM inside WSL2 is verified present. |
| Gaming | A multi-year goal, outside the POC. The POC proves AI-tuned scheduling and memory policy on synthetic workloads. |
| Pace | No fixed schedule. Effort figures measure progress, not deadlines. |
| Process | Nothing is built until the founder approves the roadmap. Each milestone ends when its exit test passes. |

| M3, decided 2026-10-16 | Interrupt controllers and timer | xAPIC (memory-mapped) local APIC and I/O APIC; the legacy PIC stays masked. HPET is the reference clock; a PIT fallback is not implemented. The local APIC timer runs one-shot at 1 kHz, re-armed each tick for an absolute HPET deadline so latency never accumulates. |
| M3, decided 2026-10-16 | ACPI | Own minimal reader (`acpitables` crate: RSDP, XSDT or RSDT, MADT, HPET) instead of the `acpi` crate, whose 6.x handler needs about 25 methods. Revisit if AML is needed. |
| M3, decided 2026-10-16 | Keyboard | PS/2 with scancode set 1 translation, decoded by `pc-keyboard`. The interrupt only queues scancodes; decoding happens outside the handler. Tests type keys through the QEMU monitor. |
| M4, decided 2026-10-16 | Kernel preemption | Kernel threads are preemptible by the timer and by wake-ups, with a preempt count that defers switching (used around memory-manager calls). Interrupt handlers acknowledge the APIC before switching. |
| M4, decided 2026-10-16 | Scheduler policy shape | Mechanism and policy split like sched_ext, in the host-tested `sched` crate: `Core` owns states, sleep, wake and a 200 ms watchdog; a `SchedPolicy` trait (enqueue, dequeue, pick_next, tick, preempt_on_wake, reset) picks threads. Policies are compiled in, allocation-free and swappable at runtime. Default `Interactive` (woken threads first, preempt on wake); fallback `RoundRobin` (10 ms slices) after an ejection. |
| M5, decided 2026-10-16 | Multiprocessing | Limine starts the other CPUs in xAPIC mode; each gets its own GDT, TSS with a guarded double-fault stack, per-CPU data via GS_BASE, and its own scheduler core. Threads go to the least-loaded CPU and an idle-ish CPU pulls work every 4 ticks when another has at least two more threads. Wake-ups for another CPU send a reschedule interrupt. Unmap and protect shoot down other CPUs' TLB entries by interrupt. Exited threads are reaped once their registers are saved, and their stacks are reused. Tests run with 4 CPUs under KVM; under TCG the VM gets at most as many CPUs as the host has cores (2 on private-repo CI runners), because an overcommitted host delays virtual CPUs in ways the kernel cannot control. The 10-minute storm runs in a separate soak workflow. |
| M6, decided 2026-10-17 | Virtio interrupts | Polling for now: the network is polled at most every 2 ms during a request. MSI-X later. |
| M6, decided 2026-10-17 | LLM transport and client | `virtio-drivers` 0.13 on q35 PCIe (ECAM from the MCFG table, bus 0 only), every DMA buffer bounced through contiguous frames; `smoltcp` 0.14 with a static 10.0.2.15/24 via 10.0.2.2 on QEMU user networking; one HTTP/1.1 request per connection, non-streaming OpenAI chat JSON via the host-tested `llmproto` crate (`serde_json`). The client runs as part of the terminal thread in the kernel for now; it moves to a ring-3 service at M7. Plain HTTP on the LAN; no TLS in the kernel. |
| M6, decided 2026-10-17 | LLM server | Any OpenAI-compatible server; llama.cpp `llama-server` recommended for the grammar support M8 needs. `cargo xtask run --llm IP:PORT --model NAME` points the kernel at it. Tests use a built-in mock server in xtask, since CI cannot reach the Mac mini. |
| M6, decided 2026-10-17 (terminal) | Terminal | Line editing with backspace and a fixed command set: help, ask, policy, threads, cpus, mem, net, uptime, clear. The document model and storage are still open for M7. Previous default: A node tree for documents. A tar initrd plus a RAM file system. |
| M7, decided 2026-10-16 | Floating point in ring 3 | Soft-float everywhere. CR0.EM is set and CR4.OSFXSR and OSXSAVE are clear on every CPU, so x87, SSE and VEX instructions trap and no FPU or vector state is ever saved. Rhai will be built with `no_float`. |
| M7, decided 2026-10-16 | Ring 3 and system calls | SYSCALL in, `iretq` out (never `sysretq`); one trap frame for interrupts, exceptions and system calls; `swapgs` on every ring-3 transition, paranoid entry for NMI, double fault and machine check. SMEP, SMAP and UMIP on when the CPU has them; FSGSBASE, PCID and SYSENTER off. QEMU uses `-cpu max` under KVM and TCG. The ABI lives in the `kabi` crate. |
| M7, decided 2026-10-16 | Processes | One thread per process, one PML4 per process sharing the kernel half, programs as static ELF executables in Limine modules (validated by the host-tested `uelf` crate). Each process has a page quota (page tables included) and a CPU-burst limit; exceeding either, or any ring-3 exception, kills only that process. The kernel never dereferences user pointers: it copies through the process's page tables. |
| M7, decided 2026-10-16 | Supervisor design | One ring-3 supervisor, restarted by a kernel init thread. Exit records queue in the kernel and are redelivered if the supervisor dies before acknowledging them; its state (restart counts, pids, start times, in the host-tested `supervise` crate's format) lives in a kernel-owned region. Restart policy: exponential backoff with a restart-intensity cap, tunable per service in the plan. |
| M7, decided 2026-10-16 | LLM client | A ring-3 `llm` service builds and parses the HTTP and JSON. The kernel terminal reaches it by name through kernel IPC; the kernel only carries bytes to the server named on its command line, so ring 3 never chooses a destination. |
| M7, follow-up (founder) | M7 exit test | Not written yet; the founder writes it. It should show a crashing, a runaway and a memory-hungry service each killed and restarted without affecting the kernel (the `crasher`, `spinner` and `hog` programs already exist). M7 shipped with every earlier CI case passing and `net`/`terminal` running through the ring-3 llm service. |
| M8, decided 2026-10-17 | LLM script API | Seven functions, each with one arity and one effect. `cpus`, `memory`, `uptime_ms`, `processes`, `threads` and `get_policy` read; `set_policy` is the only change. `ask` is not available to scripts. The model answers with a JSON object `{script, summary}` requested through the OpenAI `response_format` JSON schema rather than a GBNF grammar, so any OpenAI-compatible server works; thinking off, temperature 0.2, seed 42. The prompt and request builder live in `llmproto::script`, shared by the OS and the fluency harness. |
| M8, decided 2026-10-17 | Script checks and sandbox | A language-level sandbox. Scripts use a strict Rhai profile: no loops, closures, `fn`, `Fn`, `call`, `curry` or `eval`, strict variables, at most 40 lines of 120 ASCII characters and 3 KiB, and a summary of at most 100 characters. Each script gets a trial run before the user is asked. It runs against stub values with the same time and size limits as any run and a 1 MiB heap budget (lines the founder types get 8 MiB). The heap is checked on every operation, and `replace` and `pad` check their result size, map keys and nested values included, before allocating. The confirmed run uses the same limits. It then runs in a fresh engine that has only the functions named in its text (strings and comments included, so the list can only be too long). The confirmation shows that list first, then the model's summary, then every line, and the question repeats what the script changes. The terminal drops keys typed before the question, declines a confirmation it cannot show on one screen with every line on one row, and does not pass on `answer` lines typed at its normal prompt. Only `y` or `yes` to that script's id runs it, within 120 s. The shell process is the boundary; running scripts in a process of their own is deferred. |
| M8, decided 2026-10-17 | Repair | One repair round. An answer refused by the text checks, the strict compile or the trial run goes back to the model once, with the reason. Server errors, cut-off answers and declined requests are not repaired. The stub lists as many services, with names as long, as the real system can have, so an index it rejects is wrong everywhere. Only an integer operator error on its values (a division by zero, an overflow) is let through, and the confirmation then says which lines went untried. A Ctrl-C during the trial cancels the request instead of asking for a repair. |
| M8, decided 2026-10-17 | Fluency gate harness | `cargo xtask fluency --llm IP:PORT --model NAME [--repeat N]` runs 50 tasks through the shell's own path, with a fixed-value stand-in for the OS, and writes every run to `target/fluency/`. The tasks: 10 reads, 10 arithmetic and formatting, 10 on lists without loops, 10 on strings, arrays and maps, 5 changes and 5 impossible requests. Each task's reference script runs as a unit test. |

| M9 | Swap tiers, interfaces, state format | Tier 0 and tier 1 only. Interfaces written as WIT on paper. CBOR for saved state. |
| M9 | Probation and history | 30 s or N epochs of probation. One standby version resident, the last 5 stored. The LLM only proposes. |
| M9 | Build service | Edits compile on the host, in WSL2 or Windows. Git is the source of truth. |
| M9a, decided 2026-10-17 | Live components | A component is a plain WebAssembly module (Rust built for `wasm32-unknown-unknown` with a `component` profile), run on wasmi 2.0 by `comphost`: one ring-3 process per component, named after it (`program=comphost` in the plan). Each version ships as boot module `comp/<component>/<label>.wasm`, carrying a `kai.manifest` section and its bundled source in `kai.source`. The contract is `kai-lifecycle-1` (in `kabi::live`, WIT on paper): init, import (the migration), export, handle, health and self-test, with `kai.log` the only import, so a component has no side effects. |
| M9a, decided 2026-10-17 | Swap and probation | The host swaps between two requests. It stages the candidate (manifest, compile, link), transfers the state (the candidate imports it, or the old version writes an older schema it reads), and verifies it (self-test, health, export), then starts probation. During probation each request runs on the old version first and then on the candidate, whose reply is sent, so a rollback loses nothing. A request the old version fails is not given to the candidate either, so both stay in step with the state the kernel holds. Probation ends after N calls and T ms and a last health check: 16 calls and 30 s by default, 3 calls and 0 ms in CI. Rollbacks come only from faults and failed checks, never from time. The host owns the swap; the supervisor only restarts processes. |
| M9a, decided 2026-10-17 | Kernel ledger | The kernel never runs WebAssembly. It keeps the versions and, for each component, a ledger whose rules are `livecore::ledger`: the active version, its last CBOR checkpoint (at most 64 KiB), a list of failed versions (retried with `force`) and a 32-event history. These sit behind COMP_FETCH, COMP_EVENT and COMP_RESTORE, which need `cap::COMPONENT`, granted only to `comphost`. A host that dies restarts on the active version with its data; one that died mid-swap is rolled back by the next. |
| M9a, decided 2026-10-17 | wasmi settings | wasmi is built with `portable-dispatch`, and the `wasmhost` crate at opt-level 2 even in dev builds. The default dispatch grows the native stack with every instruction when debug assertions are on, and unoptimised host-function glue crashes. Each version gets its own engine, compiled eagerly. Start functions are refused and only the target's six proposals are allowed. Fuel is set per call (5 million per request), and each instance has 2 MiB of memory. |
| M9b, decided 2026-10-17 | Edit loop and trust split | A ring-3 `edit` service (its logic in the host-tested `editcore` crate) holds the editing session, talks to the build service and uploads. The kernel owns the store, the labels, the change view, the yes or no, and every `ctl swap`, so a human confirms every apply at a prompt the kernel draws, about a change the kernel computed. This follows M7 and M8: parsing and editing in ring 3, the kernel confirming. |
| M9b, decided 2026-10-17 | Editor | An ed-style line editor reached by `:edit <component> [version]`: `files`, `open`, `p`, `find`, `s \|old\|new\|` (exactly one match; `s <n> ...` for one line), `c`, `i`, `a`, `d`, `undo`, `diff`, `build`, `reset`, `help`, plus the kernel's `:apply`, `:quit` and `:revert`. Each line keeps its own ending, so a CRLF checkout is never shown as changed on every line. A full-screen editor comes in M9d over the same session. |
| M9b, decided 2026-10-17 | Calls and capability | COMP_PUT (24), COMP_READ (26: a component's Info, or a version's bytes) and BUILD (27), all needing `cap::PUBLISH`. PUBLISH is granted only when the service and the program are both `edit`, and no process may call that service. COMP_CONTROL (25) stays reserved for M9c, and its rule never relays swap, rollback, reset or force. HTTP still goes only to the LLM server. |
| M9b, decided 2026-10-17 | Second destination | `build=IP:PORT` and `build_token=HEX` on the kernel command line, parsed like `llm=`. BUILD sends only there, with HTTP's 64 KiB request and 256 KiB response caps and at most 300 s. The edit service is planned only when they are set, and the plan log hides the token. |
| M9b, decided 2026-10-17 | Uploads and labels | The store names uploads `e1`, `e2`, ... per component per boot; a label is never reused. An upload must say in its manifest that it is that label of this component, keep the active version's interface, come from a stored base, name a 40-hex git commit, and be at most 192 KiB. The last 5 are kept (failed ones evicted first, never the active version or the candidate), at most 2 MiB for all, as shared bytes filled with `try_reserve`. A swap to a version no longer stored is refused. The kernel keeps its own copy of the build service's reply to the latest build (BUILD carries it) and accepts an upload only if it is exactly that reply's artifact, base and commit, so what it shows and runs is what the host built, whatever the edit service says. An upload must also keep the file list of the version it was built from and stay within the editor's limits (60 KiB of source, 16 files, 4,000 lines a file), and bundle paths must be plain. Uploads live in RAM; their source stays in git. |
| M9b, decided 2026-10-17 | Confirmation | `:apply` picks the newest upload from the kernel's store, shows the change between the active version's source and the upload's (per file, the lines between the common first and last lines, byte for byte, with `? ` leads), and asks `apply e1 to notes? yes/no>`, dropping keys typed earlier. It refuses an upload that is active, on probation or failed before, and does not ask when the change does not fit one screen: more lines than rows, a line wider than the screen (a wrapped tail could pass for a line of its own), or anything but printable ASCII, which it could not show exactly (the console font has nothing else, and invisible or reordering characters could hide a change). A typed `:swap` or `:revert` is its own confirmation, and trusts what was reviewed in the editor. |
| M9b, decided 2026-10-17 | Edit rules | Only existing `.rs` files under the component's `src` may change; Cargo.toml and the file set are frozen. New lines may not name `include`, `include_str`, `include_bytes`, `env`, `option_env`, `path`, `asm`, `global_asm`, `naked_asm` or `debugger_visualizer` (an identifier cannot be split or hidden, so this also catches the `cfg_attr` and comment forms of `#[path]`), nor hold anything but printable ASCII. The word list is the guard: an inner attribute such as `#![...]` reads no host file unless it names one of those words. The edit service checks them for quick feedback and the build service enforces them. This is a guardrail for code the founder types, not a sandbox: one is required in M9c before any LLM-written source is built. |
| M9b, decided 2026-10-17 | Build service | A thread in the `cargo xtask` process (`test`, and `run --edit`) on 127.0.0.1 and a free port, with a per-run token header, one build at a time. It runs `cargo build --frozen -p comp-notes --target wasm32-unknown-unknown --profile component` with KAI_VERSION, a scrubbed environment and `target/edit-build`, killed after 120 s, and packs with xtask's own packer, so uploads are built exactly like boot versions. The guest reaches it at 10.0.2.2 under KVM and TCG alike. |
| M9b, decided 2026-10-17 | Git as the source of truth | Every successful build is committed (trailers Kai-Component, Kai-Label, Kai-Base, Kai-Build and Kai-Source) on its base's commit before the artifact leaves the host, under `refs/kai/builds/<component>/<label>-<source12>`. Each ledger commit moves `refs/heads/kai/<component>`; each rollback writes `refs/kai/rollbacks/...`. Nothing is pushed. Tests build in a fresh snapshot repository of the working tree, so an uncommitted tree still tests and the founder's repository is checked unchanged; `run --edit` uses a clone at `.live/repo` (gitignored, outside `target/`), refuses uncommitted build inputs, and the founder fetches `kai/notes` from it. |
| M9b, decided 2026-10-17 | Ledger to git | A bounded outbox (16 jobs, drops counted) records each commit and rollback the ledger accepts. A kernel thread hands the oldest to the edit service over IPC, which posts it to the build service, and keeps it until git acknowledges it with a commit. No new system call; it survives restarts of either service. |
| M9b, decided 2026-10-17 | History and revert | The ledger keeps the last 6 active versions. `:revert <component> [n]` swaps to the nth earlier distinct one, refusing one that is no longer stored. |
| M9b, decided 2026-10-17 | Default plan and exit test | notes starts on version 2, the real component, so `:edit notes` edits `components/notes`; the M9a case keeps version 1. `editcore::scenario` runs on the host first (real builds) and then as boot case `edit`: a good edit declined, then applied live with its state; a compile error that changes nothing; an index-out-of-bounds edit that rolls back by trap; a host restart on the upload; and a revert. xtask then checks the throwaway repository's refs, trees and reflogs, and that the founder's repository is unchanged. |
| M9b, decided 2026-10-17 | Dependencies | No new third-party crates; the git command line, not git2. diffy 0.5.2 was looked at and not adopted; similar 3.2.0 is noted for M9d's full diff. |
| M9c | LLM assist (the rest not built yet) | The LLM drafts a change and its forward and reverse migrations, tried with `ctl try` through COMP_CONTROL on captured state before any apply; and a build sandbox, which must exist before any LLM-written source is built. Drafts go through the same rules, build and `:apply`. The LLM never holds PUBLISH. |
| M9c, decided 2026-10-18 | State viewer | `:state <component>` prints the state the ledger last saved: a header from the kernel, then the CBOR read by `livecore::cbor`, a walker with no dependencies, as indented lines with the shell's `= ` lead. Arrays and maps that fit stay on one line. Every major type is read, indefinite lengths included; floats show as their bits. A length is checked against the bytes left before anything is allocated, nesting stops at 32 and reading at 4,096 items, and text is escaped, so every line is printable ASCII that fits the screen. The `live` case and its host run check that the restored `notes` state reads as schema 2. |
| M9c, decided 2026-10-18 | Who wrote a build | The build request is `kai-build 2` with a required `origin founder\|model` line. A request without it, or with any other value, does not decode, so the host refuses it. The edit service sends `founder` until drafts exist. |
| M9c, decided 2026-10-18 | Rehearsing a swap | `ctl try <version>`, and the kernel's `:try <name> <version>`, rehearse a swap on copies. A fresh instance of the active version takes the last checkpoint; the candidate takes the state from it as a swap would and passes its self-test, health check and export; both run the last 8 requests the host served without a fault, and the candidate may not answer `err` where the old copy answered `ok`; last, a fresh old version must read what the candidate writes in the old schema, if it can write it. Nothing goes to the ledger and the live instance is not asked anything, so a try changes no state; fetching the candidate counts as a fetch, as for a swap. During probation it answers busy. The live scenario tries 2 before swapping to it, and tries 3-health, which fails its health check. |
| M9c, decided 2026-10-18 | COMP_CONTROL (25) | Active. A PUBLISH holder (only `edit`) has the kernel send `ctl <request>` to a live component's host as caller 0, waiting at most 60 s. The kernel relays only `status`, `source [file]` and `try <version>` (`kabi::live::relayable`, its own check, whatever the component's parser would accept): swap, rollback, reset and force get Invalid, and a name that is not a live component's host gets NotFound. The editor's `try` uses it to rehearse the version it just built. The `edit` case tries e1 after building it and checks that swap, rollback, reset and a bad label are refused. |
| M9c, decided 2026-10-18 | Rollback explanation | `:why <name>` asks the model to explain the component's latest rollback. The kernel takes the facts from its own ledger alone (`livecore::why`: the version dropped and the one active then, which of them failed and what the reason means, the detail the host gave for that rollback, the versions that failed before, the recent events), at most 1 KiB of printable ASCII, and sends them to the llm service's new `explain` verb (`llmproto::explain`: its own system prompt, thinking off, a fixed seed, plain text back, at most 600 characters). The answer is printed under a kernel line naming the rollback and saying the text is the model's and may be wrong, each line with the shell's `= ` lead and cut to the screen's width. It is read-only and nothing waits on it. The ledger now keeps the latest rollback apart from its 32-entry history, with its own detail (`last_detail` may belong to a later event) and whether the active version, not the one dropped, failed (POISON). A model that spends its tokens thinking is reported as such. The `live` case runs the llm service and checks that the mock's answer names the scenario's last rollback, 3-spin (host-restart). |
| M9d | Source navigation and persistence (not built) | A full-screen editor with non-blocking builds and a pager; traps and fault reports mapped to file and line, opening the editor from them; Ctrl-click with a pointer driver; booting committed live versions under a pending/known-good boot manifest; drafts that survive a crash; edits that add files or change Cargo.toml. |
| M9d, decided 2026-10-19 | Panic locations | A component's panic handler calls a second import, `kai.panic(file, line, column)`, just before it traps. Like `kai.log` it has no side effects, so running a request on two versions stays safe; it is optional, so a module without it still loads. The host keeps that location for the current call only and reports the trap as `panicked at <path>:<line>:<col>`. A path is shown whole only when it is a plain relative path inside the workspace, with each `\` turned into `/`; anything else (an absolute path into a registry or the toolchain, `..`, odd bytes, over 64 bytes) is cut to `.../<file name>`, so no host path reaches a log. The fault and rollback lines, `:why` and `ctl try` all carry it. The live and edit scenarios check that 3-trap and part D's e2 name their lines. |
| M9d, decided 2026-10-19 | Opening a trap's line | The ledger keeps the latest trap that named a line, with the version whose source holds it: the active version for a fault, the candidate for a rollback, and the active version again when it, not the candidate, failed. `:fault [name]` opens that version in the editor at that line (`open <component> <label> at <path>:<line>` on the edit wire; on the session's own version it only moves the cursor and keeps undo), and never drops edits that are not built.
