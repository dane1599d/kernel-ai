# Live-editable system: hot swap, state migration and rollback

- **Date:** 2026-10-14
- **Status:** Research memo (no code)
- **Scope:** How Kernel AI can put any component's source one click away and reload that component without a reboot while keeping privilege rings. Covers Theseus live evolution, Redox and MINIX restartable drivers, the choice of swap unit, source bundling and indexing, state migration and rollback, the LLM's role, what must never be hot-swapped, and a POC architecture.
- **Related memos:** [rust-kernel-foundation.md](./rust-kernel-foundation.md), [compiler-in-terminal.md](./compiler-in-terminal.md), [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md), [templeos-components.md](./templeos-components.md)

## Conclusions

1. **TempleOS and Theseus both get their live editing from a single address space and a single privilege level, and the fixed decisions rule both out. Kernel AI has to build live editing layer by layer.** TempleOS runs everything in ring 0 in one identity-mapped address map. Its command line compiles straight into heap memory, and reloading a file just compiles it again into fresh memory, with no state migration [E1-E3]. Theseus credits its single swap mechanism, and its joint evolution of applications and kernel, to its single address space and single privilege level (SAS/SPL). It also says the compiler cannot check components that run in different address spaces or privilege levels [E8, E9, E11]. With rings kept, ring-3 code and ring-0 code need different swap mechanisms, and some ring-0 code cannot be swapped at all (conclusion 11).

2. **Use four swap tiers, ordered by risk. Tiers 0 and 1 make up the POC, tier 2 is an optional POC experiment, and tier 3 comes after the POC.**
   - **Tier 0, data only.** This covers policy parameters and the choice among policies compiled into the kernel. A stable policy hook does the swap and drains state from the old policy into the new one, as Theseus's `set_policy` does [E38].
   - **Tier 1, ring-3 processes.** This covers services, the control-plane policy agent, the LLM client, REPL programs, workload generators and, later, drivers. Each is replaced whole, with explicit state handoff and hot rollback, as in PROTEOS and MINIX 3 [E65, E66, E71, E74-E77].
   - **Tier 2, sandboxed kernel policy code.** Core WebAssembly modules run in-kernel under `wasmi` with fuel limits and a built-in native fallback, the sched_ext pattern [E98, E110, E113].
   - **Tier 3, native Rust kernel modules relinked at runtime.** This is the Theseus model [E18].

   Each tier down the list has less isolation and is harder to roll back. The POC goal, AI-driven scheduling and memory policy on synthetic workloads, needs only tiers 0 and 1 [A6].

3. **Theseus is the best design reference for tier 3, but it is not a viable code base.** Its paper measured critical swap pauses of tens to a few hundred microseconds, a 385 µs median downtime for channel evolution, and load stages of 19.5-179.6 ms on bare metal [E27, E28]. Its fault recovery handled 69% of manifested faults [E31]. However, the current `swap_crates` states that it guarantees nothing about correctness after a swap, and it calls state-transfer functions through an unchecked cast [E39]. The toolchain is pinned to `nightly-2023-10-27` [E45]. In 2023 the maintainer said live evolution had "fallen out of focus" [E50], and the default branch has had no commits since 2024-09-22 [E49]. The MIT licence lets us read and adapt `mod_mgmt`, `crate_metadata` and `crate_swap`, with attribution [E49].

4. **In depth, Theseus live evolution means relinking a crate while the system runs. It works because Theseus removes the state that would otherwise block a swap.**
   - **Unit.** Every component, boot code included, is a cell: one crate, compiled to one object file, loaded at runtime with its section bounds and dependencies recorded. The statically linked `nano_core` replaces itself with dynamically loaded cells at the end of boot [E5-E7].
   - **State.** The main obstacle to swapping is state spill: a component keeping state on behalf of its clients [E14]. Theseus avoids it by having clients own their resource objects. Unavoidable hardware-mandated state (GDT, TSS, IDT and interrupt contexts) goes into a separate store [E15, E16].
   - **Swap.** New cells load into an isolated namespace, and dependencies are checked in both directions. Relocations in dependent cells are rewritten, state is transferred by hand-written `Into` functions, and the old cells are removed atomically. A commit to the repository drives the whole process through an evolution manifest generated by a build server [E18-E20]. If function types changed, the swap waits for quiescence [E21]. Rust's `fn` type assumes code lives forever, so each task owns the cell that holds its entry function [E26].
   - **Results.** Theseus swapped in a new scheduler on a system that had no multi-scheduler support [E29]. Dynamic linking overhead stayed negligible: a context switch took 0.35 µs, against 0.34 µs on a static build [E34]. With 13 injected IPC faults, Theseus recovered from 11, while MINIX 3 recovered from none [E33]. The whole system was about 38,000 lines of Rust and four person-years of work [E35].
   - **Preconditions.** All of this assumes safe Rust in one address space at one privilege level. Under those conditions Theseus calls hardware protection "useless anyway" [E12, E13].

5. **About half of Theseus's mechanism carries over to Kernel AI's ring-0 half. The other half depends on SAS/SPL.** A conventional higher-half kernel is itself one address space at one privilege level, so the following carry over to kernel modules [E5, E6, E11, E18, E39, E40]:
   - module bounds kept at runtime;
   - per-section dependencies derived from `.rela` sections;
   - loading into an isolated namespace;
   - two-way dependency checks;
   - relinking by rewriting relocations;
   - a copy of `.data`/`.bss` plus explicit transfer functions;
   - an atomic commit;
   - a cache of swapped-out modules for near-instant code rollback.

   These do not carry over:
   - joint relinking of applications and kernel across ring 3 and ring 0 [E8];
   - clients that own kernel resource objects directly, because ring-3 tasks need kernel handle tables, which Theseus itself defines as state spill [E15];
   - the one-to-one virtual-to-physical mapping invariant [E10];
   - scanning user stacks for pointers into swapped code [E36];
   - reclaiming a crashed process's kernel resources purely by unwinding [E17, E30].

6. **Because the Rust ABI is unstable, native module swapping only works with the same compiler, the same flags and the same build tree. Every swap boundary must therefore be narrow and non-generic, and must be crossed with bytes or C-layout types.** The facts behind this:
   - Default type layout "can be changed with each compilation" [E51].
   - The Rust ABI has no stability guarantee [E52].
   - rustc refuses metadata produced by another compiler version [E53].
   - `TypeId` hashes change between releases [E55].
   - Symbol hashes depend on the compiler version, the source directory, the target directory and `-C metadata` [E46, E54].
   - Theseus resolves symbols by their hashed names and needs an identical build environment for updates [E41, E50].
   - Generic code is monomorphized into its callers, so swapping the crate that defines it leaves the callers' copies unchanged [E25].
   - The candidate stable ABIs, crABI and `#[export]`, are still open proposals [E57, E58].
   - `abi_stable` cannot be used in a `no_std` kernel [E59]. `stabby` builds in `no_std` but adds a third-party layer [E60].
   - The closest existing Rust hot-patching tool, Subsecond, patches only the top-level crate, works only with `debug_assertions`, and cannot change struct layouts [E64].

   Ring-3 processes (tier 1) and Wasm modules (tier 2) avoid the problem entirely: state crosses the boundary as versioned bytes, and any compiler version can build them.

7. **Redox does not have working restartable drivers today. Cite MINIX 3 for the restart model and PROTEOS for live update with rollback.** Redox drivers are user-space daemons [E80, E81], and the Redox book says a failed driver "could be ignored or restarted" [E82]. In mainline, though, nothing restarts a driver:
   - `init` reaps child processes in a loop and discards their exit status [E83].
   - Its unit scheduler only starts jobs [E84].
   - The driver spawner only waits for a readiness byte [E85].

   The only restart Redox reports is a 5-second timeout on NVMe initialization. A student-built health-monitor daemon sits unmerged in a personal GitLab namespace [E86, E87]. Redox also has no IOMMU support yet [E88]. MINIX 3's reincarnation server is the working precedent. It uses heartbeats and per-component policy scripts with exponential backoff. It recovered from all 347 induced driver crashes under emulation, with a mean NIC recovery time of 0.48 s [E65-E69]. It recovers only stateless drivers, and never character-stream drivers. MINIX itself has been dormant since 2018 [E73], so we copy its design, not its code.

8. **For tier 1, follow PROTEOS.** Replace the whole process at the top of its event loop and run state transfer in the new process. Leave the old process untouched until the new one passes a probation window, and roll back by switching back to it. PROTEOS's only update point is the top of each process's event loop, so no state is on the stack at update time [E75]. The old process is never modified, so an update can abort and roll back at any stage, and MMU isolation stops errors in the new version from reaching the old one [E74, E76]. Across 50 real updates, PROTEOS needed 265 lines of custom state-transfer code in total, with a median update time of 272 ms [E77]. MINIX 3 rolls back the same way: it kills the new instance and resumes the old one [E71]. Privilege rings make this the cheapest design to build, and it needs only what the foundation memo already plans for M3 (ring 3, syscalls and an ELF loader).

9. **WebAssembly components are the right long-term interface for swappable code. In our `no_std` kernel they can run only through Wasmtime's ahead-of-time path, and never on `wasmi`. If tier 2 is built, use core Wasm modules in `wasmi` behind a small hand-written export contract. The reason is cost, not impossibility.** A component cannot export memory, and it talks only through WIT-typed imports and exports [E106, E107]. That is exactly the property a swap boundary needs. Neither runtime fits the POC well:
   - `wasmi` 2.0.0 is a `no_std` interpreter with fuel metering, but it does not implement the component model. Its maintainer calls component support "not planned nor unplanned" [E110, E111, E113].
   - The one bridge library that adds components on top of `wasmi` uses `std` [E112].
   - Wasmtime in `no_std` excludes Cranelift and Winch, so nothing can be compiled inside the kernel. It does support the `runtime`, `component-model` and `pulley` features in `no_std`. `Component::deserialize` loads a component that the identical Wasmtime version precompiled on the host, either as native code or as Pulley bytecode that needs no executable memory — [wasmtime `Component` docs](https://docs.rs/wasmtime/latest/wasmtime/component/struct.Component.html) (docs.rs, latest; accessed 2026-10-14). The costs are lockstep upgrades with every Wasmtime release, an `unsafe` deserialize, and an unstable embedder platform API (`wasmtime-platform.h`) [E108, E109].
   - Theseus's own Wasmtime port hit the same wall [E48].

   Write the contract (for example `decide`, `save_state`, `load_state`, `migrate`) in WIT on paper as well, so a later move to components is mechanical [A6].

10. **Sandboxed code is fast enough for policy at control-plane rates, and too slow for mechanism.** Interpreters run about 10x slower than optimizing JITs, and baseline compilers 1.5-3x slower [E115]. Even ahead-of-time compiled Wasm commonly pays 20-30% or more for software fault isolation [E116], and browser Wasm ran 45-55% slower than native code on SPEC [E114]. So the scheduler's per-decision path and the page-fault path stay native, as tier-0 policies with parameters. Wasm policy code runs once per epoch, or per decision only as a measured experiment with a native fallback [E98]. This matches the fixed rule that the LLM stays off the hot path.

11. **Some components must never be hot-swapped. Changes to them are applied by rebuilding and rebooting the VM, and the UI must say so.** Every prior system examined here keeps such a list:
    - Linux livepatch cannot patch its own ftrace handler, or untraceable code such as `noinstr` entry code [E90, E94].
    - kpatch does not patch data structures, and calls some hardware-init changes "inherently incompatible" [E95].
    - MINIX cannot live-update its microkernel. It restricts updates of its VM server, because changing page tables during an update can make rollback impossible [E70, E72].
    - PROTEOS cannot update its kernel message-passing substrate [E79].
    - Erlang must restart its runtime to upgrade ERTS, Kernel, STDLIB or SASL [E104].
    - Theseus holds the GDT, TSS and IDT for the whole run, cannot automatically migrate data structures that assembly code accesses, and cannot recover from faults in its own unwinder [E16, E22, E31].
    - Even TempleOS compiles its kernel and compiler ahead of time and JIT-compiles only the rest [E3].

    The list for Kernel AI is in the Recommendation.

12. **State migration must be explicit and versioned, and it must run inside the new version. Rollback must be layered, and rolling back code does not roll back state.** Rust layout can change on every compile, and `postcard` is not self-describing [E51, E117]. So every swappable component exports versioned state and supplies a `migrate(old_version, bytes)` function, the counterpart of Erlang's `code_change` and of Theseus's `Into`-based transfer functions [E20, E101]. Ksplice shows where the human effort goes: 56 of 64 Linux security patches needed no new code, and the rest needed about 17 lines each, mostly because they changed persistent data structures [E96]. Adding new fields beside an unchanged structure, as Linux's shadow variables do, avoids a migration altogether [E93]. State rollback needs a reverse migration. Linux documents that once a live patch has changed system state, going back may no longer be safe [E92], and Theseus loses buffered messages when a channel evolves from async to sync [E24]. Use three rollback layers:
    - **Keep the old version resident until probation ends.** Precedents: Erlang's current/old code, MINIX, PROTEOS and Theseus's crate cache [E40, E71, E74, E100].
    - **Fall back to a built-in default** on any trap, timeout or stall, as sched_ext does [E98].
    - **Boot a new version only after it has been confirmed.** Precedents: OTP `make_permanent`, MCUboot test swaps, systemd boot counting and Android A/B updates [E102, E118-E120].

13. **One-click source is cheap. Ship the compressed source and the line tables in the image, and build the symbol index on the host.**
    - **Size.** Rust source averages about 34 bytes per line and compresses 4.6-5.1x with DEFLATE when each file is compressed separately (5.3-6.0x as one solid stream). A 50,000-line system is therefore roughly 0.3-0.4 MB compressed [A1, A2].
    - **Decompression.** `miniz_oxide` decompresses in `no_std` with `alloc`. `lz4_flex` works in `no_std` only for its block format [E129, E130].
    - **Address to source line.** `gimli` and `addr2line` map addresses to file and line in `no_std` through `Context::from_dwarf`. `-C debuginfo=line-tables-only` keeps only what backtraces need [E126-E128].
    - **Symbol index.** Build the cross-reference index on the host with rust-analyzer's SCIP output or Universal Ctags, and convert it to a compact table. The `scip` crate cannot be used in the kernel because it depends on a `std`-only protobuf library [E131-E134].

    TempleOS already shows the user model: all source on the disk, and a key that follows any symbol to its source [E2, E3].

14. **The LLM explains and proposes, a human confirms every apply, and rollback is mechanical and never waits for the LLM.** At about 20 tokens/s, a 1,000-token patch takes about 50 s to generate [A3]. A watchdog must act within milliseconds, and rollback must still work when the network or the Mac mini is down. The kpatch maintainers require a human expert to review every live patch, even when the tooling builds it [E95]. In the kGym benchmark, the best 2024 frontier models fixed 0.72% of Linux kernel crashes unassisted and 5.38% when given the buggy files [E135]. A local 8B model should not apply kernel-side changes on its own. After a rollback, the LLM gets the fault log and explains what went wrong.

### Recommendation

Build a **swap orchestrator** in the kernel. It is never swapped itself, and it drives four tiers. In the POC, every component's source is viewable and editable. Tier 0 and tier 1 components reload without a reboot. Every other component shows an "edit, rebuild, reboot" badge, and in QEMU that path costs seconds, not minutes.

**1. The swap orchestrator (ring 0, never swapped).** It owns:
- **Component registry:** id, tier, interface version, active version, standby version, build id, and the source-bundle entry.
- **Swap state machine:** shown in the table below.
- **State-blob store:** versioned and keyed by component id and state version, in the role of MINIX's data store [E65]. It is never keyed by `TypeId` [E47, E55].
- **Health checks and an append-only commit log.**

The shell drives it. It never calls the LLM.

| Step | What happens | If it fails |
|---|---|---|
| Stage | A new artifact arrives: a policy id plus a parameter block (tier 0), an ELF (tier 1), a `.wasm` file (tier 2), or a relocatable object (tier 3). The orchestrator checks the build id, the interface version and, for Wasm, module validation. | Reject. Nothing has changed. |
| Prepare | The old instance is asked to reach its update point (the top of its event loop, or between two policy decisions) and to export its state. A timeout applies [E75, E76]. | Abort. The old instance keeps running. |
| Transfer | The new instance starts and imports the state through `migrate(old_version, bytes)`. The old instance is suspended, not freed [E71, E74]. | Kill the new instance and resume the old one [E71, E76]. |
| Probation | The new instance serves for a fixed window while health checks run: no traps, no stalled runnable task, deadline misses and reclaim failures within bounds, heartbeats answered [E65, E98]. | Roll back. Reverse-migrate the state if a reverse function exists. Otherwise resume the old instance from its last exported state, and failing that, re-initialize the old version. Log the event. |
| Commit | Free the old instance, or keep its code cached for instant code rollback [E40]. Mark the version "confirmed" so the next boot uses it [E102, E120]. | (Commit does not fail.) |

**2. Tier 0: policy slots.** These are the scheduler `SchedPolicy` and reclaim `ReclaimPolicy` hooks from the foundation memo's M3 and M6 ([rust-kernel-foundation.md](./rust-kernel-foundation.md)).
- A native default policy is compiled in and can never be removed.
- Changing policy drains the old run queue into the new policy under the run-queue lock, as Theseus's `set_policy` does [E38].
- Parameter blocks go through stage/commit/revert.
- A stall watchdog restores the default, as in sched_ext [E98]. A separate lockup detector, like Linux's soft- and hard-lockup watchdogs, is the last resort [E99].
- This tier involves no code loading.

**3. Tier 1: restartable ring-3 processes.** Each swappable service is written as an event loop with exactly one update point [E75].
- The orchestrator acts as the reincarnation server: heartbeats, exponential backoff, and an OTP-style restart-intensity cap (for example, more than 3 restarts in 30 s escalates to "disabled, needs a human") [E65, E66, E105].
- POC targets: the control-plane policy agent (reads telemetry, writes tier-0 parameter blocks), the synthetic workload generators, the LLM client and REPL programs.
- Device drivers stay in the kernel for the POC, as the foundation memo plans for M5. They are edit-and-reboot components.
- A first ring-3 driver demo, if any, should use a virtio device, because the spec makes a restart clean: initialization starts with a reset, and a reset device stops touching its queues [E122]. It should also be a device whose lost data is harmless, such as virtio-console. MINIX shows that a restart cannot tell which data of an interrupted stream was lost [E67].

**4. Tier 2: sandboxed policy code (optional POC experiment).**
- One `wasmi` instance per policy slot, with fuel set per call [E110, E113].
- The export contract is `decide(ctx)`, `save_state() -> bytes`, `load_state(bytes, version)` and `migrate(old_version, bytes)`, mirrored in a WIT file on paper [E106, E107].
- A trap or running out of fuel falls back to the tier-0 default for the rest of the epoch, and the module rolls back.
- Build this tier only if the in-terminal compiler already targets Wasm ([compiler-in-terminal.md](./compiler-in-terminal.md)), or if tier-0 experiments show that the LLM needs to express policy logic that parameters cannot capture.

**5. Tier 3: native kernel modules (after the POC).** The preconditions:
- one pinned nightly for kernel and modules, with identical flags and `codegen-units = 1` [E44-E46];
- entry tables declared `extern "C"` with `#[no_mangle]`, and only `repr(C)` types or byte blobs crossing the boundary [E52, E56];
- no generics or `#[inline]` items across the boundary [E25];
- an explicit `reinit()` entry point, because a swap does not re-run initialization [E23];
- old module memory freed only after quiescence, proven by reference counts plus an entry barrier, not by stack scanning [E89, E91];
- if old code is still in use at commit time, the commit is refused rather than the tasks killed (OTP's `soft_purge` rather than `brutal_purge` [E103]);
- a cache of the previous version [E40];
- a loader built on `object` or `goblin`, or evaluated against `elf_loader` [E123-E125].

Read Theseus's `mod_mgmt`, `crate_metadata` and `crate_swap` (MIT) before writing this [E39-E43, E49].

**6. Source access.** The host build produces four artifacts, stamped with one build id:
- a per-file DEFLATE source bundle of first-party and vendored source [A1];
- DWARF line tables (`line-tables-only`) [E128];
- a symbol index converted from Universal Ctags at first, and from rust-analyzer SCIP later [E131-E134];
- a component manifest mapping each component to its files, tier, interface version and build id.

The framebuffer terminal opens source from a symbol, a file name, a backtrace frame or a fault address, which `addr2line` resolves [E127]. Each component shows a badge: "hot reload" (tiers 0-2), "restart" (tier 1 drivers), or "edit, rebuild, reboot" (the never-swap list). If the build id of the running binary does not match the bundle, the viewer refuses to label the source "current".

**7. Edit-and-apply loop.** Follow Theseus's "build server plus evolution manifest" pattern [E19]:
1. Edits made inside the VM sync back to the host git repository, as ZealOS's `sync` script does [E4].
2. The host builds with the pinned toolchain.
3. The artifact returns over virtio-net, and the orchestrator stages it.
4. Every applied change is a git commit. The commit log therefore serves as both the evolution manifest and the rollback history.

Compilation inside the VM is limited to whatever the in-terminal compiler produces.

**8. The LLM's role.**

| Role | The LLM does | Rules and mechanism do | Why |
|---|---|---|---|
| Explain | Summarizes a component from its source bundle, index, recent log and telemetry | Retrieve the exact source lines, symbols and addresses by deterministic lookup | Summarizing suits the LLM; lookups must be exact |
| Edit | Drafts a diff, plus the forward and reverse `migrate` functions and a round-trip test | Show the diff; build on the host; run the round-trip test; reject any change to the interface version | Human review of every live patch [E95]; low LLM fix rates on kernel crashes [E135] |
| Apply | Recommends only | A human confirms; the orchestrator stages, transfers and runs probation | Apply must be deterministic and logged |
| Roll back | Explains the fault log afterwards and proposes a fix | Traps, watchdog and health checks trigger rollback automatically | Must work offline and within milliseconds [A3] |
| Tune scheduler and memory | Proposes parameter sets, or picks among pre-built policies once per epoch | Bounds checks, stage/commit/revert, fallback to the default [E98] | Fixed decision: the LLM stays off the hot path |

**9. Never hot-swap (POC).** Changes to these components are applied by rebuild and reboot.

| Component | Why it is excluded | Precedent |
|---|---|---|
| Interrupt, exception and syscall entry stubs; IDT, GDT, TSS | The hardware holds pointers to them, and their assembly encodes struct layouts | Theseus holds GDT, TSS and IDT for the whole run [E16] and excludes assembly-accessed structures [E22]; Linux `noinstr` [E94] |
| Context switch and the task-struct fields it touches | Assembly depends on the layout, and every task passes through this code | [E22] |
| Page-table code, the active page tables, the frame allocator, the kernel heap allocator | They serve faults and allocations during the swap itself, and changed page tables can make rollback impossible | MINIX VM [E72]; PROTEOS non-transferable allocator state [E78]; Theseus's single-allocator assumption [E9] |
| Module loader, relinker, orchestrator, state-blob store | They are the swap machinery itself | Livepatch cannot patch its own handler [E90]; PROTEOS updates its update manager only last and with kernel help [E79]; Theseus's failed-cell-replacement cases [E31] |
| Panic, fault and unwind path; watchdog; built-in default policies; health checker | They are the recovery path, and must work when everything else fails | Theseus's unwinder-fault cases [E31]; sched_ext's default fallback [E98] |
| LAPIC timer, IPI and TLB-shootdown core | Many components depend on them, and they drive preemption | Splitting Theseus's APIC cell needed a system pause [E28] |
| Syscall dispatch and kernel IPC substrate | Every tier-1 swap goes through them | PROTEOS [E79] |
| The policy-hook and tier-1 interface definitions themselves | Changing an interface invalidates every implementation | Linux MODVERSIONS refuses mismatched modules [E97] |
| In-kernel device drivers (POC) | Data in flight and device state cannot be handed over without a reset | MINIX character drivers [E67]; virtio reset rule [E122] |

### Not possible / not viable

- **Theseus-style joint relinking of applications and kernel cannot work across a ring-3/ring-0 boundary with separate address spaces.** Theseus ties it to SAS/SPL. A syscall reduces typed arguments to raw integers, and the compiler cannot check across privilege levels [E8, E9].
- **Ring-3 tasks cannot own kernel resource objects directly, so kernel handle tables, and the state spill they bring, are unavoidable in Kernel AI** [E15].
- **Theseus's one-to-one virtual-to-physical mapping invariant cannot hold** once processes have separate page tables and share memory [E10].
- **A Rust-ABI module built with a different rustc, different layout- or symbol-affecting flags, or a different build tree cannot be safely hot-loaded into the running kernel.** The Rust ABI and the default layout are unstable, E0514 rejects foreign metadata, and symbol hashes include the compiler version and paths [E46, E51-E55].
- **crABI and `#[export]` cannot serve as the module ABI.** Both are open proposals with no stabilization [E57, E58].
- **`abi_stable` cannot be used in a `no_std` kernel.** `libloading` and `parking_lot` are non-optional dependencies [E59].
- **Generic or inlined code cannot be swapped by swapping only the crate that defines it.** The callers hold monomorphized copies [E25].
- **Unwinding from an arbitrary faulting instruction cannot be guaranteed to release what the faulting frame holds.** Rust/LLVM emit only synchronous unwind tables. This was the main cause of Theseus's 31% recovery failures [E32].
- **The built-in `x86_64-unknown-none` target cannot do unwinding-based recovery as shipped,** because its panic strategy is `Abort` [E61]. Theseus uses a custom target with `panic-strategy: unwind` [E43], and custom target specs need nightly `-Zunstable-options` since Rust 1.95 [E62].
- **WebAssembly components cannot run on `wasmi` today** [E110-E112].
- **Wasmtime cannot compile Wasm inside a `no_std` kernel, and cannot load an artifact precompiled by a different Wasmtime version** [E108, E109].
- **A swap cannot be assumed to re-run initialization.** Theseus calls no initializer on load, so code that runs once at boot does not reconfigure the device when swapped [E23].
- **Old code cannot be freed while any task may still be running or sleeping in it.** Livepatch allows module removal only when a module has no users, and Erlang kills processes left in old code on purge [E91, E100].
- **Shared state cannot be rolled back automatically once a swap has changed it, unless a reverse migration exists** [E24, E92]. A migration without a reverse is "no automatic rollback; reboot to recover".
- **`postcard`, or any non-self-describing serde format, cannot migrate state between struct versions by itself** [E117].
- **A restart cannot transparently recover an interrupted stream (character) driver, cannot cure a deterministic bug, and cannot revive hardware that a fresh driver cannot reinitialize** [E67].
- **Redox cannot be cited or reused as a working driver-restart implementation.** Mainline has none [E83-E87].
- **PROTEOS's automated state transfer cannot be reused for Rust.** It depends on an LLVM link-time instrumentation pass plus annotations, built for its own C system [E78]. A Rust equivalent would be a research project, not POC work.
- **Rollback cannot depend on the LLM.** The LLM host can be unreachable, and generation takes seconds to minutes at 20 tok/s [A3].
- **The `scip` crate cannot read a SCIP index in the kernel,** because rust-protobuf has no `no_std` support and imports `std::io` [E133]. Likewise, `lz4_flex` frames, the `addr2line` loader, and the `object` crate's default `compression` feature cannot be used in `no_std` [E123, E127, E130].
- **Without an IOMMU, a ring-3 driver's DMA is not hardware-confined.** Redox has the same gap [E88]. Ring-3 drivers improve fault isolation but not DMA safety.

Left-clicking a file name edits the file, and right-clicking `#include`s it. — [TempleOS Doc/Welcome.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Welcome.DD) (undated; accessed 2026-10-14)

Its links point only to local files and symbol source addresses. - [E4] ZealOS changes can be made "inside the OS, as intended by Terry". After the user powers off the VM, a `sync` script merges the changes into the repository. — [ZealOS README](https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/README.md) (master, undated; accessed 2026-10-14)

### Theseus: structure, and the role of single address space and single privilege level

- [E5] A Theseus cell is a Rust crate at implementation time, one object file at compile time, and a set of loaded memory regions with per-section bounds and dependency metadata at runtime. There are "no exemptions for components within a 'base kernel' image". Theseus avoids Rust submodules, because "module bounds are lost when the crate is built into an object file". — [Boos et al., Theseus, OSDI 2020, §3.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E6] Theseus loads and links every cell at runtime on demand. It parses the object file, loads the sections, writes relocations, recursively loads missing cells and adds public symbols to a symbol map. The loaded cells form a CellNamespace. — [OSDI 2020, §3.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E7] The statically linked `nano_core` "fully replaces itself at the final bootstrap stage by dynamically loading its constituent cells one by one". — [OSDI 2020, §3.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E8] The paper credits SAS/SPL with enabling Theseus to "(i) implement a single mechanism, cell swapping, uniformly applicable to any cell, and (ii) jointly evolve cells from multiple system layers (e.g., applications and kernel components)". — [OSDI 2020, §3.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E9] Intralingual design assumes a single address space, a single privilege level and a single allocator instance, because "the compiler cannot holistically observe or check the behavior of independently-compiled components that run in different address spaces or privilege levels". A Linux syscall "loses the type and lifetime information of its arguments because they must be reduced to raw integer values". — [OSDI 2020, §4.1-4.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E10] Invariant M.1 says the mapping from virtual pages to physical frames must be one-to-one (bijective), so that no aliasing happens beneath the language. The paper says this is possible and non-restrictive in Theseus's SAS environment. — [OSDI 2020, §4.3.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E11] Theseus "completely foregoes hardware privilege levels (x86's Ring 0 vs. Ring 3 distinction) and multiple address spaces ... we run all code at Ring 0 in a single virtual address space". Cell dependencies come from the ELF `.rela.*` relocation sections. — [Theseus Book: idea](https://www.theseus-os.com/Theseus/book/design/idea.html) and [design](https://www.theseus-os.com/Theseus/book/design/design.html) (undated; accessed 2026-10-14)
- [E12] To get Theseus's benefits, components must be written in safe Rust. "Unsafe languages require hardware protection or dynamic interposition on memory accesses (à la SFI) if isolation was desired." — [OSDI 2020, §8](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E13] The thesis says "the single address space and single privilege level OS environment renders hardware protection facilities useless anyway". It adds that stateless communication "may be inefficient in systems with multiple address spaces and privilege levels". — [Boos, PhD thesis, Rice University, §8.2.2 and §11.8](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)

### Theseus: state spill and state management

- [E14] State spill is "one software component harboring changed states as a result of handling an interaction from another component, such that their future correctness depends on said states". — [OSDI 2020, §1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E15] Client-side handles force the server to keep a handle table, "a form of state spill". Theseus rejects handles in favour of clients owning the resource object directly ("opaque exportation"). — [OSDI 2020, §5.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E16] Theseus must hold some hardware-required state for the whole run: the "Global Descriptor Table (GDT), Task State Segment (TSS), Interrupt Descriptor Table (IDT)". It also keeps static-lifetime state for asynchronous entry points such as interrupt handlers, and moves this state into `state_db`, a key-value store. — [OSDI 2020, §5.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E17] Theseus keeps no global list of memory allocations. Under memory pressure its default action is "to kill the current task and then proceed to killing lower-priority tasks until an allocation succeeds". — [Boos thesis, §11.5](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)

### Theseus: the live-evolution mechanism

- [E18] Cell swapping has four stages: (i) load the new cells into a new, empty CellNamespace; (ii) verify dependencies in both directions; (iii) redirect dependents by rewriting relocations, updating references on the stack and transferring state; (iv) atomically remove the old cells while moving the new ones in. O old cells may be replaced by N new ones, and O need not equal N. — [OSDI 2020, §6.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E19] "Evolving a running instance of Theseus is as easy as committing to its repository." A build server recompiles and generates an "evolution manifest" listing which new cells replace which old ones. Cells that must evolve together are added automatically. — [OSDI 2020, §6.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E20] Transfer functions for changed data structures are written in Rust using conversion traits such as `Into`. "Generation of transfer functions is ongoing work, thus the results reported in §7.1 use manually-implemented transfer functions." — [OSDI 2020, §6.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E21] "If types (e.g., function signatures) have not changed, Theseus can apply stack changes immediately; otherwise it must wait for quiescence." "Transfer functions are not provably valid in the general case." — [Boos thesis, §8.1](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E22] The thesis states two limits. Evolution "cannot support extralingual usage of changed data structures, e.g., accessing data structure fields in blocks of assembly code", and context switching relies on static layout assertions. Automated evolution is restricted to adjacent versions. — [Boos thesis, §8.1](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E23] "Evolving a cell whose code does not execute again, such as a device initialization routine that only runs once upon boot, will not affect that existing device's configuration. Theseus takes no default action upon loading a crate, such as invoking a crate initializer function." — [Boos thesis, §11.6](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E24] Unwinding a task back to just before its call into a swapped cell (to create a quiescent point) "only works for idempotent functions or those with side effects that can be cleanly undone". When a channel evolves from asynchronous to synchronous, the data already in its buffer is lost. — [Boos thesis, §9.1.1](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E25] Theseus's generically typed channels "will be monomorphized into the cells of the applications that use the channel", so swapping the kernel channel cell does not change the applications. To force a kernel-side swap, the authors added a singleton concrete channel with a non-generic API. — [Boos thesis, §9.1.1](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E26] Rust's `fn` type assumes a static lifetime, but with cell swapping "there is no guarantee that the function's underlying .text section will exist for all eternity". Theseus works around this with a task-owns-cell relation. — [Boos thesis, §11.9](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)

### Theseus: measured evolution and recovery

- [E27] The evolution measurements ran on an Intel NUC 6i7KYK. Loading the new cells took 19.5 ms (ITC channel), 21.3 ms (scheduler) and 65.6 ms (network), and these first two stages run in isolation. "Only the middle two steps (shaded) are critical". The ITC median downtime was 385 µs. The artifact appendix says the critical steps take "tens of µs to a few hundred µs". — [OSDI 2020, §7.1, Figure 2 and appendix A.6](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E28] Splitting the APIC cell into several cells needed a real system pause, because "25+" other cells depend on it for preemption and timers. The pause was under 1.3 ms, and loading the new cells took 179.6 ms. — [Boos thesis, §9.1.4 and Figure 9.1(d)](https://repository.rice.edu/server/api/core/bitstreams/371f7686-a6f2-4416-8d71-8bc947a30fd1/content) (PDF dated 2020-08-14)
- [E29] Theseus replaced its round-robin scheduler with a priority scheduler at runtime, although it "booted as an OS that did not originally contain a priori knowledge of or in-band support for multiple schedulers". — [OSDI 2020, §7.1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E30] Fault recovery escalates in three stages: unwind the failed task, restart it (trait bounds `F: Fn(A) -> R + Clone`, `A: Send + Clone + 'static`), then reload the corrupted cells at new addresses. The recovery path relies on the unwinder, task spawning and object loading. "All of this can safely execute within the context of a CPU exception handler." — [OSDI 2020, §6.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E31] Of 800,000 injected faults (run in QEMU), 0.083% manifested. Theseus recovered from 461 of these: 50 by restarting the task and 411 by reloading cells. It failed on 204: 94 incomplete unwinding, 30 hung tasks ("recoverable via complementary hardware mechanisms like watchdog timers"), 18 failed cell replacements and 62 faults in the unwinder's own code path. — [OSDI 2020, §7.2, Table 1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E32] "Theseus failed to recover from 31% of manifested faults, primarily due to the lack of asynchronous unwinding in Rust/LLVM. The compiler generates synchronous unwinding tables that only cover instructions where language-level exceptions (Rust panics) may occur." — [OSDI 2020, §7.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E33] With 13 deterministic IPC-layer faults injected into both systems, Theseus recovered in all but 2 cases (where tasks hung). "MINIX 3 fails to recover correctly in all 13; its kernel crashes in 11 cases and loses a message in the other two." — [OSDI 2020, §7.2](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E34] Runtime linking costs almost nothing: a context switch takes 0.35 µs on dynamically linked Theseus and 0.34 µs on a statically linked build. — [OSDI 2020, §7.3, Table 3](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E35] Theseus "represents roughly four person-years of effort and comprises ~38000 lines of from-scratch Rust code, 900 lines of bootstrap assembly code, 246 crates of which 176 are first-party". — [OSDI 2020, §1](https://www.usenix.org/system/files/osdi20-boos.pdf) (2020-11-04)
- [E36] When reloading a faulty cell, "Theseus iterates through the stack regions of all the tasks and checks for pointers to the faulty cells text, data, or read-only regions" and rewrites them. The routine "assumes that the version of the cell in the storage is not-tainted". — [Liyanage, MS thesis, Fault Recovery in Theseus Operating System, Rice University, §4.4](https://repository.rice.edu/server/api/core/bitstreams/81f1c44e-b217-4a25-9719-d08186046543/content) (PDF dated 2021-02-10)
- [E37] Recovery downtime: ITC rendezvous took 0.475 ± 0.053 ms to restart the task and 8.214 ± 0.353 ms to reload the cell. ITC async took 0.587 ms and 6.072 ms. Display rendering took 3.815 s and 3.825 s. — [Liyanage MS thesis, Table 5.2](https://repository.rice.edu/server/api/core/bitstreams/81f1c44e-b217-4a25-9719-d08186046543/content) (PDF dated 2021-02-10)

### Ring-based restart and live update: MINIX 3 and PROTEOS

- [E65] The MINIX 3 reincarnation server "guards all servers and drivers". When configured, it "periodically pings the driver and expects it to reply with a heartbeat message". After a restart, the new IPC endpoint is published in a publish/subscribe data store, and dependents reinitialize. — [Herder et al., Roadmap to a Failure-Resilient Operating System, ;login: 32(1)](https://www.usenix.org/system/files/login/articles/618-herder.pdf) (2007-02)
- [E66] Recovery policy is set by per-component scripts, with a sample "binary exponential backoff" script. "Recovery of stateful components is not used by our prototype implementation." "Since the core operating system servers maintain a lot of state, recovery is currently not supported." — [;login: 32(1)](https://www.usenix.org/system/files/login/articles/618-herder.pdf) (2007-02)
- [E67] "Character device drivers cannot be transparently recovered, since it is impossible to tell whether data was lost ... an undecidable problem." "Algorithmic and deterministic failures that repeat after a restart cannot be cured." On real hardware, a few NIC cases could not be reinitialized by the restarted driver and needed a BIOS reset. — [Herder et al., Failure Resilience for Device Drivers, DSN 2007](https://www.minix3.org/docs/jorrit-herder/dsn-dccs07.pdf) (2007)
- [E68] Over 12,500 injected faults produced 347 detectable crashes, and recovery "was successful in 100% of the induced failures". Preliminary real-hardware tests succeeded for more than 99%. The mean recovery time for RTL8139 driver failures was 0.48 s. Throughput loss from repeated NIC driver kills ranged from 25% down to 1%. — [DSN 2007](https://www.minix3.org/docs/jorrit-herder/dsn-dccs07.pdf) (2007)
- [E69] Dynamic driver updates reuse the recovery path, "even if I/O is in progress". The reincarnation server sends SIGTERM, then SIGKILL, and recovery proceeds as after a failure. — [DSN 2007](https://www.minix3.org/docs/jorrit-herder/dsn-dccs07.pdf) (2007)
- [E70] MINIX 3 live update covers all system services, including RS and VM. "There is no support for live updating the microkernel or user applications at this time." The feature is "still in an experimental state, not enabled by default, and available for x86 only". — [MINIX 3 wiki: Live update and rerandomization](https://wiki.minix3.org/doku.php?id=developersguide:liveupdate) (last modified 2022-02-12)
- [E71] "If the state transfer fails, RS performs a rollback: the new instance is killed, and the system resumes execution of the old instance." Process slots are "swapped before the new instance gets to run, and swapped back upon rollback". — [MINIX 3 wiki: Live update](https://wiki.minix3.org/doku.php?id=developersguide:liveupdate) (last modified 2022-02-12)
- [E72] VM can be updated only "with severe restrictions": "If these page tables are changed during a live update, it may be impossible to perform a proper rollback." VM updates are limited to identity transfer and self state transfer. — [MINIX 3 wiki: Live update](https://wiki.minix3.org/doku.php?id=developersguide:liveupdate) (last modified 2022-02-12)
- [E73] The newest commit in the main MINIX repository is "Remove building with NOCRYPTO option", dated 2018-11-14. — [Stichting-MINIX-Research-Foundation/minix commits](https://github.com/Stichting-MINIX-Research-Foundation/minix/commits/master) (2018-11-14)
- [E74] PROTEOS uses "transactional process-level updates". MMU isolation "sandboxes the execution of the entire state transfer code in the new version ... allowing for safe hot rollback". The update manager "can safely abort and rollback the update during any stage of the update process, since no changes are made to the original process". — [Giuffrida, Kuijsten, Tanenbaum, Safe and Automatic Live Update for Operating Systems, ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)
- [E75] "The top of the loop is the only possible update point", and the event-loop design "allows no state objects on the stack at update time". — [ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)
- [E76] Hot rollback is triggered by timeouts in the preparation phase, timeouts in the state-transfer phase and fatal errors in state transfer. "The MMU-based protection prevents any run-time errors from propagating back to the old version." — [ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)
- [E77] Across 50 updates, PROTEOS "required only 265 lines of custom state transfer code in total". Median update time was 272 ms and the maximum 3550 ms. Allocator operations had 6-130% overhead, and replacing a component every 20 s cost "less than 5% macrobenchmark overhead". — [ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)
- [E78] Each OS process is instrumented by "an LLVM link-time pass" that embeds state metadata in an ELF section. The kernel grants "(only) the new process read-only access to the address space of the old process". Annotations are still needed for unions with inner pointers and for "nontransferrable state objects (e.g., allocator variables)". — [ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)
- [E79] PROTEOS cannot "live update the message-passing substrate running in kernel mode". Its update manager "is constrained to be the last process in the update transaction". Failing to isolate state-transfer code "would lower the dependability of our hot rollback strategy". — [ASPLOS 2013](https://download.vusec.net/papers/asplos-2013.pdf) (2013-03-16)

### Linux live patching, modules and watchdogs

- [E89] Livepatch applies patches "on a per-task basis, when the task is deemed safe to switch over". Its main check, stack checking of sleeping tasks, needs `HAVE_RELIABLE_STACKTRACE`. Kernel-exit switching and an idle-loop call cover other cases; "there's not yet such an approach for kthreads". "A patch can remain in transition indefinitely." — [Linux docs: Livepatch](https://docs.kernel.org/livepatch/livepatch.html) (undated; accessed 2026-10-14)
- [E90] "Only functions that can be traced could be patched ... functions implementing ftrace or the livepatch ftrace handler could not be patched. Otherwise, the code would end up in an infinite loop." — [Linux docs: Livepatch, §7](https://docs.kernel.org/livepatch/livepatch.html) (undated; accessed 2026-10-14)
- [E91] Module removal is safe only when no task uses the module's functions. "Removal (rmmod) of patch modules is permanently disabled when the force feature is used", and "If force is used, reboot should be planned". — [Linux docs: Livepatch](https://docs.kernel.org/livepatch/livepatch.html) (undated; accessed 2026-10-14)
- [E92] Shadow variables and callbacks "might change the system behavior or state so that it is no longer safe to go back and use an older livepatch or the original kernel code". — [Linux docs: Livepatch system state changes](https://docs.kernel.org/livepatch/system-state.html) (undated; accessed 2026-10-14)
- [E93] Shadow variables attach new data to existing structures: "Shadow data is allocated separately from parent data structures, which are left unmodified." — [Linux docs: Shadow Variables](https://docs.kernel.org/livepatch/shadow-vars.html) (undated; accessed 2026-10-14)
- [E94] Entry and exit code that must not be instrumented "must be marked with the 'noinstr' attribute, placing that code into a special section inaccessible to instrumentation and debug facilities". — [Linux docs: Entry/exit handling](https://docs.kernel.org/core-api/entry.html) (undated; accessed 2026-10-14)
- [E95] "kpatch patches functions, not data ... changes to data structures are not allowed by default." "Some changes involving hardware init are inherently incompatible with live patching." "Do not blindly apply patches. There is no substitute for human analysis and reasoning on a per-patch basis." — [kpatch Patch Author Guide](https://raw.githubusercontent.com/dynup/kpatch/master/doc/patch-author-guide.md) (master, undated; accessed 2026-10-14)
- [E96] "Most security patches—56 of 64—require no new code" as Ksplice updates. The rest needed "about 17 lines per patch, on average", mainly where a patch changed the semantics of persistent data structures. — [Arnold and Kaashoek, Ksplice, EuroSys 2009](https://pdos.csail.mit.edu/papers/ksplice:eurosys.pdf) (2009)
- [E97] With module versioning, "A CRC value of the full prototype for an exported symbol is created ... if they are not equal, the kernel refuses to load the module." — [Linux docs: Building External Modules](https://docs.kernel.org/kbuild/modules.html) (undated; accessed 2026-10-14)
- [E98] With sched_ext, "The default scheduling behavior is restored anytime an error is detected, a runnable task stalls, or on invoking the SysRq key sequence SysRq-S." — [Linux docs: Extensible Scheduler Class](https://docs.kernel.org/scheduler/sched-ext.html) (undated; accessed 2026-10-14)
- [E99] A soft lockup is the kernel looping in kernel mode "for more than 20 seconds". A hard lockup is detected by a periodic NMI. — [Linux docs: lockup watchdogs](https://docs.kernel.org/admin-guide/lockup-watchdogs.html) (undated; accessed 2026-10-14)

### Estimates and analysis

These items are my own measurements or reasoning, not sourced facts. Each one states its assumptions.

- [A1] **Measured in this session (2026-10-14).** I downloaded the published crate sources [x86_64 0.15.5](https://static.crates.io/crates/x86_64/x86_64-0.15.5.crate) and [smoltcp 0.14.0](https://static.crates.io/crates/smoltcp/smoltcp-0.14.0.crate) and compressed every `.rs` file with Python's `zlib` (DEFLATE, level 6, the same algorithm family `miniz_oxide` implements).

  | Crate | Files | Lines | Raw bytes | Solid DEFLATE | Per-file DEFLATE | Solid xz |
  |---|---|---|---|---|---|---|
  | `x86_64` 0.15.5 | 33 | 12,937 | 445,663 | 83,769 (5.32x) | 97,130 (4.59x) | 65,680 (6.79x) |
  | `smoltcp` 0.14.0 | 115 | 60,908 | 2,061,241 | 342,388 (6.02x) | 407,282 (5.06x) | 248,832 (8.28x) |

  Both crates average about 34 bytes per line. Per-file compression is the relevant figure, because the viewer opens one file at a time. `miniz_oxide`'s exact ratio may differ slightly from `zlib`'s.
- [A2] **Estimate of bundle size.** Assumptions: 34 bytes per line and per-file DEFLATE at 4.6-5.1x, from A1. A 50,000-line kernel plus user space is about 1.7 MB raw and 0.33-0.37 MB compressed. With 200,000 lines of vendored dependencies it is about 6.8 MB raw and 1.3-1.5 MB compressed. The size of DWARF `line-tables-only` sections for a Rust kernel is unmeasured (Open question 4).
- [A3] **Estimate of LLM timing.** Assumption: 20 tokens/s generation on the Mac mini (fixed decision), with prompt processing and network time ignored. A 300-token explanation takes about 15 s and a 1,000-token patch about 50 s. A watchdog or a trap handler must decide within milliseconds. Fault-time rollback therefore cannot involve the LLM, but an edit loop measured in minutes can.
- [A4] **Estimate of swap latency in QEMU on Windows.** No primary measurement exists for this setup.
  - Tier 0: the cost of draining a run queue under a lock. Microseconds natively, more under TCG.
  - Tier 1: hardware precedents are PROTEOS's 272 ms median update [E77] and MINIX's 0.48 s NIC recovery [E68]. Assuming TCG slows kernel-heavy code by roughly 5-20x (assumed, not verified), expect about 0.3-3 s per process swap before probation.
  - Tier 3: Theseus's load stage took 19.5-179.6 ms on a bare-metal NUC [E27, E28]. Under TCG, expect hundreds of milliseconds to seconds.

  In every tier the probation window, not the swap itself, dominates the time a user waits.
- [A5] **Estimate of milestone effort** (the L0-L5 table in the Recommendation). Assumptions:
  - It uses the foundation memo's assumptions: a solo founder new to kernels, 30-35 focused hours per person-week, ranges of roughly ±50%.
  - The foundation milestones each L-step depends on are already done.
  - State transfer is written by hand, with no generated transfer functions.
  - For scale: Theseus's loader, relinker and swap code in `mod_mgmt/src/lib.rs`, `crate_metadata/src/lib.rs` and `crate_swap/src/lib.rs` total 5,774 lines at `1fbfe56` (3,241 + 1,430 + 1,103, counted in this session) [E39, E41, E43]. A minimal tier-3 loader with one namespace, about six relocation types and no TLS is estimated at 2,500-4,000 lines.
- [A6] **Analysis: why tiers 0 and 1 suffice for the POC.** The POC must show the LLM changing scheduling and memory policy on synthetic workloads. A ring-3 policy agent (tier 1) can hold arbitrary logic, written by the LLM or the founder, and can be replaced and rolled back the PROTEOS way. It drives native hot-path policies through bounded parameter blocks (tier 0). This needs no in-kernel code loading at all. It also sidesteps the Rust ABI: the agent is an ELF built by any compiler, and it talks to the kernel through syscalls and versioned bytes. Tier 2 is worth building only if the LLM must express per-decision logic that parameters cannot capture. Writing the tier-2 export contract in WIT on paper costs nothing and keeps a later move to components open [E106].
- [A7] **Analysis of discrepancies between the Theseus sources.** These matter only if Theseus code is adapted.
  - The OSDI paper says stage (iii) updates on-stack references [E18], but the `crate_swap` code at `1fbfe56` disclaims correctness and does no stack scanning [E39]. Stack fix-up appears only in the fault-recovery path [E42].
  - The paper says `state_db` serializes itself so that it can be swapped [E16], but `state_store` at `1fbfe56` contains a panic placeholder [E47]. I did not find serialization code.
  - Liyanage's thesis text calls the ITC cell swap "about 5.5 µs", which conflicts with its own Table 5.2 [E37]. The table figure is the one used here.
- [A8] **Analysis: Theseus's recovery rate does not transfer.** The 69% recovery rate [E31] comes from hardware-fault injection into SAS/SPL safe-Rust code. Kernel AI's ring-3 components get process-level restart instead, which is the MINIX approach [E68]. Its ring-0 code aborts on panic by default [E61]. Do not quote 69% as an expected figure for Kernel AI.

## Open questions

1. **Will the in-terminal compiler emit Wasm, its own bytecode or native x86_64?** This decides whether tier 2 and the REPL share one sandbox runtime or whether Kernel AI needs two. Resolve it together with [compiler-in-terminal.md](./compiler-in-terminal.md), before L5.
2. **Does `wasmi` 2.0.0 build and run on `x86_64-unknown-none` without changes (for example, does it need its `libm` feature)?** This decides whether tier 2 is a few days or a few weeks of work. Resolve it with a throwaway `no_std` test kernel that instantiates one module under QEMU TCG and measures per-call cost with fuel on and off.
3. **How long does a tier-1 process swap take under TCG, and under WHPX?** This sets the probation-window floor and the UI expectations. Measure L2's demo swap (the policy agent under a synthetic load) in both modes, using the foundation memo's icount setup for repeatability.
4. **How large are `line-tables-only` DWARF sections for the Kernel AI image?** This decides whether line tables ship inside the image or load from the virtio-blk disk. Measure at M1 with `llvm-readelf`/`llvm-objdump` section sizes.
5. **What health checks and probation window should gate a commit?** Candidates are deadline-miss rate, runnable-task stall time, reclaim failures and fuel exhaustion. Without good gates, auto-rollback either never fires or fires on noise. Resolve with A/B runs of the synthetic workloads in the deterministic icount mode, injecting known-bad policies.
6. **How should quiescence be detected for tier 3 on SMP?** The options are reference counts plus an entry barrier, stack scanning (which needs reliable unwind info, as livepatch does [E89]), or Theseus-style unwinding to a safe point [E24]. Decide before any tier-3 work. Watch the Theseus `theseus_main` branch for any revival of live evolution.
7. **Does `-C panic=unwind` with `-Zbuild-std` work on the built-in `x86_64-unknown-none` target, or is a custom target JSON (nightly-only since 1.95 [E62]) required?** This matters only if kernel-side unwinding recovery is wanted (decision 8). Resolve with a small build experiment on the pinned nightly.
8. **Does `elf_loader` 0.17.0 need `libc` or a user-supplied mapping backend in ring 0?** Its default `full` feature may pull in `libc` (unverified). This decides whether to use it or write a loader on `object`/`goblin` [E123-E125]. Read its `Cargo.toml` and memory module before tier 3.
9. **Should the POC enable QEMU's emulated IOMMU for any ring-3 driver demo?** Without an IOMMU, a ring-3 driver's DMA is unconfined [E88]. Whether QEMU's `intel-iommu` device works with TCG and WHPX on a Windows host is unverified. Test it in the foundation memo's spike if decision 2 changes.
10. **Can QEMU VM snapshots (`-loadvm` [E121]) serve as a development-time "undo everything", and what disk format and Windows-host support do they need?** Snapshots would give the founder a safety net beyond in-OS rollback during early work. Test `savevm`/`loadvm` on the founder's Windows 11 QEMU build.
11. **What sync mechanism carries in-VM edits back to the host repo?** The candidates are virtio-net to a small host service, a shared virtio-blk image, or a serial channel. This decides L3's design and its Windows-host support. Prototype the simplest option (an HTTP push over the virtio-net and smoltcp stack from foundation M5) and confirm it works under WHPX and TCG.
12. **Is the v0-mangling crate disambiguator stable across rebuilds of an unchanged crate with the pinned toolchain?** Tier-3 relinking by symbol name depends on this. Rebuild twice from a clean tree and diff the symbol tables.
