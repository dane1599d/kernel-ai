# LLM in a from-scratch OS: network client, in-OS inference, and where AI pays off

- **Date:** 2026-10-14
- **Status:** Research memo (no code)
- **Scope:** How the Kernel AI guest, running in QEMU on Windows 11, reaches an OpenAI-compatible LLM server on the Mac mini M4; whether a 0.5-3B model can run inside the OS instead; and, for each POC feature, where the LLM earns its latency and where deterministic rules win.
- **Related memos:** [rust-kernel-foundation.md](./rust-kernel-foundation.md), [compiler-in-terminal.md](./compiler-in-terminal.md), [live-editable-system.md](./live-editable-system.md), [templeos-components.md](./templeos-components.md)

## Conclusions

1. **The network path that works on Windows 11 without admin rights or extra drivers is QEMU `-machine q35` with `virtio-net-pci` on `-netdev user` (slirp). The guest opens TCP straight to the Mac mini's LAN address.** slirp routes guest packets out through the host unless `restrict=on` is set, so no `hostfwd` rule is needed for outbound calls [E2]. The guest uses the slirp defaults 10.0.2.15, gateway 10.0.2.2 and DNS 10.0.2.3 [E1]. The MSYS2 build of QEMU 11.1.2 links libslirp [E4]. `q35` is required because the chosen virtio crate only speaks PCIe ECAM, which QEMU exposes on x86 only for `q35` [E8, E19]. TAP needs a third-party driver installed as Administrator, and Windows itself must do the bridging [E5, E6]. passt does not run on Windows at all [E7].

2. **The kernel side is mostly integration work. rcore's `virtio-drivers` 0.13 feeding `smoltcp` 0.14 is a working template.** The crate's own x86_64 example already boots on `q35` with `virtio-net-pci`, user networking, `smoltcp` 0.14 and the static address 10.0.2.15 [E21]. We change three things. We replace its hard-coded `rdtsc / 2500` clock with the calibrated monotonic millisecond clock that `phy::Device` requires [E15, E21]. We drop the `-cpu host -accel kvm` default, which cannot work on Windows [E21]. We implement the `Hal` trait over our own frame allocator [E20]. `smoltcp` lacks SACK and TCP timestamps [E13], which does not matter at LLM data rates. Its maintainer has started a rewrite called xarxa, which embassy-net's main branch already uses [E17], so keep the adapter between virtio and the network stack thin.

3. **Write a small blocking HTTP/1.1 client from `httparse`, a chunked-body decoder and an SSE line parser, driven by one polled network task. Do not adopt the async embassy stack for the POC.** llama-server streams Server-Sent Events over chunked transfer encoding and ends with `data: [DONE]` [E43]. Every HTTP/1.1 client must be able to decode chunked bodies [E24]. `httparse` parses headers and chunk sizes in `no_std` without allocating [E23]. `reqwless` 0.14 is a real `no_std` alternative, but it pulls in `embedded-io-async` and `embedded-nal-async` and needs an executor platform and a global time driver [E18, E26]. It also has no SSE parser [E26]. The SSE parser must skip comment lines, because llama-server sends keep-alive pings every 30 s by default [E25, E43].

4. **Parse JSON with `serde_json` (`default-features = false`, `alloc`) and not with `serde-json-core`.** `serde_json` works in `no_std` once a global allocator exists [E34]. `serde-json-core` has no dynamic `Value` type. Unless the caller supplies an unescape buffer, it hands strings back still escaped. It also rejects any `😀`-style surrogate pair [E29, E30, E31]. `mlx_lm.server` escapes every non-ASCII character with Python's default `json.dumps`, so one emoji in a reply breaks `serde-json-core` [E32]. llama-server writes raw UTF-8 and never splits a character across events, so `serde-json-core` would work against llama-server only [E33]. Tying the parser to one server's encoding habits is the reason not to use it.

5. **Keep TLS out of the kernel. On the home LAN, use plain HTTP with llama-server's `--api-key`. If encryption is required, run `ssh -L` on the Windows host and point the guest at 10.0.2.2.** TLS in the kernel is possible but not worth it for the POC. `reqwless` 0.14 with `embedded-tls` (its `rustpki` feature) can verify a server chain against one pinned CA through `TlsVerify::Certificate`. It passes no clock, though, so certificate expiry is never checked [E26]. `rustls` in `no_std` offers only its unbuffered API, needs a non-default crypto provider and needs a `TimeProvider` [E36]. slirp rewrites guest connections to 10.0.2.2 onto the host's loopback interface [E3]. Windows ships an OpenSSH client as an optional feature [E11]. A tunnel therefore costs about an hour of setup instead of weeks of in-kernel cryptography.

6. **Run llama-server on the Mac mini. Of the three candidate servers, it alone accepts an arbitrary grammar, and it gives the guest built-in latency telemetry.** It accepts GBNF `grammar`, `json_schema` and `response_format` on `/v1/chat/completions` [E40]. It has a public `/health` endpoint that returns 503 while loading [E39], a `timings` object in every response [E38], prompt caching on by default [E42], and per-request control over thinking [E44]. `mlx_lm.server` offers no constrained decoding, speaks HTTP/1.0 and ends a stream by closing the connection [E46, E47]. Ollama offers JSON schemas only, defaults to a 4,096-token context and unloads the model after 5 minutes [E49, E50, E51]. Start llama-server with `--host 0.0.0.0`, because the default is 127.0.0.1. Its default port is now 9931, not 8080 [E39].

7. **Latency from inside the VM is set by the Mac, not by the VM. The Mac prefills at about 220-240 tok/s and decodes at about 20-24 tok/s; the guest and the network add an estimated 2-15 ms per request.** Those speeds were measured on a base M4 for 7-8B 4-bit models [E55, E57]. They match the bandwidth ceiling of 120 GB/s divided by a 5.0 GB Qwen3-8B Q4_K_M file [E54, E59]. A streamed answer uses about 4-6 KB/s of bandwidth (Estimates). Four design rules follow. Keep a stable prompt prefix so `cache_prompt` reuses it [E42]. Ask for short, constrained outputs. Stream everything. Turn thinking off, because Qwen3 thinks by default and every thinking token costs about 50 ms [E44, E59].

8. **Off-the-shelf crates cannot do in-OS inference: candle cannot build for `no_std`, and Burn's only `no_std` backend has no GGUF loader, no k-quants and no threads.** `candle-core` has no `std` feature and depends unconditionally on `memmap2`, `rayon`, `num_cpus`, `libc`, `zip` and `parking_lot`. Its GGUF reader is written against `std::io` [E60, E61, E62]. Burn 0.22.0 says only the Flex backend runs in `no_std`. Flex's parallelism comes from `rayon`, Burn's 4-bit formats are its own, and Burn imports ONNX and Safetensors but not GGUF [E63, E64, E65]. `mistral.rs`, `tract` and the archived `rustformers/llm` are std-only or dead [E68]. A from-scratch engine is feasible: a llama2.c-style forward pass [E69], `gguf-rs-lib` for metadata [E70], and candle's MIT/Apache AVX2 kernels ported by hand [E62]. The GGUF file already carries the tokenizer and chat template [E73].

9. **Under QEMU TCG, in-OS generation from a 0.5-3B model cannot be interactive. Expect roughly 1-5 tok/s at 0.5B, well under 1 tok/s at 3B, and minutes of prefill (estimates).** TCG runs the key int8 dot-product instructions (`PMADDUBSW`, `PMADDWD`) and FMA as out-of-line C helpers [E77]. Every guest load goes through the software MMU [E79]. AVX-512 and AVX-VNNI do not exist under TCG [E76]. The default `qemu64` CPU model lacks even AVX, so AVX2 code needs `-cpu max` [E78]. TCG remains fine for correctness tests with 260K-15M-parameter toy models [E69].

10. **Under WHPX, a hand-written AVX2 engine could plausibly run a 0.5-0.6B model at tens of tok/s and a 1.5B model at about 15-30 tok/s (estimates). That is no faster than the remote 8B and much weaker, so do not build in-OS generation for the POC.** Under WHPX the guest runs directly on the CPU [E83]. Batch-1 decode is limited by memory bandwidth [E88]. Native llama.cpp reaches about 56-60 GiB/s of effective bandwidth on desktop x86 [E86, E87]. Under WHPX, any SIMD-enabled code must keep MMIO accessors scalar [E84]. The only case for in-OS generation is offline operation without the Mac. That is a founder decision, not a POC need.

11. **Route intents in three tiers: deterministic rules first, a tiny local classifier second, and the remote LLM last. Never use a generative in-OS model as the router.** A fastText-style linear classifier matches deep classifiers on many text tasks at a tiny fraction of the cost, and it can be compressed about 100x [E101, E102]. BERT-Tiny has 4.4M parameters and works best when distilled from a larger teacher [E103]; here the remote 8B can be that teacher. In-kernel learned models of this size decide in 4-21 µs [E105, E107]. Gemma 3 270M is built for fine-tuned classification [E96], but under TCG it would take seconds per query (estimate), and the Gemma terms carry use restrictions that we must pass on to our users.

12. **For each feature, the LLM pays off where it turns intent into a structured artifact or explains something. Rules win wherever the answer must be fast, exact or authoritative.**

| Feature | Where the LLM pays off | Where rules win | LLM latency (estimate) | Required guard |
|---|---|---|---|---|
| REPL | Turning a natural-language request into one command or a short script; explaining output on request | Parsing, tab completion, history, help lookup, known verbs (router tier 1); anything per keystroke | 0.3-2.6 s for a command, about 16 s for a 300-token script | Grammar or schema at decode time, local re-parse, show, confirm, run [E40, E114] |
| Compiler in the terminal | Drafting code from a description; explaining diagnostics in plain words [E116]; proposing one fix | Lexer, parser, type checker, code generation, accepting or rejecting code | 9-17 s | The compiler decides acceptance. Allow at most one or two repair rounds (see [compiler-in-terminal.md](./compiler-in-terminal.md)) |
| Live editing | Explaining a component's source; drafting a patch; summarising a diff; suggesting a rollback | Build, interface and version checks, tests, health checks, apply, automatic rollback on fault or stall [E111] | about 30 s for a patch to a 2,000-token component | The LLM is never the only rollback trigger |
| Scheduler and memory tuning | Inferring the workload's goal from a metrics summary; choosing a pre-verified policy; setting bounded parameters; explaining results [E109] | Every hot-path decision; tiny integer models if any; bounds checks; A/B measurement; revert [E105, E107, E111] | about 5 s per decision, at most every 30 s | Stage, measure, commit or revert, with a watchdog [E110, E112] |
| System control by prompt | Mapping a fuzzy request to one structured command validated by a JSON schema | Permission checks, confirming destructive actions, frequent intents served locally, multi-step plans [E115] | 1-3 s | One confirmed step at a time |

13. **For scheduler and memory tuning, the LLM selects among pre-verified policies and fills a bounded parameter schema, every few tens of seconds or less often. It never writes hot-path code in the POC.** SchedCP's best results came from selecting and configuring existing schedulers [E109]. In the same paper, a frontier agent asked to write a scheduler from scratch needed 33 minutes and $6 for one success, and the result sometimes ran slower than EEVDF [E110]. AutoOS found that directly prompting an LLM for kernel tuning gave "nearly no performance improvement" [E113]. KEN's verified natural-language-to-eBPF pipeline was right 80% of the time [E114]. sched_ext restores the default scheduler on error or stall, and the Guardrails proposal compiles declared properties into in-kernel monitors [E111, E112]. The 8B emits one token every 50 ms, while learned hot-path policies decide in microseconds [E105, E107]. AIOS is not prior art for this design: its "kernel" is agent middleware running above a normal OS [E117].

14. **Choose Apache-2.0 or MIT models, both for the Mac server and for anything shipped in the OS image, so that "possibly commercial later" stays open.** Qwen3-8B and the small Qwen3 models are Apache-2.0 [E59, E93]. SmolLM2, Qwen2.5-0.5B and -1.5B are Apache-2.0, and Phi-4-mini is MIT [E90, E91, E95, E97]. Qwen2.5-3B is research-only [E92]. Llama 3.2 needs "Built with Llama" attribution and a separate licence above 700M monthly users [E94]. Gemma requires passing its use restrictions on to users and lets Google restrict use remotely [E96]. LFM2.5 has a US$10M revenue threshold [E100].

### Recommendation

Build the LLM path as a ring-3 control-plane service that talks plain HTTP/1.1 to llama-server. Build no in-OS generative inference for the POC.

1. **Mac mini.** Run llama-server pinned to one build (b11624 or later) [E45] with Qwen3-8B Q4_K_M (Apache-2.0, 5.0 GB) [E59] or the 8B model the founder already uses. Start it with `--host 0.0.0.0`, an explicit `--port`, an `--api-key`, and thinking off by default (`--reasoning off`, or `chat_template_kwargs` with `enable_thinking: false` per request) [E39, E44]. Lower `--cache-ram` from its 8,192 MiB default so the 16 GB machine does not swap [E42]. Whether two slots fit in memory is unverified (Open question 6). If they do, pin interactive prompts and control-plane prompts to separate slots with `id_slot`, so their cached prefixes do not evict each other [E42].
2. **QEMU on Windows.** Use `-machine q35 -device virtio-net-pci,netdev=n0 -netdev user,id=n0` [E1, E8, E21]. Use `-cpu max` under TCG so that AVX2, SMEP and SMAP are visible [E76, E78]. TCG stays the reference platform and WHPX an optional fast mode, as [rust-kernel-foundation.md](./rust-kernel-foundation.md) recommends. Under WHPX, watch for the open virtio-net hang [E9].
3. **Kernel.** Use `virtio-drivers` `VirtIONet` with `alloc` and our own `Hal` [E20], wrapped in a `smoltcp` 0.14 `phy::Device`. Build `smoltcp` with `default-features = false` plus `alloc`, `medium-ethernet`, `proto-ipv4` and `socket-tcp` [E14, E21]. Give it a static address of 10.0.2.15/24 via 10.0.2.2 [E1, E21]. A polled network task runs first; MSI-X comes later. The kernel exposes a minimal TCP socket syscall interface.
4. **Ring-3 `llmd` service.** It owns the HTTP/1.1 client (`httparse`, a chunked-body decoder, an SSE parser), `serde_json` structs for OpenAI request and stream chunks, request timeouts and cancellation, a boot-time `GET /health` probe, and a telemetry log that compares guest wall time with the server's `timings` [E23, E24, E25, E34, E38, E39]. It disables Nagle and sends each request in one write [E16]. It keeps prompt templates with stable prefixes and a library of grammars and JSON schemas. It treats every model output as untrusted input and re-validates it before acting. During bring-up the client can run as a kernel task. Move it to ring 3 once system calls exist, so that untrusted network and model bytes are never parsed in ring 0 (analysis).
5. **Router in the shell (ring 3).** Tier 1 is a rule and grammar table for known verbs. Tier 2, added after the core loop works, is an int8 hashed-n-gram linear classifier trained on the host from utterances the 8B labels or generates [E101, E102, E103]. Tier 3 sends everything else to `llmd`.
6. **Control-plane policy agent (ring 3).** Every 30 s or more, it summarises metrics, asks llama-server for a `json_schema`-constrained choice from the policy registry with bounded parameters, and hands that choice to the kernel. The kernel stages it, measures it against the incumbent policy and commits or reverts, with a sched_ext-style watchdog fallback [E109, E111, E112]. This matches the policy hook in [rust-kernel-foundation.md](./rust-kernel-foundation.md).
7. **Deferred.** In-OS generation (WHPX only, Qwen3-0.6B or SmolLM2, own engine) is revisited only if offline operation becomes a requirement.

| Step | Deliverable | Depends on | Effort (estimate) |
|---|---|---|---|
| L1 | The guest prints `GET /health` and the RTT to the Mac from the framebuffer terminal | M5 of [rust-kernel-foundation.md](./rust-kernel-foundation.md) (PCI over ECAM, `Hal`, virtio-net plus `smoltcp`) | 2-4 days |
| L2 | Streaming chat in the terminal: POST, chunked decoding, SSE, `serde_json`, timeouts, cancel, guest-side timing against server `timings` | L1 | 4-6 days |
| L3 | Client moved into a ring-3 `llmd` with socket system calls and a request queue | Ring 3 and system calls (memo 1) | 1-2 weeks |
| L4 | Constrained outputs (JSON schema for commands, GBNF for script), show, confirm, run; router tier 1 | L3; the script host from [compiler-in-terminal.md](./compiler-in-terminal.md) | 1-2 weeks |
| L5 | Control-plane policy agent: metrics summary, policy registry, bounded schema, stage, A/B, commit or revert | L4; scheduler and reclaim hooks (memo 1, M6) | 2-3 weeks |
| L6 | Router tier 2: training pipeline on the host and an int8 classifier in the OS | L4 | 1-2 weeks |

### Not possible / not viable

- **passt cannot be the network backend on the Windows 11 host.** passt runs only on Linux; its portability table lists Windows only as "nice-to-have, eventually" [E7].
- **The guest cannot ping the Mac mini through slirp.** QEMU says ICMP generally does not work with user-mode networking, and the ping-socket workaround exists only on Linux hosts [E1]. Check reachability with a TCP connect or `GET /health`.
- **QEMU TAP networking on Windows cannot run without a third-party driver installed with admin rights, and QEMU cannot bridge it.** The TAP-Windows driver is not shipped with QEMU. The Windows tap backend reads only `ifname=` [E5, E6].
- **The rcore `virtio-drivers` x86_64 example cannot run unmodified on Windows.** Its Makefile adds `-cpu host -accel kvm` by default, and KVM does not exist on Windows [E21].
- **`reqwless` plus `embedded-tls` cannot check certificate expiry in `no_std`.** It can verify a chain against a pinned CA (`TlsVerify::Certificate`, `rustpki` feature), but it supplies no clock, and RSA chains need the extra `rsa` and `alloc` features — [reqwless 0.14.0 `TlsVerify`](https://docs.rs/reqwless/0.14.0/reqwless/client/enum.TlsVerify.html) (docs.rs, 0.14.0 released 2026-01-12; accessed 2026-10-14). The README sentence saying verification is unsupported is out of date [E26].
- **`serde-json-core` cannot deserialize untyped JSON or unescape surrogate pairs.** It has no `Value` type, `deserialize_any` returns `AnyIsUnsupported`, and each `\uXXXX` is decoded alone with `char::from_u32` [E29, E30, E31]. Against `mlx_lm.server`, any streamed emoji fails to parse [E32].
- **Arbitrary grammar-constrained generation cannot be done through `mlx_lm.server` or Ollama.** `mlx_lm.server` has no constraint fields, and Ollama accepts only JSON or a JSON schema [E47, E50]. Only llama-server accepts GBNF [E40].
- **The LLM cannot sit on the scheduler or reclaim hot path, and it cannot drive per-keystroke completion.** One generated token takes about 41-50 ms on the M4 [E55, E57]. Learned hot-path policies decide in 4-21 µs [E105, E107]. The LLM is at least 10^3 to 10^4 times too slow per decision.
- **candle and mistral.rs cannot run in `no_std`.** Both depend unconditionally on std-only crates (`memmap2`, `rayon`, `libc`; `tokio` and `reqwest` for mistral.rs) [E60, E61, E68]. Their kernels and GGUF logic can be read and ported; the crates cannot be used.
- **No Burn backend except Flex works in `no_std`, and Flex has no threads there.** Flex's parallelism comes only from `rayon`, which needs `std::thread`. Burn also has no GGUF importer and no GGUF k-quant formats [E61, E63, E64, E65].
- **Under QEMU TCG the guest cannot use AVX-512 or AVX-VNNI, and under the default `qemu64` CPU it cannot use AVX2 at all.** TCG's CPUID masks list AVX2 but not AVX512F, and `qemu64` advertises only SSE3 and CX16 in leaf 1 ECX [E76, E78].
- **Under WHPX the kernel cannot use MMX, SSE or AVX instructions to touch MMIO.** QEMU's instruction emulator cannot decode them on MMIO exits [E84].
- **Interactive in-OS generation from a 1.5B or 3B model under TCG is not viable.** This rests on estimates (0.2-1.6 tok/s), not on a measurement (see Estimates and analysis, D) [E77, E79].
- **Qwen2.5-3B-Instruct cannot be used commercially without a separate licence from Alibaba Cloud.** It is under the Qwen Research License [E92].

### Decisions the founder must make

| # | Decision | Options | Recommended default |
|---|---|---|---|

| 2 | Remote model | Qwen3-8B (Apache-2.0); a Llama 3.x 8B (custom licence); the current model | **Qwen3-8B Q4_K_M with thinking off**, unless the current model is clearly better on our prompts [E44, E59] |

| 12 | Offline requirement | The Mac is always present; the OS must work without it | **The Mac is always present for the POC.** If offline is required, budget the deferred WHPX engine |

## Evidence

### Network path from the QEMU guest to the Mac mini

- [E1] In QEMU user-mode networking the guest is 10.0.2.15, the gateway and host alias is 10.0.2.2, DNS is 10.0.2.3 and SMB is 10.0.2.4. "ICMP traffic in general does not work with user mode networking"; ping to 10.0.2.2 works, and Internet ping relies on unprivileged ping sockets that exist only on Linux hosts. — [QEMU network emulation docs](https://www.qemu.org/docs/master/system/devices/net.html) (QEMU 11.1.50 docs, undated; accessed 2026-10-14)
- [E2] With `restrict=on` "the guest will be isolated ... no guest IP packets will be routed over the host to the outside". The default is off, so guest-initiated TCP reaches any address the Windows host can reach. `hostfwd` takes an optional host bind address. `guestfwd` with a TCP chardev opens one host connection at startup (doc example), which suits repeated HTTP requests poorly (inference from the example). — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html) (undated; accessed 2026-10-14)
- [E3] libslirp rewrites guest connections addressed to the virtual host (10.0.2.2) to the host's loopback address unless host loopback is disabled. The latest libslirp releases are v4.9.5 (2026-09-22) and v4.9.4 (2026-08-25). — [libslirp src/socket.c](https://gitlab.freedesktop.org/slirp/libslirp/-/raw/master/src/socket.c) (master, undated; accessed 2026-10-14); [libslirp releases API](https://gitlab.freedesktop.org/api/v4/projects/slirp%2Flibslirp/releases?per_page=2) (2026-09-22)
- [E4] The latest QEMU release is 11.1.2 (2026-09-28). Windows binaries come from Stefan Weil or from MSYS2. The MSYS2 UCRT64 package `mingw-w64-ucrt-x86_64-qemu` 11.1.2-1 was built on 2026-09-29 and depends on `mingw-w64-ucrt-x86_64-libslirp`. — [QEMU download page](https://www.qemu.org/download/) (2026-09-28); [MSYS2 qemu package](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-qemu) (2026-09-29)
- [E5] TAP-Win32 "is not included in standard QEMU for Windows, so you will need to get it separately". QEMU's Windows tap backend fails without `ifname=` and reads no `script`, `br` or `helper` option. — [QEMU network emulation docs](https://www.qemu.org/docs/master/system/devices/net.html) (undated; accessed 2026-10-14); [QEMU net/tap-win32.c](https://raw.githubusercontent.com/qemu/qemu/master/net/tap-win32.c) (master, undated; accessed 2026-10-14)
- [E6] The TAP-Windows6 NDIS 6 driver (hardware ID TAP0901) is installed from an Administrator shell with `tapinstall`. — [OpenVPN tap-windows6 README](https://github.com/OpenVPN/tap-windows6) (undated; accessed 2026-10-14)
- [E7] passt supports Linux 4.18 and later. FreeBSD, Darwin, NetBSD, OpenBSD and "Win2k" are marked "nice-to-have, eventually". QEMU's docs say "passt has better performance than -net user, full IPv6 support and better security". — [passt about page](https://passt.top/passt/about/) (undated; accessed 2026-10-14); [QEMU network emulation docs](https://www.qemu.org/docs/master/system/devices/net.html) (undated; accessed 2026-10-14)
- [E8] "The PCIe features are available only when using the 'q35' machine type on x86 architecture." — [QEMU docs/pcie.txt](https://raw.githubusercontent.com/qemu/qemu/master/docs/pcie.txt) (master, undated; accessed 2026-10-14)
- [E9] QEMU issue #4492, "virtio-net-pci hangs on sustained network download" (opened 2026-09-17, last updated 2026-10-11, QEMU 11.1.1 built with MSYS2 UCRT64 on Windows 11, `-accel whpx`, `-nic user,model=virtio-net-pci`). The networking hangs when a download of 400 MiB or more follows a few small downloads. It does not hang with `model=e1000`. The reporter says the download "usually should take just over 5 seconds" on a 1 Gb/s connection, which implies slirp can move several hundred Mb/s under WHPX when it works. — [QEMU issue 4492 (GitLab API)](https://gitlab.com/api/v4/projects/qemu-project%2Fqemu/issues/4492) (2026-09-17, updated 2026-10-11)

### HTTP, SSE, JSON and TLS in `no_std`

- [E23] `httparse` 1.10.1 (2025-03-03, MIT OR Apache-2.0) is "A push parser for the HTTP 1.x protocol. Avoids allocations. No copy. Fast. Works with no_std, simply disable the std Cargo feature." - [E24] "A recipient MUST be able to parse and decode the chunked transfer coding." Each chunk is a hexadecimal size, CRLF, data and CRLF, ending with a zero-size last chunk. — [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html) (2022-06)
- [E25] An SSE stream is `text/event-stream` and "must always be encoded as UTF-8". Lines starting with a colon are comments and are ignored. `data` lines accumulate, and a blank line dispatches the event. — [WHATWG HTML: Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html) (living standard, undated; accessed 2026-10-14)
- [E26] `reqwless` 0.14.0 (2026-01-12, Apache-2.0) is a `no_std`, no-alloc HTTP client over `embedded-io` transports. - [E28] `sse-core` 0.2.3 (2026-07-31; crate created 2026-05-01) is "A high-performance, zero-I/O, no_std compatible state-machine parser for Server-Sent Events". It is young. — [crates.io API: sse-core](https://crates.io/api/v1/crates/sse-core) (2026-07-31)
- [E29] `serde-json-core` 0.7.0 was published on 2026-10-08 (changelog date 2026-10-07) with MSRV 1.87.0 under MIT OR Apache-2.0. "(De)serialization doesn't require memory allocations." - [E30] Without an unescape buffer, `serde-json-core` hands strings to the visitor still escaped ("If the unescape buffer is not provided, skip unescaping strings"). `deserialize_any` returns `Error::AnyIsUnsupported`. - [E31] `serde-json-core` decodes each `\u` escape as exactly four hex digits passed to `char::from_u32`, returning `InvalidEscapeSequence` on failure. A lone surrogate half is not a valid `char`, so every surrogate pair fails (verified in source this session). RFC 8259 requires characters outside the Basic Multilingual Plane to be escaped as a 12-character UTF-16 surrogate pair. — [serde-json-core src/str.rs](https://raw.githubusercontent.com/rust-embedded-community/serde-json-core/master/src/str.rs) (master, undated; accessed 2026-10-14); [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) (2017-12)

### GGUF and 4-bit formats

- [E73] GGUF is designed for "Single-file deployment" and `mmap` compatibility. The file starts with the magic `GGUF` and version `3`, and alignment is 32 when unspecified. Metadata embeds the tokenizer (`tokenizer.ggml.tokens`, merges) and `tokenizer.chat_template`. — [ggml docs/gguf.md](https://raw.githubusercontent.com/ggml-org/ggml/master/docs/gguf.md) (2026-07-09)
- [E74] A Q4_0 block holds 32 weights as one fp16 scale plus 16 bytes of nibbles (4.5 bits per weight). A Q4_K super-block holds 256 weights with 6-bit sub-block scales and mins, "Effectively 4.5 bits per weight". Q6_K is 6.5625 bits per weight. Q4_K_M mixes Q4_K with higher-bit tensors. — [llama.cpp ggml/src/ggml-common.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-common.h) (master, undated; accessed 2026-10-14)

### QEMU TCG and WHPX for compute-heavy guest code

- [E75] QEMU 7.2 added "TCG support for AVX, AVX2, F16C, FMA3, and VAES instructions". — [QEMU 7.2.0 release announcement](https://www.qemu.org/2022/12/14/qemu-7-2-0/) (2022-12-14)
- [E76] In QEMU v11.1.0, `TCG_7_0_EBX_FEATURES` includes SMEP, SMAP, BMI1/2, ADX and AVX2 but not AVX512F, and `TCG_7_1_EAX_FEATURES` contains only FZRM, FSRS, FSRC and CMPCCXADD (verified this session). The 11.1.0 tarball is dated 2026-08-11 and 11.1.2 is dated 2026-09-29. — [QEMU target/i386/cpu.c at v11.1.0](https://raw.githubusercontent.com/qemu/qemu/v11.1.0/target/i386/cpu.c) (2026-08-11); [download.qemu.org](https://download.qemu.org/) (2026-09-29)
- [E77] TCG translates simple vector integer ops (PADD, PAND and similar) inline through gvec. `PMADDUBSW` and `PMADDWD` call helpers (`helper_pmaddubsw`, `helper_pmaddwd`) that loop over lanes in C, and FMA goes through `float32_muladd` softfloat helpers. — [QEMU target/i386/ops_sse.h at v11.1.0](https://raw.githubusercontent.com/qemu/qemu/v11.1.0/target/i386/ops_sse.h) (2026-08-11); [QEMU target/i386/tcg/emit.c.inc](https://raw.githubusercontent.com/qemu/qemu/master/target/i386/tcg/emit.c.inc) (master, undated; accessed 2026-10-14)
- [E78] The `qemu64` CPU model sets only `CPUID_EXT_SSE3 | CPUID_EXT_CX16` in leaf 1 ECX, so it has no SSSE3, SSE4 or AVX. The `max` model "Enables all features supported by the accelerator in the current host". — [QEMU target/i386/cpu.c](https://raw.githubusercontent.com/qemu/qemu/master/target/i386/cpu.c) (master, undated; accessed 2026-10-14)
- [E79] "For system emulation QEMU uses a software MMU. In that mode, the MMU virtual to physical address translation is done at every memory access", sped up by a TLB cache. — [QEMU docs/devel/tcg.rst](https://raw.githubusercontent.com/qemu/qemu/master/docs/devel/tcg.rst) (master, undated; accessed 2026-10-14)
- [E80] With multi-threaded TCG, "each vCPU will run on its own user-space thread". It is enabled by default wherever the host memory model can accommodate the guest's, and x86 sets `mttcg_supported = true`. — [QEMU docs/devel/multi-thread-tcg.rst](https://raw.githubusercontent.com/qemu/qemu/master/docs/devel/multi-thread-tcg.rst) (master, undated; accessed 2026-10-14)
- [E81] (secondary) A QEMU 5.1 GSoC study counted about 20 host instructions per guest instruction on x86_64 double-precision benchmarks (`matmult_double` 1:20.33) and about 6.5-12 on integer ones (`matmult_int32` 1:6.498). These are linux-user instruction-count ratios measured before TCG had AVX2. — [Measuring QEMU Emulation Efficiency](https://ahmedkrmn.github.io/TCG-Continuous-Benchmarking/Measuring-QEMU-Emulation-Efficiency/) (2020-08-03, secondary)
- [E82] A DATE 2015 paper found QEMU's software helper functions to be a major cause of slow SIMD emulation. Mapping guest SIMD to host SIMD made Linpack run 11.5x faster. — [Fu, Wu, Hsu: Improving SIMD Code Generation in QEMU (DATE 2015)](https://past.date-conference.com/proceedings-archive/2015/pdf/0356.pdf) (2015-03)
- [E83] `WHvRunVirtualProcessor` "runs the virtual processor (that is, it runs guest code)" and blocks until the guest performs an operation that the virtualization stack must handle (an exit). — [Microsoft Learn: Windows Hypervisor Platform API](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/hypervisor-platform) (2021-06-07, updated 2026-06-11)
- [E84] QEMU 11.0 (2026-04-21): "WHPX now uses improved and faster emulation code" and supports x2APIC and vAPIC. QEMU 11.1's WHPX docs say x86_64 is tested from Windows 10 version 2004. Known issue: the emulator "does not support guests that use MMX, SSE or AVX instructions for access to MMIO memory ranges". — [QEMU ChangeLog/11.0](https://wiki.qemu.org/index.php?title=ChangeLog/11.0&action=raw) (2026-04-21); [QEMU docs/system/whpx.rst at v11.1.0](https://raw.githubusercontent.com/qemu/qemu/v11.1.0/docs/system/whpx.rst) (2026-08-11)
- [E85] "By default, Rust code generated for this target does not use any vector or floating-point registers (e.g. SSE, AVX)." Code that uses them must have the kernel save and restore those registers. — [rustc book: x86_64-unknown-none](https://raw.githubusercontent.com/rust-lang/rust/master/src/doc/rustc/src/platform-support/x86_64-unknown-none.md) (master, undated; accessed 2026-10-14)

### Prior art: ML and LLMs in OS control

- [E105] LinnOS runs a light neural network on every I/O in the kernel. It "improves the average I/O latencies by 9.6-79.6% with 87-97% inference accuracy and 4-6μs inference overhead for each I/O". — [Hao et al., LinnOS (OSDI '20)](https://www.usenix.org/conference/osdi20/presentation/hao) (2020-11)
- [E106] LinnOS's network has three layers (31 inputs, 256 hidden neurons, 2 outputs). It is trained offline, and its weights are converted to integers "Because using floating points is not well supported in OS kernel". — [LinnOS paper PDF](https://www.usenix.org/system/files/osdi20-hao.pdf) (2020-11)
- [E107] KML uses under 4 KB of kernel memory and under 0.2% CPU and improves I/O throughput by up to 2.3x (readahead) and 15x (NFS rsize). Neural-network inference takes 21 µs and decision-tree inference 8 µs, run once per second on an asynchronous thread with `kernel_fpu_begin`/`end`. — [Akgun et al., KML (arXiv 2111.11554v2)](https://arxiv.org/pdf/2111.11554v2) (2022-01-26)
- [E108] LAKE found that "the benefits of ML and acceleration for OSes is subsystem-, workload- and hardware-dependent". CPU inference for its I/O latency predictor took about 15 µs. — [Fingler et al., LAKE (ASPLOS '23)](https://par.nsf.gov/servlets/purl/10405160) (2023-03-25)
- [E109] SchedCP keeps the LLM in a decoupled control plane: the AI decides "what to optimize" and the system decides "how to observe and act". Its authors argue that ML models in the scheduler hot path "would cause unacceptable inference latency". It reports up to 1.79x over EEVDF on kernel compilation by first selecting `scx_rusty` and then `scx_layered`, and 2.11x better P99 latency on schbench. — [Zheng et al., Towards Agentic OS (arXiv 2509.01245)](https://arxiv.org/abs/2509.01245) (v4 2025-09-30)
- [E110] In SchedCP's baseline, a frontier agent asked to write a FIFO scheduler succeeded once in three attempts. The success took "33 minutes, 221 LLM API calls, and 15+ iterations, costing $6", sometimes performed worse than EEVDF, and had no fallback. SchedCP's safety pipeline is the eBPF verifier, scheduler-specific static analysis, dynamic tests in a micro-VM, and a monitored canary deployment. — [SchedCP paper PDF](https://arxiv.org/pdf/2509.01245) (2025-09-30)
- [E111] sched_ext: "The system integrity is maintained no matter what the BPF scheduler does. The default scheduling behavior is restored anytime an error is detected, a runnable task stalls, or on invoking the SysRq key sequence SysRq-S." — [Linux Documentation/scheduler/sched-ext.rst](https://raw.githubusercontent.com/torvalds/linux/master/Documentation/scheduler/sched-ext.rst) (master, undated; accessed 2026-10-14)
- [E112] "Guardrails for the OS" (HotOS '25) names unsafe decisions, opaque debugging and kernel latency limits as barriers to learned policies. It proposes declared properties with corrective actions, compiled "into monitors capable of running within the kernel". Only the abstract was available. — [Saxena et al., HotOS '25 (NSF PAR record)](https://par.nsf.gov/biblio/10594522) (2025-05-14)
- [E113] AutoOS: "directly prompting the state-of-the-art LLM (i.e., ChatGPT)" for kernel configuration yielded only 10-20 generic options and "nearly no performance improvement". A structured observe-prune-propose-act-correct loop reached up to 25% over vendor configurations. — [Chen et al., AutoOS (ICML 2024, PMLR 235)](https://raw.githubusercontent.com/mlresearch/v235/main/assets/chen24at/chen24at.pdf) (2024-07-21)

### Estimates and analysis

Everything in this subsection is my own analysis. Each item states its assumptions. Nothing here was measured on the founder's hardware.

**A. Remote generation rates.** Assume Qwen3-8B Q4_K_M at 5.03 GB [E59]. Batch-1 decode reads roughly every weight once per token [E88], so 120 GB/s ÷ 5.03 GB gives a ceiling of about 24 tok/s [E54]. Measured 7-8B 4-bit models run at 22.6-24.1 tok/s [E55, E57], and the founder reports about 20. The budgets below use **20 tok/s decode**. They assume **about 225 tok/s prefill** for a cold prompt: 221-240 tok/s measured at pp512 [E55, E57], trimmed about 5% for 8.2B parameters. Prefill slows as KV depth grows; `llama-bench -d` measures this [E53]. A short new suffix after a cached prefix runs less efficiently per token, so it is budgeted at 0.1-0.3 s. Grammar sampling may slow decode further. [compiler-in-terminal.md](./compiler-in-terminal.md) cites a benchmark where it doubled time per token on server hardware. That has not been measured on the M4.

**B. Network and guest term.** Assumptions: a wired gigabit LAN; slirp NAT inside QEMU on Windows; a guest under TCG; HTTP/1.1 keep-alive to llama-server. All values are unmeasured estimates.

| Component | Estimate |
|---|---|
| LAN round trip, wired gigabit | 0.2-1 ms |
| LAN round trip, Wi-Fi | 2-10 ms |
| slirp and QEMU event loop, per packet | 0.1-1 ms |
| Guest `smoltcp`, HTTP and JSON work per SSE event under TCG | 0.1-2 ms |
| New TCP connection (no keep-alive; always the case with `mlx_lm.server`) | +1 round trip |
| **Total added per request** | **about 2-15 ms** |
| Streamed bandwidth: 20 events/s × about 200-300 bytes per event | about 4-6 KB/s |

Every budget below lasts at least 0.2 s, so this term is under 1-5% of the shortest interaction and under 0.1% of the longer ones. The only slirp throughput data points are a 2012 anecdote of about 10 Mb/s [E10] and the reporter's statement in [E9] (several hundred Mb/s under WHPX). Either one is two to five orders of magnitude above 5 KB/s. Delayed ACK (10 ms) only matters if the guest dribbles a request out in small writes. Disabling Nagle and sending the request in one write removes the issue [E16].

**C. Latency budget for the remote 8B.** Assumptions: thinking off, `cache_prompt` on and the prefix warm unless stated, 225 tok/s prefill, 20 tok/s decode, network term from B.

| Interaction | Prompt tokens (new / cached) | Output tokens | Time to first token | Total |
|---|---|---|---|---|
| Intent fallback, cold cache | 340 / 0 | 1-8 | about 1.5 s | about 1.6-1.9 s |
| Intent fallback, warm cache | 40 / 300 | 1-8 | about 0.15-0.3 s | about 0.2-0.7 s |
| System command as schema-checked JSON | 100 / 400 | about 40 | about 0.3-0.6 s | about 2.3-2.6 s |
| Explain a compiler diagnostic | 300 / 500 | about 150 | about 1.4 s | about 9 s (text visible from 1.4 s) |
| Generate a REPL script | 300 / 1,200 | about 300 | about 1.4 s | about 16-17 s |
| Draft a patch to a 2,000-token component | 2,300 / 600 | about 400 | about 10-11 s | about 30-31 s |
| Policy choice from a metrics summary | 400 / 600 | about 60 | about 1.8 s | about 4.8 s |
| Any of the above with Qwen3 thinking left on | same | +200-1,000 thinking tokens | +10-50 s | +10-50 s |
| Model reloaded after idle unload (Ollama `keep_alive`, llama-server sleep) | — | — | + several seconds (unmeasured) | same |

The design rules from Conclusion 7 follow from this table. The only interactions under a second are the cached, tiny-output ones. Anything that generates code or prose takes 10-30 s, so the UI must stream and must never block the shell.

**D. In-OS decode speed (tokens per second, batch 1, 4 vCPUs).** Assumptions:
- Bytes read per token equal the Q4_K_M file size [E90-E95].
- Native llama.cpp-class effective bandwidth is about 58 GiB/s (about 62 GB/s) on a desktop dual-channel DDR5 machine [E86, E87]. The founder's CPU is unknown.
- WHPX passes AVX2 through, and its guest memory runs near native speed [E83].
- Four threads reach about 70% of the bandwidth plateau, taken from the 4-thread versus 8-thread rows of [E86].
- A hand-written Rust engine reaches 40-80% of llama.cpp's efficiency. The gap between mature engines is already 15-40% [E87].
- WHPX therefore reaches 28-56% of the native ceiling.
- Under TCG, decode becomes compute-bound. Native single-thread int8 throughput is about 83 GOP/s, from 6.17 t/s × 2 × 6.74B in [E86]. Helper-based SIMD [E77, E82] and softmmu loads [E79] slow it 50-200x, giving 0.4-1.7 GOP/s per vCPU. Four vCPUs under MTTCG [E80] give about 3x that, so 1.2-5 GOP/s. Each token costs about 2 × parameters operations.

| Model (Q4_K_M size) | Native ceiling | WHPX, own AVX2 engine | TCG `-cpu max`, MTTCG |
|---|---|---|---|
| Qwen3-0.6B (397 MB) | about 155 | about 45-85 | about 1-4 |
| Qwen2.5-0.5B (491 MB) | about 125 | about 35-70 | about 1-5 |
| Qwen2.5-1.5B, Qwen3-1.7B, SmolLM2-1.7B (1,056-1,117 MB) | about 55 | about 15-30 | about 0.4-1.6 |
| Llama-3.2-3B (2,019 MB) | about 31 | about 9-17 | about 0.2-0.8 |
| Remote Qwen3-8B on the M4 (reference) | measured 22.6-24.1 for 7-8B [E55, E57] | n/a | n/a |

Prefill under WHPX is compute-bound. Assume native 16-thread 8B Q4_0 pp512 of 153.5 t/s [E87], scaled by a quarter for 4 vCPUs and by 30-60% for engine quality. That gives roughly 180-440 tok/s at 0.5B, 60-140 at 1.5B and 30-70 at 3B. A 300-token prompt therefore takes about 0.7-1.7 s at 0.5B and 4-10 s at 3B. Under TCG the same 300-token prompt at 0.5B takes about 1-4 minutes (300 × 1 GOP at 1.2-5 GOP/s). A scalar build without SIMD would be several times slower on both accelerators. Verdict: under WHPX a 0.5-0.6B model is usable and a 1.5B model is usable, but neither beats the remote 8B on speed and both lose clearly on quality. Under TCG, generation works only as a non-interactive demo at 0.5B.

**E. Engine effort if in-OS generation is ever built.** Assumptions: the kernel already has ring 3, a heap and SMP. The XSAVE/FPU context-switch support that [E85] requires takes about 1 week. A llama2.c-style forward pass for a Qwen or Llama GQA architecture [E69], GGUF parsing via `gguf-rs-lib` [E70], Q4_K and Q8 dequantization and dot products ported from candle [E62, E74], a BPE tokenizer using `regex` without `std` [E72], and a 4-thread work split take 4-8 weeks for a first-time kernel author. Hybrid architectures (Qwen3.5 DeltaNet, LFM2.5 convolutions, Gemma 4 Per-Layer Embeddings) add weeks each [E98, E99, E100], so the first target should be a plain GQA transformer: Qwen3-0.6B, Qwen2.5-0.5B or SmolLM2.

**F. Intent-router costs.** Parameter counts come from the sources; the latencies are estimates. The TCG column assumes the 1.2-5 GOP/s of D for SIMD code and about 0.1-0.6 GFLOP/s for scalar floating point.

| Tier | Size | Per query, native or WHPX | Per query, TCG | Training data |
|---|---|---|---|---|
| Rules: grammar, keyword and verb table | kilobytes | under 10 µs | under 1 ms | none |
| Hashed n-gram linear classifier, int8 (fastText-style) [E101, E102] | about 0.1-2 MB | about 10-50 µs | about 0.1-2 ms | 50-200 utterances per intent, labelled or generated by the 8B |
| BERT-Tiny encoder, int8 [E103] | about 4.4 MB | about 1-5 ms (about 13 MFLOP for 16 tokens) | about 20-150 ms | hundreds to thousands of examples, distilled |
| Gemma 3 270M, scoring only the label tokens [E96] | about 250 MB at Q4 | about 30-150 ms (about 3.2 GFLOP for 16 tokens) | about 0.6-3 s | off-box fine-tuning |
| Remote Llama-3.2-3B on the Mac [E57] | 1.9 GB on the Mac | about 0.1-0.3 s warm, 0.7-0.8 s cold | same | prompt only |
| Remote 8B (C above) | 5.0 GB on the Mac | about 0.2-0.7 s warm, 1.6-1.9 s cold | same | prompt only |

Floating-point inference in a ring-0 context would need explicit FPU state handling, as KML does [E107], or integer weights, as LinnOS uses [E106]. Running the router in the ring-3 shell, whose vector state the kernel already saves, avoids both.

**G. Where the hot-path gap comes from.** One token from the remote 8B costs about 41-50 ms [E55, E57]. Learned hot-path policies cost 4-21 µs [E105, E107]. A JSON policy decision of about 60 tokens plus prefill costs about 5 s (table C). The LLM therefore acts on workload phases that last tens of seconds or longer. That is why the policy agent's cadence is set at 30 s or more, and why every LLM choice is staged and measured before it is committed.

**H. Ring placement of the client.** Analysis, not sourced. Bytes from the network and text from the model are untrusted input. Parsing HTTP, SSE and JSON in ring 0 puts parsers of hostile input in the same address space as `unsafe` DMA code, and turns any parser bug into a kernel crash. In ring 3 the service can also be restarted and live-edited without touching the kernel, which fits [live-editable-system.md](./live-editable-system.md). The kernel keeps only the driver, the TCP/IP stack and a socket system call interface.

## Open questions

1. **What are the real guest-to-Mac round trip and per-request overhead through slirp under TCG, and under WHPX, on the founder's machine?** They confirm or replace the 2-15 ms estimate in B and set the timeouts. Resolve it at L1: time a TCP connect plus `GET /health` 100 times from the guest, compare with `curl` from the Windows host, and log guest wall time against llama-server `timings` [E38, E39].
2. **Does QEMU issue #4492 (virtio-net hang under WHPX with slirp) affect long LLM streams?** The trigger was a bulk download, while LLM streams run at a few KB/s [E9]. `virtio-drivers` has no e1000 driver to fall back on [E19]. Resolve it with a 30-minute loop of streamed completions under WHPX at L2, and watch the issue for a fix.
3. **Is the Windows PC wired or on Wi-Fi to the Mac mini, and does Windows Defender Firewall or the macOS firewall interfere?** This changes the network term several-fold and can block llama-server's listening port (firewall behaviour unverified). Resolve it by recording the setup in the developer notes and testing from Windows first with `curl http://<mac>:<port>/health`.
4. **What are the real prefill and decode rates for the chosen 8B on this Mac mini, with and without a grammar?** The whole latency budget rests on them. Resolve it with `llama-bench -p 1500 -n 300 -pg 1500,300 -d 0,2048` [E53], then the same prompts through llama-server with and without `grammar` and `json_schema`, reading `timings` [E38, E40].
5. **Is MLX meaningfully faster than llama.cpp on a base M4 for 8B 4-bit models?** No primary absolute M4 number exists; Apple publishes only M5-versus-M4 ratios [E58]. This matters only if the founder would give up GBNF. Resolve it with `mlx_lm.benchmark -p 1500 -g 300` [E48] against the llama-bench run in question 4.
6. **How much memory headroom does the 16 GB Mac have for the 8B, a second slot, an optional 3B router and the prompt cache?** The default `--cache-ram` alone is 8 GiB [E42], and the weights are 5.0 GB [E59]. How much RAM macOS lets the GPU wire down is unverified. Resolve it by watching memory pressure in Activity Monitor during the question 4 runs, at `--cache-ram` 2048 and 4096.
7. **Does WHPX on the founder's machine expose AVX2 and XSAVE to the guest, and what are the host CPU and memory configuration?** These decide whether the WHPX estimates in D apply at all, and they shift them about 2x. Resolve it during the spike in [rust-kernel-foundation.md](./rust-kernel-foundation.md) by printing CPUID leaves 1 and 7 and XCR0 under TCG `-cpu max` and under WHPX.
8. **What is the real TCG slowdown of our own AVX2 Q4 dot-product loop in system mode?** It replaces the 50-200x assumption in D. Resolve it at the milestone where SSE and AVX are enabled: time a fixed dot-product microbenchmark under TCG, WHPX and natively on Windows.
9. **Must Kernel AI work without the Mac mini?** If not, in-OS generation can be dropped permanently. If so, budget the deferred WHPX engine (E in the estimates). This is a founder decision.
10. **Which intents must work locally, without the remote LLM?** For example: help, run, open the source of component X, reload, roll back. The answer sets the router's label set and how much training data it needs. Resolve it by listing the POC shell verbs before L4.
11. **Should the LLM ever emit new policy code, or only choose and parameterise pre-verified policies?** The evidence favours the second for the POC [E109, E110, E113, E114]. Revisit after L5 shows whether selection alone moves the synthetic workload metrics.
12. **How does the guest learn the Mac's address: a config file, slirp DNS, or a DHCP reservation?** Whether slirp DNS resolves `.local` mDNS names, and whether slirp forwards multicast for `smoltcp` mDNS, are both unverified. Resolve it by testing a DNS query to 10.0.2.3 for the Mac's `.local` name. Until then, use a static address in a boot config file.
13. **Will `smoltcp` keep receiving maintenance after embassy-net moves to xarxa?** This matters if the kernel later wants async networking or a maintained stack [E17]. Watch the smoltcp and xarxa repositories and the next embassy-net release.
14. **Should virtio-net be polled or interrupt-driven (MSI-X) in the POC?** Polling is simpler. Its latency and CPU cost under TCG are unmeasured. Resolve it at L2 by comparing time to first byte and guest CPU use with both.
15. **If Ollama is ever used instead, does its native NDJSON stream use HTTP chunked encoding?** Only the content type was verified [E50]. Resolve it with `curl -v` against `/api/chat` if the server decision changes.
