# LLM in a from-scratch OS: remote client, routing and where AI pays off

**Date:** 2026-10-14

Merged from two independent research passes (local and cloud).

- **Project:** Kernel AI
- **Scope:** how the Kernel AI guest, running in QEMU, reaches an OpenAI-compatible LLM server on the Mac mini M4 (16 GB); what in-OS inference would take (post-POC); how to route intents; and where the LLM earns its latency per feature. Milestones M0-M10 are defined in [rust-kernel-foundation.md](./rust-kernel-foundation.md).
- **Related memos:** [compiler-in-terminal.md](./compiler-in-terminal.md), [live-editable-system.md](./live-editable-system.md), [templeos-components.md](./templeos-components.md)
- "Estimate" means derived from bandwidth or FLOP arithmetic, not measured. "Unverified" means no primary source confirmed it.

## Conclusions

1. **Remote inference is the POC path (founder decision). The LLM stays in the control plane, never in scheduling or reclaim.** Measured Mac mini M4 numbers (both passes, different sources, kept side by side):
   - llama.cpp, Llama 2 7B Q4_0: 221 tokens/s prefill, 24.1 decode. A Mac mini M4 (24 GB) on llama.cpp: Qwen2.5-coder 7B Q4_K_M 239.7 / 22.6; Llama 3.2 3B Q4_K_M 530.0 / 45.95 (a user comment, secondary).
   - oMLX: Llama 3.2 3B 4-bit 478 / 48.4 at 1k context (2.1 s time to first token); Llama 3.1 8B 4-bit 234 / 22.8 (4.4 s, 4.9 GB peak).
   - Bandwidth ceiling: 120 GB/s divided by a 5.03 GB Qwen3-8B Q4_K_M file is about 24 tokens/s. The budgets below use 20 tokens/s decode (the founder's own figure) and about 225 tokens/s cold prefill. One token costs 41-50 ms.

2. **The network path: QEMU `-machine q35` with `virtio-net-pci` on `-netdev user` (slirp).** The guest opens TCP straight to the Mac mini's LAN address with no admin rights, no TAP driver and no `hostfwd` for outbound calls. Slirp defaults: guest 10.0.2.15, gateway and host alias 10.0.2.2, DNS 10.0.2.3. `q35` is required because `virtio-drivers` speaks only PCIe ECAM. TAP needs a third-party driver, and passt does not run on Windows. Test reachability with a TCP connect or `GET /health`.
   - Disputed: ICMP. Local: ping fails. Cloud: QEMU says ICMP "in general does not work"; ping to 10.0.2.2 works; Internet ping needs unprivileged ping sockets that exist only on Linux hosts. Resolution: both agree TCP is the test. With QEMU in WSL2 (a Linux host) ping may work depending on `net.ipv4.ping_group_range`; do not rely on it.
   - **WSL2 caveat (cross-memo consistency finding).** Both passes assumed QEMU runs as a native Windows process, so 10.0.2.2 reaches the Windows host, guest traffic arrives from the Windows host's IP, and the relay, `ssh -L` tunnel and an optional RTX endpoint live on Windows. The founder's verified loop is KVM inside WSL2. There, 10.0.2.2 reaches WSL2's loopback, outbound traffic leaves through WSL2's network (which fell back from NAT to "VirtioProxy" on this machine), and a Mac-side firewall rule must admit whatever source address WSL2 presents. Host-side services (build service, tunnel, optional GPU endpoint) should run in WSL2 or be reached through WSL2's host address. Validate at M0 and M6.

3. **The kernel side is integration work.** `virtio-drivers` 0.13 `VirtIONet` (needs `alloc`) feeding `smoltcp` 0.14 is a working template: the crate's own x86_64 example boots on q35 with `virtio-net-pci`, user networking, `smoltcp` 0.14 and static address 10.0.2.15. We change two things: replace its hard-coded `rdtsc / 2500` clock with the calibrated monotonic millisecond clock that `phy::Device` requires, and implement `Hal` over our frame allocator. Its default `-cpu host -accel kvm` works under KVM in WSL2 (the cloud pass thought it "cannot work on Windows"; that holds only for native-Windows QEMU). The adapter is 100-200 lines. `smoltcp` lacks SACK, timestamps and PMTU discovery, which does not matter at LLM data rates. Its maintainer started a rewrite (xarxa) that embassy-net's main branch already uses, so keep the adapter thin. Hermit, ArceOS, Redox and Asterinas already run smoltcp or a derivative.

4. **Disputed: first transport.** Local: a serial bridge (guest UART, QEMU socket chardev, 50-100 line host relay) gets prompts flowing in days, then swap in virtio-net. Cloud: go straight to virtio-net, because the reference example nearly works (2-4 days to print `GET /health` and RTT). Resolution: no serial bridge milestone. The founder order puts the network at M6 and the AI shell at M8, so a bridge does not unblock anything. Build the HTTP/chunked/SSE/OpenAI-type crate now as a host-tested `no_std` plus `alloc` crate (about 400-700 lines with tests, estimate), and develop the terminal against a mock stream. Add a bridge only if M6 slips.

5. **HTTP: a small blocking client on `httparse`, a chunked decoder and an SSE line parser, driven by one polled network task.** llama-server streams SSE over chunked encoding and ends with `data: [DONE]`. The SSE parser must skip comment lines, because llama-server pings every 30 s by default. `reqwless` 0.14 is `no_std` but async (needs an executor and time driver) and has no SSE parser. `edge-http` is async. `sse-core` 0.2.3 is young. `picoserve` is a server, useful later for a control endpoint. Disable Nagle and send each request in one write. Esc closes the socket; whether the server stops generating then depends on the server (verify).

6. **JSON: `serde_json` with `default-features = false` and `alloc`.** `serde-json-core` has no `Value`, returns strings still escaped unless given a buffer, and rejects every surrogate pair. `mlx_lm.server` escapes all non-ASCII (Python `ensure_ascii`), so one emoji breaks it. llama-server writes raw UTF-8. `miniserde` cannot model tagged shapes.

7. **TLS stays out of the kernel.** Plain HTTP with llama-server's `--api-key` on the private LAN; if encryption is required, run an `ssh -L` tunnel on the host side of slirp. `reqwless` with `embedded-tls` can verify a chain against one pinned CA (`TlsVerify::Certificate`, `rustpki`) but passes no clock, so expiry is never checked (its README's "verification is not supported" is out of date). `rustls` in `no_std` offers only the unbuffered API and needs a non-default crypto provider and a `TimeProvider`. Under TLS-free design the realistic threat is another LAN device sniffing prompts or injecting scripts; mitigate with the API key and a firewall rule.

8. **Server: llama-server on the Mac mini.** It alone accepts raw GBNF `grammar`, `json_schema` and `response_format` on `/v1/chat/completions`; it has a public `/health` (503 while loading), a `timings` object in every response, prompt caching on by default and per-request control of thinking. Start it with `--host 0.0.0.0`, an explicit `--port` (the default is now 9931: read in `common.h` at release b11624 by the cloud pass and re-checked on `master` on 2026-10-14), `--api-key`, thinking off, and a lower `--cache-ram` than its 8,192 MiB default so 16 GB does not swap. `mlx_lm.server` offers no constrained decoding, speaks HTTP/1.0 and ends streams by closing the connection. Ollama offers JSON schemas only, defaults to a 4,096-token context and unloads the model after 5 minutes.

9. **Latency from inside the VM is set by the Mac, not the VM.** Guest plus network add an estimated 2-15 ms per request. Rules: keep a stable prompt prefix so `cache_prompt` reuses it (a cold 1k-token prompt costs 2.1-4.4 s to first token, a cached one 0.1-0.4 s); ask for short constrained outputs; stream everything; turn Qwen3 thinking off (every thinking token costs about 50 ms).

10. **Run the LLM client in ring 3 (`llmd`) once syscalls exist.** Local and cloud agree on a kernel task during bring-up. The cloud pass adds that untrusted network and model bytes should not be parsed in ring 0, and a ring-3 client can be restarted and live-edited. Resolution: kernel task at M6 (the M6 exit test needs it), ring-3 `llmd` with socket syscalls from M7.

11. **In-OS inference is out of the POC (founder decision: remote only).** Post-POC facts:
    - No off-the-shelf crate works: `candle-core` has no `std` feature and unconditionally needs `memmap2`, `rayon`, `libc`; Burn's only `no_std` backend (Flex) has no threads without `rayon`, no GGUF and its own 4-bit formats; `mistral.rs`, `tract` and `rustformers/llm` are std-only or dead. The best reference is NightRun (Rust, UEFI, hand-written AVX2 kernels, MIT): about 20 tokens/s on Llama 3.2 1B Q8_0 and about 11 on Qwen3 4B Q4_K_M in an 8-core QEMU/KVM guest, at parity with llama.cpp decode. A from-scratch engine is 3k-6k lines (local) or 4-8 weeks for a first-time kernel author (cloud).
    - The kernel stays soft-float (`x86_64-unknown-none` has no SSE or AVX; Rust is making `#[target_feature]` AVX on soft-float targets a hard error). Run inference as a ring-3 service on a hard-float target; the kernel must save XSAVE state.
    - Under TCG it is not interactive (about 1-5 tokens/s at 0.5B, minutes of prefill). Under KVM or WHPX, decode is bandwidth-bound. Estimates differ: local 30-65 tokens/s for Llama 3.2 1B in a VM, cloud 35-85 for a 0.5-0.6B and 15-30 for a 1.5B model. Neither beats the remote 8B on speed or quality. Revisit only if offline operation becomes a requirement.

12. **Route deterministically first.** Sigils (`?` forces the LLM, `!` forces literal), parser-first (does it parse as Rhai and do its identifiers resolve, or is the first word a known command), then heuristics. Add a tiny classifier (fastText-style hashed n-grams, int8, 0.1-2 MB, or Model2Vec) only if logs show misroutes, trained on logged data and labels from the remote 8B. Never use a generative model as the router and never spend an LLM call on routing. A small generative model (Gemma 3 270M, Qwen2.5-0.5B) is for offline natural-language-to-command only.

13. **The RTX 4070 Ti is out of reach from inside the OS.** QEMU has no PCI passthrough on Windows and WSL2 would still need an NVIDIA driver we would write. Its only use is a second network endpoint (CUDA llama.cpp on the host), reachable from a WSL2-hosted guest through WSL2's host address, not at 10.0.2.2.

14. **Per feature, the LLM pays off where it turns intent into a structured artifact or explains something. Rules win where the answer must be fast, exact or authoritative.** Anything with a deadline under about 100 ms is rules territory.

    | Feature | Where the LLM pays off | Where rules win | LLM latency (estimate) | Guard |
    |---|---|---|---|---|
    | Routing | Nothing (tiny classifier later) | Sigils, parser, command table | none | Never an LLM call |
    | REPL | Natural language to command or short script; explain output | Parsing, completion, history, known verbs, per-keystroke work | 0.3-2.6 s command, about 16 s for a 300-token script | Grammar or schema at decode, local re-parse, show, confirm, run |
    | Compiler diagnostics | Explain a diagnostic; propose one fix | Precise compiler diagnostics, quick-fixes for common errors | 9-17 s | The compiler decides acceptance; at most 2 repair rounds |
    | Live editing | Explain a component; draft a patch; summarize a diff | Build, version checks, tests, health checks, apply, auto-rollback | about 30 s for a patch to a 2,000-token component | LLM never the only rollback trigger |
    | Scheduler and memory tuning | Infer the workload goal from a metrics summary; choose a pre-verified policy; set bounded parameters; explain results | Every hot-path decision, bounds checks, A/B measurement, revert | about 5 s per decision, at most every 30 s | Stage, measure, commit or revert, watchdog |
    | System control | Map a fuzzy request to one structured command validated by JSON schema | Permission checks, confirming destructive actions, frequent intents | 1-3 s | One confirmed step at a time |
    | Completion as you type | Not in the POC | Symbol-table completion is instant and exact | n/a | n/a |

15. **For scheduler and memory tuning the LLM selects among pre-verified policies and fills a bounded parameter schema every few tens of seconds. It never writes hot-path code in the POC.** SchedCP's best results came from selecting and configuring existing schedulers; asked to write one from scratch a frontier agent needed 33 minutes and $6 for one success, sometimes slower than EEVDF. AutoOS found direct prompting gave "nearly no performance improvement". KEN's verified natural-language-to-eBPF pipeline was right 80% of the time. sched_ext restores the default on error or stall. Learned hot-path policies decide in 4-21 microseconds, so the LLM is at least 10^3 to 10^4 times too slow per decision. AIOS is not prior art here: its "kernel" is agent middleware above a normal OS.

16. **Choose Apache-2.0 or MIT models** for the Mac server and anything shipped in the OS image: Qwen3-8B and small Qwen3 (Apache-2.0), SmolLM2, Qwen2.5-0.5B and -1.5B (Apache-2.0), Phi-4-mini (MIT). Qwen2.5-3B is research-only; Llama 3.2 needs attribution and a separate licence above 700M monthly users; Gemma lets Google restrict use remotely; LFM2.5 has a US$10M revenue threshold. (The local pass listed Qwen2.5-0.5B and 1.5B as "believed Apache-2.0"; the cloud pass confirmed it.)

## Decisions

| Decision | Status | Default or choice |
|---|---|---|
| LLM placement | Decided (founder) | Remote only (Mac mini M4, 16 GB); in-OS inference out of the POC; control plane only |
| LLM server on the Mac mini | Open | llama-server pinned to one build (b11624 or later) |
| Remote model | Open | Qwen3-8B Q4_K_M, thinking off, unless the founder's current 8B is clearly better on our prompts |
| First transport | Open | virtio-net plus smoltcp at M6; no serial-bridge milestone |
| QEMU network backend | Open | slirp (`-netdev user`) on `q35`; revalidate under WSL2 |
| Encryption on the LAN | Open | Plain HTTP plus API key; SSH tunnel if required; no TLS in the kernel |
| Where the HTTP/JSON client lives | Open | Kernel task at M6, ring-3 `llmd` from M7 |
| Sync or async networking | Open | Blocking client on a polled network task |
| JSON crate | Open | `serde_json` (`alloc`) |
| Virtio-net interrupts | Open | Polling first, MSI-X later |
| Router tiers | Open | Rules and sigils; classifier only if logs show misroutes |
| LLM authority over scheduling and memory | Open | Select and parameterize pre-verified policies; no generated policy code in the POC |
| Model licence policy | Open | Apache-2.0 or MIT only |
| Offline behaviour | Open | Mac assumed present; commands and scripts never depend on the LLM; health check every 5-10 s behind a circuit breaker, status indicator |
| Prompt and cache policy | Open | Fixed system prompt first, variable context last, `cache_prompt` on, slot pinning only if memory allows |

Superseded by founder decision: in-OS inference engine and model-size tables for the POC (kept as post-POC notes), Windows-host tunnel and relay locations (revalidate for WSL2), "Mac always present" as an open founder question.

## Evidence

### 1. Network path from the QEMU guest to the Mac mini

- Slirp: guest 10.0.2.15, gateway and host alias 10.0.2.2, DNS 10.0.2.3, SMB 10.0.2.4; "ICMP traffic in general does not work"; inbound blocked without `hostfwd`. https://www.qemu.org/docs/master/system/devices/net.html. `restrict=on` isolates the guest; default off, so outbound TCP reaches anything the host can reach; `guestfwd` with a TCP chardev opens one host connection at startup. https://www.qemu.org/docs/master/system/invocation.html
- libslirp rewrites connections to 10.0.2.2 onto the host's loopback unless disabled; v4.9.5 (2026-09-22). https://gitlab.freedesktop.org/slirp/libslirp/-/raw/master/src/socket.c and https://gitlab.freedesktop.org/api/v4/projects/slirp%2Flibslirp/releases?per_page=2
- TAP-Win32 is not shipped with QEMU for Windows and the Windows tap backend reads only `ifname=`. https://raw.githubusercontent.com/qemu/qemu/master/net/tap-win32.c. TAP-Windows6 installs from an Administrator shell. https://github.com/OpenVPN/tap-windows6
- passt supports Linux 4.18+; Windows is "nice-to-have, eventually"; QEMU says passt "has better performance than -net user". https://passt.top/passt/about/
- PCIe features exist on x86 only for `q35`. https://raw.githubusercontent.com/qemu/qemu/master/docs/pcie.txt
- QEMU issue 4492, virtio-net-pci hangs on sustained download under WHPX with `-nic user` (opened 2026-09-17; not hit with `model=e1000`; implies slirp moves several hundred Mb/s when it works). https://gitlab.com/api/v4/projects/qemu-project%2Fqemu/issues/4492. `virtio-drivers` has no e1000 driver to fall back on.
- Slirp throughput: the only figures are a 2012 anecdote of about 10 Mb/s (low confidence, pre-libslirp) and the report above; both are far above 5 KB/s. https://docs.zephyrproject.org/latest/services/connectivity/networking/qemu_user_setup.html and https://lkml.iu.edu/hypermail/linux/kernel/1210.2/03810.html
- Servers bind 127.0.0.1 by default (llama.cpp `--host`, Ollama `OLLAMA_HOST`); smoltcp's DNS client has no mDNS, so `macmini.local` will not resolve (whether slirp forwards `.local` is unverified). Give the Mac a DHCP reservation and put its IP in boot config.

### 2. Guest network stack

- `smoltcp` 0.14.0 (published 2026-08-17, 0BSD, MSRV 1.91): redesigned congestion control (Reno, CUBIC), TCP segmentation offload; 0.13.0 (2026-03-20) moved to Edition 2024. https://crates.io/api/v1/crates/smoltcp and https://raw.githubusercontent.com/smoltcp-rs/smoltcp/main/CHANGELOG.md
- "smoltcp does not need heap allocation at all"; MSS and window scaling, Nagle, delayed ACK, keep-alive; no SACK, timestamps or PMTU discovery. https://raw.githubusercontent.com/smoltcp-rs/smoltcp/main/README.md. Features: `socket-tcp`, `socket-udp`, `socket-dhcpv4`, `socket-dns`, `proto-ipv4`; use `default-features = false`; the README's "alloc needs nightly" is stale (stable since 1.36). https://raw.githubusercontent.com/smoltcp-rs/smoltcp/main/Cargo.toml and https://blog.rust-lang.org/2019/07/04/Rust-1.36.0/
- `phy::Device` has `receive`, `transmit`, `capabilities`; timestamps are monotonic milliseconds. https://docs.rs/smoltcp/0.14.0/smoltcp/phy/trait.Device.html. TCP buffers are caller-provided; ACK delay is 10 ms; disabling Nagle equals TCP_NODELAY. https://docs.rs/smoltcp/0.14.0/smoltcp/socket/tcp/struct.Socket.html. Supply a seed for initial sequence numbers (RDRAND or TSC jitter). Poll from the timer tick or the virtio interrupt and keep the interval at 5 ms or less, since it adds to per-token latency.
- xarxa is a rewrite by smoltcp's maintainer (crates.io name reserved 2026-07-27); embassy-net 0.9.1 depends on smoltcp 0.13, its main branch uses xarxa. https://raw.githubusercontent.com/embassy-rs/xarxa/main/README.md, https://crates.io/api/v1/crates/xarxa, https://crates.io/api/v1/crates/embassy-net/0.9.1/dependencies and https://raw.githubusercontent.com/embassy-rs/embassy/main/embassy-net/README.md. embassy-executor and embassy-time need exactly one platform implementation and one time driver. https://raw.githubusercontent.com/embassy-rs/embassy/main/embassy-executor/README.md and https://raw.githubusercontent.com/embassy-rs/embassy/main/embassy-time/README.md
- `virtio-drivers` 0.13.0: `VirtIONet` needs `alloc`, `VirtIONetRaw` does not; `Hal` has `dma_alloc` ("allocates and zeroes the given number of contiguous physical pages"), `dma_dealloc`, `mmio_phys_to_virt`, `share`, `unshare`; PCI config goes through `ConfigurationAccess` (`MmioCam` built in). https://raw.githubusercontent.com/rcore-os/virtio-drivers/master/README.md, https://docs.rs/virtio-drivers/0.13.0/virtio_drivers/device/net/index.html, https://docs.rs/virtio-drivers/0.13.0/virtio_drivers/trait.Hal.html and https://docs.rs/virtio-drivers/0.13.0/virtio_drivers/transport/pci/bus/index.html
- Its x86_64 example depends on `smoltcp` 0.14.0 (`alloc`, `medium-ethernet`, `proto-ipv4`, `socket-tcp`), runs `-machine q35 -device virtio-net-pci -netdev user,hostfwd=tcp::5555-:5555`, adds `-cpu host -accel kvm` by default, hard-codes 10.0.2.15 via 10.0.2.2 and a `_rdtsc() / 2_500` clock. https://raw.githubusercontent.com/rcore-os/virtio-drivers/master/examples/x86_64/Cargo.toml, https://raw.githubusercontent.com/rcore-os/virtio-drivers/master/examples/x86_64/Makefile and https://raw.githubusercontent.com/rcore-os/virtio-drivers/master/examples/x86_64/src/tcp.rs. A RISC-V example has a smoltcp `Device` wrapper and TCP echo server (local pass).
- Others: Hermit (MIT OR Apache-2.0) uses smoltcp 0.14 with its own virtio-net on `virtio-spec` 0.4. https://raw.githubusercontent.com/hermit-os/kernel/main/Cargo.toml. ArceOS `ax-net` 0.9.x. https://docs.rs/crate/ax-net/0.9.0. Redox's `smolnetd` is smoltcp-based. https://gitlab.redox-os.org/redox-os/redox/-/merge_requests/845. Asterinas `aster-bigtcp` is smoltcp-derived (unverified). https://github.com/asterinas/asterinas/tree/main/kernel/libs
- Effort for PCI enumeration, virtio-net, smoltcp and DHCP through a TCP connection to the Mac: 1-3 weeks for a first-time kernel developer (local estimate).

### 3. HTTP, SSE, JSON and TLS in `no_std`

- `httparse` 1.10.1 (2025-03-03): zero-copy HTTP/1.x push parser, `no_std` with `std` off, exports `parse_chunk_size` and `parse_headers`. https://raw.githubusercontent.com/seanmonstar/httparse/master/README.md and https://docs.rs/httparse/1.10.1/httparse/index.html
- Chunked coding: hex size, CRLF, data, CRLF, zero-size last chunk; every recipient must decode it. https://www.rfc-editor.org/rfc/rfc9112.html. SSE is `text/event-stream`, UTF-8; lines starting with a colon are comments; a blank line dispatches. https://html.spec.whatwg.org/multipage/server-sent-events.html. Four parser layers (socket bytes, transfer decoding, SSE framing, JSON per event) must each handle arbitrary split points. Ollama's native `/api/chat` streams NDJSON, another reason to use the OpenAI dialect.
- `reqwless` 0.14.0 (2026-01-12, Apache-2.0): `embedded-io-async ^0.7`, `embedded-nal-async ^0.9.0`, `httparse`, `heapless`, optional `embedded-tls ^0.18`; `BodyReader` has `Chunked`; no SSE. https://raw.githubusercontent.com/drogue-iot/reqwless/main/README.md, https://crates.io/api/v1/crates/reqwless/0.14.0/dependencies and https://docs.rs/reqwless/0.14.0/reqwless/response/enum.BodyReader.html. Pinned-CA verification without expiry check, RSA chains need `rsa` and `alloc`. https://docs.rs/reqwless/0.14.0/reqwless/client/enum.TlsVerify.html
- `edge-http` (edge-net 0.8.0, 2026-06-25): async, `no_std`, no alloc. https://raw.githubusercontent.com/sysgrok/edge-net/master/edge-http/README.md. `picoserve` 0.20.1 (2026-09-21): async `no_std` server. https://crates.io/crates/picoserve. `sse-core` 0.2.3 (2026-07-31). https://crates.io/api/v1/crates/sse-core
- `serde-json-core` 0.7.0 (2026-10-08): no allocation, no `Value`; strings stay escaped without an unescape buffer; `deserialize_any` returns `AnyIsUnsupported`; each `\u` escape goes through `char::from_u32`, so every surrogate pair fails (verified in source). https://raw.githubusercontent.com/rust-embedded-community/serde-json-core/master/CHANGELOG.md, https://docs.rs/serde-json-core/0.7.0/serde_json_core/index.html, https://raw.githubusercontent.com/rust-embedded-community/serde-json-core/master/src/de/mod.rs and https://raw.githubusercontent.com/rust-embedded-community/serde-json-core/master/src/str.rs. RFC 8259 requires non-BMP characters as 12-character UTF-16 pairs. https://www.rfc-editor.org/rfc/rfc8259.html. Python `json.dumps` defaults to `ensure_ascii=True` and `mlx_lm/server.py` writes `data: {json.dumps(resp)}`. https://docs.python.org/3/library/json.html and https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/server.py. llama-server uses `dump_safe` with `ensure_ascii` false and holds back an incomplete UTF-8 character. https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/json.cpp, https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-common.cpp and https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-context.cpp
- `serde_json` 1.0.154 (2026-10-11): works with `alloc` and without `std`. https://raw.githubusercontent.com/serde-rs/json/master/README.md, https://crates.io/api/v1/crates/serde_json and https://docs.rs/crate/serde_json/latest/features. `miniserde` 0.1.46 (2026-07-18) has no tuple structs or enums with data. https://raw.githubusercontent.com/dtolnay/miniserde/master/src/lib.rs
- `rustls` 0.23.46 (2026-10-14): `no_std` with `alloc`, unbuffered API, defaults include `aws_lc_rs` (C) and `std`. https://raw.githubusercontent.com/rustls/rustls/v/0.23.46/rustls/src/lib.rs. `embedded-tls` 0.19.0 (2026-06-01, Apache-2.0): TLS 1.3, no allocator, one frame at a time up to 16 KB. https://raw.githubusercontent.com/drogue-iot/embedded-tls/main/README.md

### 4. LLM servers on the Mac mini

- llama-server (release b11624, 2026-10-14): `/v1/chat/completions` sync and streaming with a `timings` object; `GET /health` is public; `--host` defaults to 127.0.0.1, `--port` to 9931 (`int32_t port = 9931` in `common.h`, verified by fetch); `--api-key`; `--sleep-idle-seconds` -1. https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md, https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.h and https://github.com/ggml-org/llama.cpp/releases

### 8. Prior art: ML and LLMs in OS control

- LinnOS: a light neural network on every I/O, 4-6 microseconds, integer weights "because using floating points is not well supported in OS kernel". https://www.usenix.org/conference/osdi20/presentation/hao and https://www.usenix.org/system/files/osdi20-hao.pdf
- KML: under 4 KB kernel memory, 21 microsecond NN and 8 microsecond decision-tree inference, run once per second on an async thread with `kernel_fpu_begin`/`end`. https://arxiv.org/pdf/2111.11554v2. LAKE: benefits are "subsystem-, workload- and hardware-dependent"; about 15 microseconds CPU inference. https://par.nsf.gov/servlets/purl/10405160
- SchedCP keeps the LLM in a decoupled control plane; up to 1.79x over EEVDF on kernel compilation and 2.11x better P99 on schbench by selecting `scx_rusty` then `scx_layered`; a frontier agent writing a FIFO scheduler succeeded once in three attempts (33 minutes, 221 API calls, $6). https://arxiv.org/abs/2509.01245 and https://arxiv.org/pdf/2509.01245
- sched_ext: "The system integrity is maintained no matter what the BPF scheduler does." https://raw.githubusercontent.com/torvalds/linux/master/Documentation/scheduler/sched-ext.rst. "Guardrails for the OS" (HotOS '25, abstract only). https://par.nsf.gov/biblio/10594522
- AutoOS: direct prompting gave "nearly no performance improvement"; a structured observe-prune-propose-act-correct loop reached up to 25%. https://raw.githubusercontent.com/mlresearch/v235/main/assets/chen24at/chen24at.pdf. KEN: 80% correct eBPF. https://arxiv.org/abs/2312.05531. BFCL: models excel at single-turn calls; memory and long-horizon reasoning are open. https://icml.cc/virtual/2025/poster/46593. LLM-enhanced error messages can beat the originals. https://arxiv.org/abs/2210.11630. AIOS is agent middleware above a normal OS. https://arxiv.org/pdf/2403.16971

### 9. Estimates and analysis

**Latency budget for the remote 8B** (thinking off, `cache_prompt` on and warm unless stated, 225 tokens/s prefill, 20 tokens/s decode, network term below).

| Interaction | New / cached prompt tokens | Output tokens | First token | Total |
|---|---|---|---|---|
| Intent fallback, cold cache | 340 / 0 | 1-8 | about 1.5 s | about 1.6-1.9 s |
| Intent fallback, warm cache | 40 / 300 | 1-8 | about 0.15-0.3 s | about 0.2-0.7 s |
| System command as schema-checked JSON | 100 / 400 | about 40 | about 0.3-0.6 s | about 2.3-2.6 s |
| Explain a compiler diagnostic | 300 / 500 | about 150 | about 1.4 s | about 9 s |
| Generate a REPL script | 300 / 1,200 | about 300 | about 1.4 s | about 16-17 s |
| Draft a patch to a 2,000-token component | 2,300 / 600 | about 400 | about 10-11 s | about 30-31 s |
| Policy choice from a metrics summary | 400 / 600 | about 60 | about 1.8 s | about 4.8 s |
| Any of the above with Qwen3 thinking on | same | +200-1,000 | +10-50 s | +10-50 s |

Local 3B-class budget for comparison (cached prompt, 60-token answer): prefill about 100 new tokens at 450 tokens/s is about 0.2 s, first token 0.25-0.4 s, decode 60 tokens at 45 tokens/s about 1.3 s. Without prefix caching a 1,000-1,500 token system prompt adds 2-3 s (3B) or 4-6.5 s (8B) to every request. Only cached, tiny-output interactions finish under a second; anything generating code or prose takes 10-30 s, so the UI must stream and never block the shell.

**Network and guest term** (unmeasured): LAN round trip 0.2-1 ms wired, 2-10 ms Wi-Fi; slirp per packet 0.1-1 ms; guest smoltcp, HTTP and JSON work per SSE event under TCG 0.1-2 ms; new TCP connection adds one round trip (always with `mlx_lm.server`). Total about 2-15 ms per request. Streamed bandwidth about 4-6 KB/s. Under 1-5% of the shortest interaction.

**Intent-router costs** (parameter counts sourced, latencies estimated): rules under 10 microseconds native, under 1 ms TCG; hashed n-gram int8 about 10-50 microseconds; BERT-Tiny int8 about 1-5 ms; Gemma 3 270M scoring label tokens 30-150 ms native or 0.6-3 s under TCG. Floating-point inference in ring 0 needs explicit FPU handling (KML) or integer weights (LinnOS); a ring-3 router avoids both.

**Hot-path gap.** One remote token costs 41-50 ms; learned hot-path policies cost 4-21 microseconds; a 60-token JSON decision plus prefill costs about 5 s. The LLM acts on workload phases lasting tens of seconds or longer, so the policy agent's cadence is 30 s or more and every choice is staged and measured before commit.

**Confirmation gap.** Confirm UI rules are in [compiler-in-terminal.md](./compiler-in-terminal.md).

## Recommended path

1. **M0.** Check guest-to-Mac TCP reachability from WSL2 (`curl http://<mac>:<port>/health` from WSL2 first; record wired vs Wi-Fi and firewall state). Build the host-tested protocol crate (HTTP/1.1, chunked, SSE, OpenAI request and stream types) at any time; it needs no kernel.
2. **Mac mini.** llama-server pinned to one build (b11624 or later), Qwen3-8B Q4_K_M, `--host 0.0.0.0`, explicit `--port`, `--api-key`, thinking off (`--reasoning off` or `chat_template_kwargs`), reduced `--cache-ram`. Whether two slots fit in 16 GB is unverified; if so, pin interactive and control-plane prompts to separate slots with `id_slot`.
3. **M6 (kernel task).** q35, `-device virtio-net-pci,netdev=n0 -netdev user,id=n0`, `-cpu max` under TCG so AVX2, SMEP and SMAP are visible. `VirtIONet` with our `Hal`, a smoltcp `Device` adapter (build with `default-features = false` plus `alloc`, `medium-ethernet`, `proto-ipv4`, `socket-tcp`, optionally `socket-dhcpv4`), static 10.0.2.15/24 via 10.0.2.2, polled network task, MSI-X later. Print `GET /health` and RTT (L1, 2-4 days), then streaming chat with chunked decoding, SSE, `serde_json`, timeouts, cancel and guest timing against server `timings` (L2, 4-6 days).
4. **M7.** Socket syscalls; move the client into ring-3 `llmd` with a request queue (L3, 1-2 weeks). `llmd` owns the HTTP client, request timeouts and cancellation, a boot-time health probe, a telemetry log comparing guest wall time with server `timings`, prompt templates with stable prefixes, and a grammar and schema library. It treats every model output as untrusted and re-validates it.
5. **M8.** Constrained outputs (JSON schema for commands, GBNF for scripts), show, confirm, run, router tier 1 (L4, 1-2 weeks). Natural-language-to-script uses a fixed system prompt (language summary plus 20-50 examples) and prefix caching.
6. **M10.** Control-plane policy agent (L5, 2-3 weeks): every 30 s or more it summarizes metrics, asks llama-server for a `json_schema`-constrained choice from the policy registry with bounded parameters, and hands it to the kernel, which stages, measures against the incumbent, commits or reverts under a sched_ext-style watchdog. Optional router tier 2 (L6, 1-2 weeks): host-trained int8 classifier.
7. **Exit criteria.** First token under 0.5 s with a cached prompt; a one-line script fully generated in under 3 s; a system command as schema-checked JSON in about 2.5 s; commands and scripts work identically with the Mac mini unplugged.
8. **Later.** Ring-3 in-OS inference service (NightRun-style, hard-float target, XSAVE) for offline fallback; typed capability tool-calling with audit trail; TLS via proxy once traffic leaves the LAN; bare-metal NIC drivers (virtio exists only in VMs); GPU only as a remote endpoint.

## Open questions

1. **What are the real guest-to-Mac round trip and per-request overhead through slirp under KVM in WSL2 and under TCG?** Time a TCP connect plus `GET /health` 100 times from the guest, compare with `curl` from WSL2 and from Windows, and log guest wall time against server `timings`.
2. **Does the WSL2 network mode (VirtioProxy now, NAT before) change the source address the Mac sees,** and where do the build service, tunnel and optional GPU endpoint live? Decides the firewall rule.
3. **Does QEMU issue 4492 (virtio-net hang) affect long LLM streams** under KVM in WSL2 as well as WHPX? Run a 30-minute streamed-completion loop at M6.
4. **Is the Windows PC wired or on Wi-Fi to the Mac mini, and do Windows Defender Firewall or the macOS firewall interfere?** Changes the network term several-fold.
5. **What are the real prefill and decode rates for the chosen 8B on this Mac mini, with and without a grammar?** Run `llama-bench -p 1500 -n 300 -pg 1500,300 -d 0,2048`, then llama-server with and without `grammar` and `json_schema`, reading `timings`. Also compare against the founder's reported 20 tokens/s.
6. **How much memory headroom does the 16 GB Mac have** for the 8B, a second slot, an optional 3B router and the prompt cache? Watch memory pressure at `--cache-ram` 2048 and 4096.
7. **Is MLX meaningfully faster than llama.cpp on a base M4 for 8B 4-bit?** Matters only if the founder would give up GBNF. `mlx_lm.benchmark -p 1500 -g 300` against question 5.
8. **How large will live-editing contexts get?** Component sources of 5-20k tokens mean 10-90 s of cold prefill; do we need retrieval or summarization?
9. **How does the guest learn the Mac's address:** config file, slirp DNS or DHCP reservation? Whether slirp forwards `.local` names or multicast is unverified. Use a static address in a boot config file until tested.
10. **Which intents must work locally without the remote LLM** (help, run, open source of component X, reload, roll back)? Sets the router's label set.
11. **Should the LLM ever emit policy code,** or only choose and parameterize? Evidence favours the second; revisit after the M10 demo shows whether selection moves the synthetic metrics.
12. **What is the security model for LLM-proposed changes to kernel tunables:** who approves, how is rollback triggered? Default: human approval plus mechanical rollback (see live-editable-system.md).
13. **Will `smoltcp` keep receiving maintenance after embassy-net moves to xarxa?** Watch both repositories.
14. **Polled or interrupt-driven (MSI-X) virtio-net in the POC?** Polling is simpler; compare time to first byte and guest CPU at M6.
15. **If Ollama is ever used, does its native NDJSON stream use HTTP chunked encoding?** Only the content type was verified.
16. **Does WHPX or nested KVM expose AVX2 and XSAVE to the guest, and what are the real native llama-bench numbers on this PC?** Only for the post-POC in-OS inference decision.
17. **Model licensing for anything bundled in the OS image** (Apache-2.0 vs custom terms): confirm per model card before shipping weights.
