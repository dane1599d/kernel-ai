# Compiler in the terminal: language, JIT and LLM-generated script

- **Date:** 2026-10-14
- **Status:** Research memo (no code)
- **Scope:** How TempleOS and ZealOS compile shell input straight into memory; which language, compiler and JIT options work in no_std Rust under Kernel AI's ring and address-space rules; and how LLM-written script is constrained, shown, confirmed and run in a sandbox.
- **Related memos:** [rust-kernel-foundation.md](./rust-kernel-foundation.md), [live-editable-system.md](./live-editable-system.md), [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md), [templeos-components.md](./templeos-components.md)

## Conclusions

1. **TempleOS's shell is a real native compiler: each statement becomes x86_64 bytes in heap memory, and the CPU then CALLs them. Nothing is interpreted.** The terminal loop `ExeCmdLine` passes each statement to `LexStmt2Bin`. That function parses the statement into reverse-Polish intermediate code, appends a return and calls `COCCompile` [E4, E5, E8]. `COCCompile` runs the optimizer: `OptPass012` twice, passes 3 to 6, then `OptPass789A` repeatedly until the code stops shrinking. Only pass 10 writes bytes, into exactly `code_size` bytes taken with `MAlloc(code_size, Fs->code_heap)` [E6, E7]. The shell then executes `Call(machine_code)`, stores the answer and the elapsed time, and frees the statement's code. Function definitions stay in the code heap and in the task's symbol table, which falls back to the parent tables up to Adam [E4, E13, E14]. Everything except the Kernel and Compiler modules is JIT-compiled from source on every boot [E12].

2. **ZealOS is the same compiler under new names. Use it as a readable reference, not as a second design.** Its own documentation says ZealC is HolyC with reformatting, renames, bug fixes and additions. The only functional compiler changes in its log are assembler additions, and `src/Compiler` has had no functional commit since 2022-01-28 [E27, E28, E29]. It still runs in ring 0 with memory that is writable and executable at once, and it still allocates JIT output from `Fs->code_heap` [E30, E31]. holyc-lang (2026) is the useful modern counterpoint: it runs a HolyC JIT in user space under W^X by mapping pages read-write and then switching them to read-execute [E32, E33].

3. **The TempleOS mechanism depends on rules our fixed decisions remove, so we copy the experience, not the mechanism.** TempleOS runs everything in ring 0 and shares one identity-mapped page table across all tasks. Every page is writable, executable and user-accessible: EFER.NXE is never set, page entries are `0x87`, and SMEP is off. All code sits in the low 2 GiB, so a rel32 `CALL` reaches any kernel function, and scheduling is cooperative [E7, E8, E20 to E24]. In Kernel AI, REPL code runs in ring 3. It cannot touch or call pages mapped U/S=0, and once NXE and XD are set it cannot execute from writable pages. It also cannot allocate on another session's heap [E10, E109, E110, E111]. These parts carry over: statement-at-a-time compile-and-run, symbols that persist for the session, one language for the shell and for programs, and built-in disassembly and trace tools [E2, E13, E17, E25].

4. **TempleOS does not update existing callers when a function is redefined, so live editing needs an indirection layer that we must build.** A redefinition adds a new symbol that shadows the old one. A call site compiled against a defined function holds a direct `CALL` to the old address. Only calls compiled while the function was still a forward-declared extern go through its `exe_addr` slot [E13, E15, E16]. holyc-lang kept the same rule in 2026 ("already-patched code keeps the old one") [E34]. Live editing means that editing a function changes how code that already calls it behaves. For that, every function needs either a per-symbol slot, which costs one indirect call, or a patchable stub. See [live-editable-system.md](./live-editable-system.md).

5. **For the POC, embed Rhai in a ring-3 script-host process. It is the only off-the-shelf candidate that is no_std, actively released, sandboxed by default and equipped with execution limits.** Rhai 1.26.1 (2026-09-10, MIT or Apache-2.0) builds as core plus alloc with its `no_std` feature, which its book says needs nightly Rust. It keeps REPL state between evaluations through a `Scope`. Its `Engine` offers limits on operations, call depth, expression depth, sizes and variables, plus `on_progress` termination, `set_allow_looping`, `disable_symbol`, custom syntax and a bare `new_raw` engine [E37 to E42]. The costs are real. Rhai has no formal grammar, so any GBNF for it is a hand-written approximation [E43]. The released version depends on `smartstring`, which is MPL-2.0+ and unmaintained; the MIT-licensed `compact_str` replacement exists only in the unreleased 1.27.0 [E44, E45]. Rhai walks the AST unless the Grain bytecode VM is enabled [E44]. It also does not look like HolyC: custom syntax can add statement forms, but it cannot turn Rhai into C.

6. **Each of the other language options falls short for the POC in one respect.** A custom HolyC-like language gives full control and an exact grammar, but it costs months and no model has training data for it. TempleOS's compiler is 18,634 lines, and holyc-lang's JIT commit alone was 30,522 lines [E35, E96, Estimates]. No pure-Rust Lua builds for no_std today. Freestanding C Lua does work (Lunatik runs it inside the Linux kernel), but it brings a C toolchain, a libc subset, and undefined behaviour whenever a Lua error `longjmp`s across Rust frames [E49 to E53]. Stak gives Scheme a genuinely tiny no_std VM, but its compiler wrapper uses std, and Scheme is a low-resource language for code models [E54, E55, E95]. wasmi is an excellent no_std execution sandbox with fuel and resumable calls. However, it is not a language and it cannot parse WAT without std, so it fits later as a compile target [E57 to E61]. Rune is no_std with its compiler included, but it is a 2.8 MB crate, and its no_std use beyond a hosted example is unverified [E48]. Koto, Gluon, Dyon, Mun, Boa and mlua all need std [E56].

7. **Small models write unfamiliar syntax badly, so the language the LLM writes must be C-family and small, and the prompt must teach it.** How well a code model writes a language tracks how much of that language it was trained on; Lua and Scheme count as low-resource [E95]. On Cangjie, models below 200B parameters scored near zero, and most failures were "foreign syntax". A syntax reference of about 2,100 tokens was the best prompt-side fix [E96]. Few-shot examples help 1B to 7B models only a little [E97], while a grammar in the prompt and a grammar at decode time both help [E99, E88]. Rhai ships a cheat sheet written for AI agents [E46]. This favours Rhai's C/JS-like syntax over Lua or Scheme for the POC. If we later build our own language, it also favours a strict C subset over a faithful HolyC with postfix casts and implicit printing.

8. **A native JIT in no_std is possible, but no ready-made path exists. Build an interpreter first.** `cranelift-codegen` and `cranelift-frontend` are no_std and are cargo-checked for `x86_64-unknown-none` in Wasmtime's CI. But `cranelift-jit` and `cranelift-native` require std, so we would have to write our own code-page allocator, relocation patcher, ISA-flag setup and W^X switch [E63 to E66]. `dynasmrt` requires std, and Wasmtime cannot compile Wasm in no_std at all [E69, E62]. iced-x86, with its `no_std` and `code_asm` features, is the lightest proven encoder for a hand-written template JIT, though its last release was 2024-01-20 [E68]. Copy-and-patch is the cheapest documented route to native code later, at the cost of a build step on the host that generates stencils [E71, E72].

9. **An interpreter is fast enough for what the POC must prove.** Efficient interpreters run about 10x slower than native code, and register bytecode VMs beat stack VMs by roughly 25 to 35% [E73, E74, E75]. POC scripts are control-plane work: read metrics, propose a policy, print. Generating a script at about 20 tok/s takes 7.5 to 20 s (see Estimates), which dwarfs any interpretation time. Under QEMU TCG on Windows, a guest JIT would also force QEMU to discard translated code each time the JIT writes a code page [E76].

10. **Design the LLM step as a fixed sequence: free explanation, a grammar-constrained code block, local re-parse, show, confirm, run in a fresh sandbox, log.** Build the grammar per request so that it names only the API functions and REPL variables that request may use. Geng et al. call this an input-dependent grammar [E87]. Let the model explain before it writes code, because tight format constraints reduce reasoning quality and constrained decoding can distort the output distribution [E92, E89]. GBNF can leave a free section open and constrain only the code after it [E78]. Reject any answer that stopped on the token limit, because a prefix that matches the grammar is still not a complete program [E80, E88]. Allow at most one or two repair rounds, each shown and confirmed again, because self-repair gains are modest [E100].

11. **Of the three candidate servers, only llama-server accepts a raw grammar. Send script generation to llama-server, or accept validate-and-retry.** llama-server accepts a `grammar` field even on `/v1/chat/completions`. It rejects a grammar combined with `json_schema` or with tools, and it caps bounded repetition at 2,000 [E79, E80, E81]. Ollama accepts only JSON or a JSON schema, and `mlx_lm.server` accepts no constraint at all [E84, E85]. Constrained decoding for MLX exists only as in-process Python libraries or through LM Studio [E86]. In JSONSchemaBench, grammar sampling roughly doubled llama.cpp's time per token on server hardware. Whether the stated 20 tok/s holds with a grammar on the M4 must therefore be measured [E90].

12. **The grammar is a syntax filter, not a safety control, and the confirm prompt checks intent; it is not a security boundary.** Constrained decoding cut syntax errors in generated Python and Go by 96%. It cannot enforce declare-before-use, types, termination or completeness [E88, E93, E83]. Users approve 93% of agent permission prompts, and prompt injection has no known fool-proof prevention. OWASP says to treat model output as untrusted input and to authorize every action downstream [E101, E104, E105, E106]. So the OS must re-parse and check every script with its own front end and derive the capability list from the parsed code. The kernel must enforce each call.

13. **Put the compiler, the interpreter and all generated code in ring 3, with a separate address space per script, W^X, SMEP, SMAP, UMIP and capability handles. Never compile untrusted code in ring 0.** Ring-3 code cannot touch U/S=0 pages. With IOPL 0 it cannot execute `IN`, `OUT`, `CLI` or `STI`, so the timer can always preempt it [E111, E113]. SMEP stops the kernel from executing user pages, and SMAP stops it from reading or writing them except inside explicitly marked copy routines. A later JIT must write pages read-write with XD set, then remap them read-execute, invalidate the TLB on every CPU, and serialize before running the new code [E109, E110, E112]. Linux disables unprivileged BPF, its in-kernel verifier plus JIT, by default. Rhai only promises that any panic is a bug, which is not a guarantee to stake ring 0 on [E107, E41]. A new script process should start with nothing and receive only the handles granted on the confirm screen, as Fuchsia processes do [E119, E120].

14. **No grammar or analysis can guarantee that a script terminates. Termination has to come from a loop-free subset or from budgets.** The halting problem is undecidable [E108]. Rhai can switch loops off and cap operations, wasmi meters fuel, and the kernel's preemptive timer and kill are the backstop [E40, E58].

15. **Test the sandbox under QEMU TCG with `-cpu max`, and treat PCID as optional.** TCG emulates NX, SYSCALL, SMEP, SMAP, UMIP and PKU. The default `qemu64` model exposes no leaf-7 CPUID features, so SMEP is off unless the command line uses `-cpu max` or `+smep`. QEMU's source lists PCID as missing in system emulation [E118]. Whether WHPX passes these features to the guest is unverified.

### Recommendation

Take the interpreter-first path below. Steps C0 to C3 belong to the POC; C4 and C5 come after it. In the POC, "compiler in the terminal" means that each line typed or generated is compiled to Rhai's AST (or Grain bytecode) and run immediately. Native code generation is deliberately deferred.

| Step | What | Done when | Effort (estimate) |
|---|---|---|---|
| C0 | Ring-3 script host prerequisites (from [rust-kernel-foundation.md](./rust-kernel-foundation.md)): own CR3 per process, SYSCALL entry and exit with stack switch and a canonical-RCX check before SYSRET [E115], user heap, timer preemption, per-process page and CPU-time quotas, 8 to 12 capability syscalls | A ring-3 process that faults, spins forever or exhausts its memory is killed and the kernel keeps running | 4 to 8 weeks after paging and interrupts at blog_os level |
| C1 | Rhai REPL in the script host: `no_std`, `Engine::new_raw`, limits on, a persistent `Scope`, one statement or definition per Enter, answer echoed after each line as TempleOS does | Definitions and variables typed in the framebuffer terminal persist across lines | 2 to 4 weeks |
| C2 | OS API as registered Rhai functions that wrap capability syscalls: console output, read-only scheduler and memory metrics, and `policy.propose` sent to a kernel-side validator that checks bounds | A typed script can change a scheduler or reclaim parameter only through the validator | 1 to 2 weeks |
| C3 | LLM path: per-request GBNF, cheat-sheet prompt, llama-server call, stop-reason check, local parse with the same restricted engine, capability list derived from the parse, confirm screen, fresh process with only granted handles, 1 or 2 repair rounds, append-only log | The 50-task benchmark in Open question 1 runs end to end with complete logs | 3 to 5 weeks |
| C4 (post-POC) | Our own HolyC-flavoured strict C subset, compiled to a register bytecode VM written in Rust, with the same API and REPL behaviour | Steps C1 to C3 work unchanged on the new language | 2 to 4 months part-time; 5k to 10k lines |
| C5 (post-POC) | Native code in ring 3 under W^X: a template JIT on iced-x86, Wasm emitted with `wasm-encoder` and run on wasmi, or Cranelift codegen with our own loader | Profiles show the interpreter is the bottleneck for a real workload | 1 to 3 months, plus 2 to 3 weeks of kernel W^X and TLB-shootdown work |

Rules that hold at every step: the kernel never compiles anything. LLM output runs only after confirmation, in a fresh process that holds only the handles the user granted. Every syscall is checked in the kernel. Grammar validity is never treated as safety. Nothing an LLM writes runs on the scheduler hot path; scripts can only propose policy through the validator.

### Not possible / not viable

- **TempleOS's sequence "MAlloc a buffer, write bytes, CALL it" cannot be copied once W^X is on.** It works only because NXE is never set and XD is clear everywhere. With NXE=1 and XD set on writable pages, instruction fetch from them is blocked, so a JIT must write through a read-write mapping, remap read-execute, shoot down TLBs and serialize [E22, E23, E109, E112].
- **Ring-3 REPL code cannot call kernel functions by address or resolve kernel symbols the way HolyC code does.** User-mode access to U/S=0 pages faults; the only ways in are SYSCALL or an interrupt gate. The OS API the REPL sees must be syscall wrappers [E111, E115].
- **With SMEP on, the kernel cannot execute JIT code placed in user-accessible pages** [E110].
- **Two REPL sessions cannot share heaps or raw pointers** (HolyC's "MAlloc and Free off-of other task's heaps") without explicit shared mappings or IPC [E10, E21].
- **The TempleOS or ZealOS compiler source cannot be reused as-is in a Rust kernel.** It compiles only with TempleOS's own compiler and assumes ring 0, the identity map and a code heap in the low 2 GiB. Licensing is not the obstacle: TempleOS is public domain and ZealOS uses the Unlicense [E19, E20, E26].
- **`cranelift-jit` and `cranelift-native` cannot be used in no_std.** They depend on libc, memmap2 and region, and use `std::is_x86_feature_detected!` [E65, E66].
- **Wasmtime cannot compile Wasm inside a no_std build;** it only runs modules precompiled elsewhere [E62].
- **`dynasmrt` cannot run in no_std without a fork,** because it depends on memmap2 and std [E69].
- **No maintained pure-Rust Lua builds for no_std today** [E53]. **Koto, Gluon, Dyon, Mun, Boa and mlua cannot run in no_std** [E56].
- **A no_std wasmi cannot parse WAT;** the `wat` feature forces std [E57].
- **An exact GBNF for Rhai cannot be derived, because Rhai has no formal grammar** [E43].
- **C Lua errors must never unwind through Rust frames by `longjmp`;** under current Rust rules that is undefined behaviour [E50, E51].
- **Raw GBNF cannot be sent to Ollama or to stock `mlx_lm.server`** [E84, E85].
- **A single llama-server request cannot combine a custom grammar with `json_schema` or with tools, and grammar repetition cannot cap length above 2,000;** use `n_predict` [E79, E81].
- **No grammar can guarantee that code type-checks, uses only declared names, does what the user asked, or is complete** [E83, E88, E93, E80].
- **No analysis can prove that an arbitrary script in a Turing-complete language terminates** [E108].
- **Prompt injection cannot be reliably prevented at the model level** [E104].
- **The confirm prompt cannot serve as the security boundary** [E101, E102].
- **PCID code paths cannot be exercised under QEMU TCG** [E118].

## Evidence

### TempleOS: how the shell compiles into memory

TempleOS files are cited from the `archive` branch of the cia-foundation/TempleOS mirror. The date given for each is that file's last commit in the mirror, checked with `git log` on 2026-10-14.

- [E1] The repository is a community archive of the final V5.03 snapshot. Its last commit (2020-02-24, minexew) fixes a corrupted `Compiler.BIN`, and its parent (2017-11-21, Terry A. Davis) is "TempleOS V5.03 Nightly". — [commit c26482b](https://github.com/cia-foundation/TempleOS/commit/c26482bb6ad3f80106d28504ec5db3c6a360732c) (2020-02-24; accessed 2026-10-14)
- [E2] "The cmd line feeds into the HolyC compiler line-by-line as you type. A stmt outside a function executes immediately." — [Doc/CmdLineOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/CmdLineOverview.DD) (2016-09-29)
- [E3] Davis writes that the command line "places code into memory it MAlloc()s", that "nothing is interpreted and there is no byte code", and that booting, which compiles many files, "takes only two seconds". The boot time is his claim; no measurement was found. — [Doc/Welcome.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Welcome.DD) (2017-06-19)
- [E4] `ExeCmdLine` ("Terminal JIT-compile-and-execute loop") calls `LexStmt2Bin` for each statement and runs the result with `Call(machine_code)`. It records the answer and the elapsed time, then frees the code unless `CCF_HAS_MISC_DATA` is set. `UserTaskCont` wraps it in a try/catch loop over a `CCF_CMD_LINE|CCF_PMT|CCF_QUESTION_HELP` compiler context. — [Kernel/KTask.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KTask.HC) (2017-06-19)
- [E5] `LexStmt2Bin` parses one statement with `PrsStmt`, appends `IC_RETURN_VAL2` and `IC_RET` to make it a callable fragment, and calls `COCCompile`. The same file defines `ExePutS` (compile and run a string), `ExePrint`, `ExeFile` (which builds `#include "file";`), and `*2` variants that let exceptions propagate. — [Compiler/CMain.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/CMain.HC) (2017-06-19)
- [E6] `COCCompile` runs `OptPass012` twice, then `OptPass3` to `OptPass6`, then `OptPass789A` until the size stops shrinking. In JIT mode it allocates `MAlloc(code_size, Fs->code_heap)`, and a final pass writes the bytes. With Trace on, it disassembles the result. — [Compiler/PrsLib.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/PrsLib.HC) (2017-01-19)
- [E7] Inside `OptPass789A`, pass 9 repeats until the size stops shrinking, and pass 10 is the only pass that writes into the output buffer. `IC_CALL` becomes a 5-byte `E8 rel32` call; in JIT mode, a target beyond ±2 GiB falls back to `MOV RBX,imm64` plus `CALL RBX`. `IC_CALL_INDIRECT2` becomes `MOV RBX,imm64` plus `CALL [RBX]`. — [Compiler/OptPass789A.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/OptPass789A.HC) (2017-01-19)
- [E8] The glossary calls the intermediate code "rev polish stack machine in nature", viewable with `PassTrace()`. JIT mode places code and data in heap memory "immediately ready for in-place execution", and `#include` compiles function by function into the first 2 GiB. All code is kept below 2 GiB because `CALL` reaches only ±2 GiB. AOT (`.PRJ` to `.BIN`) is used only for the Kernel and the Compiler, and users are told "Do not use AOT". A loaded module can be unloaded only by killing its task. — [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD) (2017-06-19)
- [E9] The compiler build order is lexer, hash tables, assembler, parser library, expression and variable parsers, `CMain`, statement parser, optimizer passes 0 to 6, back ends, and finally `OptPass789A`. Parser files are named `Prs*`; ZealOS later renamed them `Parse*`. — [Compiler/Compiler.PRJ](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/Compiler.PRJ) (2016-09-19)
- [E10] TempleOS has no separate preprocessor: the lexer handles `#include`, `#define`, `#if`, `#ifaot`, `#ifjit` and `#exe`. `#exe{}` runs `ExeCmdLine` on each statement at compile time and splices any `StreamPrint` output back into the token stream. `HolyC.DD` also lists no type-checking, inline `asm{}`, a stack that does not grow, and the rule that tasks can "MAlloc and Free off-of other task's heaps". — [Compiler/Lex.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/Lex.HC) (2017-06-19); [Compiler/PrsStmt.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/PrsStmt.HC) (2017-01-19); [Doc/HolyC.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/HolyC.DD) (2017-06-19)
- [E11] "TempleOS does not use object files or a linker." Linking happens when `Load()` copies a `.BIN` module into the code heap and resolves its patch table. — [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD) (2017-06-19); [Kernel/KLoad.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KLoad.HC) (2017-06-19)
- [E12] At boot, `KMain` loads the AOT-built Compiler module and then runs `ExeFile("StartOS")`. `/Adam`, the non-kernel part of the OS, "is JIT compiled during boot". — [Kernel/KMain.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KMain.HC) (2017-11-07); [Doc/GuideLines.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/GuideLines.DD) (2017-01-11)
- [E13] In JIT mode, symbols are looked up in the current task's hash table and then in its parents' tables. Newer symbols shadow older ones, and duplicates are allowed "so that you can repeatedly #include the same file from the cmd line". `Spawn()` links each task's table to its parent's, and `SYS_HASH_FIND` walks the chain linearly. — [Doc/ScopingLinkage.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/ScopingLinkage.DD) (2016-09-29); [Kernel/KTask.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KTask.HC) (2017-06-19); [Kernel/KHashA.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KHashA.HC) (2016-09-29)
- [E14] `Adam("...")` queues source text as a job for the immortal root task and waits for the result. An `#include` sent this way creates code and data visible system-wide. — [Kernel/Job.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Job.HC) (2017-01-26)
- [E15] On a redefinition, `PrsFunJoin` reuses a function entry only if it is in the current table and still extern. Otherwise it creates a new entry that shadows the old one. New functions start with `exe_addr = &UndefinedExtern`. — [Compiler/PrsStmt.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/PrsStmt.HC) (2017-01-19)
- [E16] A call to an already-defined function compiles to a direct `IC_CALL` to the address known at compile time. Only a call to a still-extern function compiles to `IC_CALL_INDIRECT2` through `&exe_addr`, so old callers keep calling the old body. This is the research team's reading of the source, cross-checked with [E7] and [E15]. — [Compiler/PrsExp.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/PrsExp.HC) (2017-01-19)
- [E17] Built-in tools: `Dbg()` or Ctrl-Alt-D enters the debugger. `U()` and `Uf()` disassemble memory or a function, `Trace()` disassembles compiler output, `PassTrace()` shows intermediate code, and `Dr()` dumps registers. — [Doc/DbgOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/DbgOverview.DD) (2017-01-11)
- [E18] A CPU fault in any task goes to `Fault2`, which switches to single-user mode, prints the fault, RIP and CR2, and enters the debugger. No process isolation contains the fault. ### TempleOS assumptions our fixed decisions exclude

- [E20] The Charter requires "Ring-0-only. Everything runs in kernel mode, including user applications", "Full access to everything" and "Single-address-map as though paging is not used". Its governance metric is how fast the compiler compiles itself and the kernel. — [Doc/Charter.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Charter.DD) (2017-06-19)
- [E21] Memory is identity-mapped, and "All tasks on all cores use the same page table map". Dereferencing NULL no longer faults, and a task's memory is freed when the task is killed. — [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (2017-06-19)
- [E22] Long-mode entry writes `IA32_EFER` with only LME set (no NXE) and ORs CR4 with `0xB0` (PSE, PAE, PGE), so neither no-execute nor SMEP is ever enabled. — [Kernel/KStart64.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KStart64.HC) (2017-01-19)
- [E23] Every large page is mapped with low dword `0x87` (present, writable, user, page-size) and upper dword 0. XD is therefore clear, and all memory is writable, executable and user-accessible. — [Kernel/Mem/PageTables.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Mem/PageTables.HC) (2017-11-15)
- [E24] Scheduling is cooperative: "A task runs until it voluntarily yields". Davis puts a task switch at half a microsecond; this is his claim and was not independently measured. — [Kernel/Sched.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Sched.HC) (2017-01-11)
- [E25] "One language and compiler for command-line, scripts, songs, automations and code." Every task has a heap and a symbol table that falls back to its parent's. — [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD) (2017-01-11)

### Interpreter performance and the QEMU environment

- [E73] Efficient interpreters run about 10x slower than optimized native code, while poorly built ones can be over 1,000x slower; dispatch branches dominate the cost. — [Ertl and Gregg, JILP 5](https://jilp.org/vol5/v5paper12.pdf) (2003-11)
- [E74] Translating stack VM code to register code removed over 47% of executed VM instructions. Run time fell by 32.3% with switch dispatch and by about 26.5% with threaded dispatch. — [Shi, Gregg, Beatty, Ertl, VEE'05](https://www.usenix.org/legacy/events/vee05/full_papers/p153-yunhe.pdf) (2005-06-11)
- [E75] Lua 5.0's register VM is "more than twice as fast" as Lua 4.0's stack VM on a simple loop. — [The Implementation of Lua 5.0](https://www.lua.org/doc/jucs05.pdf) (J.UCS 11(7), 2005)
- [E76] In system emulation, QEMU TCG write-protects guest pages that hold translated code. A write to such a page invalidates all translated code for that page. — [QEMU TCG emulation docs](https://www.qemu.org/docs/master/devel/tcg.html) (undated; accessed 2026-10-14)
- [E77] By default, Rust's `x86_64-unknown-none` target does not use SSE, AVX or other floating-point registers, and it uses the kernel code model. — [rustc book: x86_64-unknown-none](https://raw.githubusercontent.com/rust-lang/rust/master/src/doc/rustc/src/platform-support/x86_64-unknown-none.md) (undated; accessed 2026-10-14)

### x86_64 protection hardware and QEMU

- [E109] With `IA32_EFER.NXE = 0`, "instructions may be fetched from any supervisor-mode address". With NXE = 1, fetches are blocked from any page whose XD bit (63) is set. With CR0.WP = 1, read-only pages stay read-only even for ring 0. — [Intel SDM Vol. 3, 325384-093US, §5.6](https://cdrdv2-public.intel.com/929358/325384-093-sdm-vol-3abcd.pdf) (2026-09)
- [E110] "If CR4.SMEP = 1, software operating in supervisor mode cannot fetch instructions from linear addresses that are accessible in user mode." With CR4.SMAP = 1, supervisor data access to user pages is blocked unless EFLAGS.AC = 1. — [Intel SDM Vol. 3, 325384-093US](https://cdrdv2-public.intel.com/929358/325384-093-sdm-vol-3abcd.pdf) (2026-09); [Intel SDM Vol. 3A, 253668-093US, §5.6.1](https://cdrdv2.intel.com/v1/dl/getContent/671190) (2026-09-01)
- [E111] At CPL 3 the processor "can access only user-level pages". An address is supervisor-only if the U/S bit (bit 2) is 0 at any paging level. Systems that use two privilege levels "should use levels 0 and 3". — [Intel SDM Vol. 3A, §6.5, §6.11.2, §5.6.1](https://cdrdv2.intel.com/v1/dl/getContent/671190) (2026-09-01)
- [E112] After software changes access rights in a paging entry, the processor "might not use that change" until the TLB is invalidated. On multiprocessors this requires "TLB shootdown" with IPIs. Code written by one CPU and run by another needs a serializing instruction (for example CPUID) on the executing CPU first. — [Intel SDM Vol. 3, 325384-093US, §5.6, §5.10, §11.1.3](https://cdrdv2-public.intel.com/929358/325384-093-sdm-vol-3abcd.pdf) (2026-09)
- [E113] CR4.UMIP makes SGDT, SIDT, SLDT, SMSW and STR raise #GP at CPL > 0. `IN`, `OUT`, `CLI` and `STI` execute only if CPL ≤ IOPL. — [Intel SDM Vol. 3A, §2.5](https://cdrdv2.intel.com/v1/dl/getContent/671190) (2026-09-01); [Intel SDM combined volumes, 325462-093US, Vol. 1 §20.5.1](https://cdrdv2.intel.com/v1/dl/getContent/671200) (2026-09-01)
- [E114] CR3 holds the root of the paging hierarchy, and "each task can have its own hierarchy". PCIDs (12-bit) let the TLB cache several address spaces at once; they are an optimization, not protection. — [Intel SDM Vol. 3A, §2.1.5, §5.10.1](https://cdrdv2.intel.com/v1/dl/getContent/671190) (2026-09-01)
- [E115] SYSCALL/SYSRET is the fast ring-3 to ring-0 path, and the hardware does not switch stacks. "The SYSRET instruction generates #GP(0) if the value of RCX is not canonical", so the OS must check RCX first or use an IST stack. — [Intel SDM Vol. 3A, §6.8.8](https://cdrdv2.intel.com/v1/dl/getContent/671190); [Intel SDM Vol. 2B, SYSRET](https://cdrdv2.intel.com/v1/dl/getContent/671200) (2026-09-01)
- [E116] Protection keys (CR4.PKE, PKRU) control only read and write access to user pages, not execution. — [Intel SDM Vol. 3A, §2.5](https://cdrdv2.intel.com/v1/dl/getContent/671190) (2026-09-01)
- [E117] Linux counters Meltdown-class leaks with page-table isolation: separate page tables used while user space runs. — [Linux PTI documentation](https://docs.kernel.org/arch/x86/pti.html) (undated, 7.3.0-rc7; accessed 2026-10-14)
- [E118] QEMU's TCG feature masks include SMEP, SMAP, UMIP, PKU, NX and SYSCALL. PCID is listed as "missing" for system emulation and is exposed only in user-mode builds. The default `qemu64` model has no leaf-7 features, and `max` "Enables all features supported by the accelerator". — [QEMU target/i386/cpu.c](https://gitlab.com/qemu-project/qemu/-/raw/master/target/i386/cpu.c) (2026-10-05; re-checked 2026-10-14)

**Effort estimates.** All assume one strong Rust developer who is new to compilers and kernels, working part-time.
- Embedding Rhai in a ring-3 REPL process: 2 to 4 weeks, once ring-3 processes, a user heap, console syscalls and a timer exist. This assumes Rhai builds for our user target on nightly, which is unverified for x86_64.
- A custom HolyC-like language (lexer, parser, simple type checker, register bytecode VM, REPL integration): 5k to 10k lines of Rust, 2 to 4 months. The basis is TempleOS's stage sizes above, minus the assembler, disassembler and most of the optimizer.
- A native template JIT on iced-x86 for a typed C subset: another 3k to 6k lines and 1 to 3 months. Cranelift glue (IR building, our own code-page allocator, relocations, W^X calls): 1.5k to 3k lines and 1 to 2 months, with a much larger dependency tree. Both assume the bytecode front end already exists.
- Kernel support for W^X JIT pages (map RW with XD, remap RX, local INVLPG, IPI shootdown, serialization): 2 to 3 weeks once SMP and IPIs work.
- A GBNF covering a small Rhai or C subset (statements, expressions, calls to allow-listed functions): 40 to 120 lines. The basis is llama.cpp's roughly 40-line sample C grammar [E83].

**Latency budget for one LLM-written script.** These are estimates for an 8B 4-bit model at the stated 20 tok/s. Network and prefill are covered in [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md).

| Stage | Estimate | Basis |
|---|---|---|
| Prompt prefill (cheat sheet plus context, about 2.5k tokens) | Unmeasured; a prompt cache should amortize it (unverified) | [E96] for cheat-sheet size |
| Generate 150 to 400 tokens (explanation plus a 10- to 40-line script) | 7.5 to 20 s | 20 tok/s fixed decision |
| The same with grammar overhead, if it matches JSONSchemaBench | up to 15 to 40 s | [E90], different hardware |
| Grammar mask with llguidance | under 0.2% of a 50 ms token budget | [E82], JSON grammars, not code grammars |
| Local parse, scope check and capability derivation | milliseconds; TCG may multiply this | Assumption |
| Spawning a fresh script process | microseconds to milliseconds; a full TLB flush without PCID | [E114, E118] |
| Human confirmation | seconds | — |

Generation dominates. Neither the sandbox nor interpretation adds noticeable delay for a user already waiting 10 to 40 s.

**Confirm-screen contents (design analysis, based on [E101 to E106]).** The screen shows the user's request verbatim and the full generated source, with a diff against any previous attempt. It shows the model's explanation and the capability list derived from the parsed code, together with the resource limits. It also shows provenance: model, quantization, server address, grammar hash, sampling parameters and stop reason. Finally, it flags every untrusted input that was in the prompt (files, network responses, source comments) as a possible injection channel. The default answer is No. Approval covers exactly what is shown, once, and there is no "always allow" for generated code.

**Log contents.** The kernel keeps an append-only log, readable from the REPL. Each entry records the timestamp, the prompt, hashes and sources of the context items, the model and server identity, the grammar hash, the raw output, the local check result, the user's decision and the capabilities granted. It also records runtime events: denied syscalls, faults, budget exhaustion, the kill reason, the exit status and CPU time. The basis is OWASP's call to "Log and monitor" [E106], and the log also gives live editing a record to explain and roll back from.

**The derived capability list is not the enforcement mechanism.** If the language lets a script call a function through a value (a function pointer, or something like eval), the list derived from the parsed code can be incomplete. The kernel's handle checks remain the ground truth. The derived list exists so the user sees what the script intends to do. Constructs that hide which function is called should be disabled in the engine configuration the LLM targets (Open question 6).

**Meltdown and KPTI.** QEMU TCG emulates instructions in software and does not model the CPU's speculative execution, so Meltdown-style leaks should not appear under TCG. This is our inference, not a measured result. On real Meltdown-affected Intel hardware, U/S separation alone is not enough, and separate user page tables are needed [E117].

## Open questions

1. **Can an 8B model write correct Rhai against our API often enough?** This decides D1 and D8. Resolve it by running 50 synthetic tasks on the Mac mini through llama-server, with and without the grammar and the cheat sheet. Example tasks: read the memory metrics and print a table, or propose a time-slice change for one task class. Record parse, check and run success, plus success after one repair round. As our own threshold, a first-pass run success below about 70% would argue for moving step C4 forward.
2. **How much does a code grammar slow generation on the M4?** It sets the real latency of every LLM script. Measure tok/s for the chosen 8B model in llama-server with no grammar, with a GBNF of about 100 rules, and with an LLGuidance build. Also check whether the Homebrew or official macOS build includes LLGuidance [E82, E90].
3. **Does Rhai build and run in our ring-3 target?** Our evidence shows only a riscv32 check in Rhai's CI and a nightly requirement in its book [E39]. Build it in Kernel AI's CI for the user-space target, with and without `no_float`, and record binary size and startup time under TCG.
4. **Which Rust target and FPU policy will ring-3 code use?** `x86_64-unknown-none` disables SSE by default [E77]. User code that uses floats needs the kernel to save and restore FPU state. Decide this together with [rust-kernel-foundation.md](./rust-kernel-foundation.md); defaulting to `no_float` in the POC avoids the question.
5. **What happens in Rhai when a script function is redefined in a persistent Scope or AST?** If existing callers do not switch to the new body, D4 needs our own indirection on top of Rhai. Test it in hosted Rhai first, then in the VM.
6. **Which Rhai constructs allow indirect calls or eval, and can `disable_symbol` or engine options switch them off?** A sound capability list depends on the answer (see Estimates and analysis). Read the Rhai Book's function-pointer and eval sections, then test with a restricted engine.
7. **Should any form of compile-time execution, like TempleOS's `#exe{}`, survive?** It runs arbitrary code while compiling [E10], which is a sandboxing problem when the source came from an LLM. Recommended: allow it only in code the founder types, never in LLM output.
8. **Does WHPX expose SMEP, SMAP, UMIP and PCID to the guest on Windows 11?** If it does, the kernel's behaviour under WHPX and under TCG can diverge. Boot a test kernel that prints CPUID leaves 1 and 7 under `-accel whpx` and under TCG with `-cpu max` [E118].
9. **How slow is the interpreter in the VM?** Measure the same Rhai and wasmi micro-benchmarks on the Windows host, under TCG and under WHPX, to confirm that interpretation is negligible next to LLM latency.
10. **Does Cranelift's no_std codegen actually work at runtime on `x86_64-unknown-none`?** CI only cargo-checks it [E64]. This matters only for step C5; revisit when the interpreter becomes a bottleneck.
11. **Should traffic to the Mac mini be authenticated?** A LAN attacker who can inject code that a fatigued user approves defeats the confirm step [E101]. Decide in [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md); a shared-secret header is the minimum.
12. **Is fine-tuning a small model on our language worth it later?** Fine-tuning is usually best for small models on low-resource languages [E97]. Revisit once the log has collected enough confirmed, working scripts to serve as training data.
