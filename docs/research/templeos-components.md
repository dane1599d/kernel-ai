# TempleOS and ZealOS components: what to keep, what to leave behind

**Date:** 2026-10-14

Merged from two independent research passes (local and cloud).

- **Project:** Kernel AI
- **Scope:** which parts of TempleOS (HolyC, DolDoc, the Adam task, RedSea, graphics, debugger, boot speed) and ZealOS Kernel AI carries forward as ideas, which it leaves behind, and why it drops the single address space and ring-0-only model. Milestones M0-M10 are defined in [rust-kernel-foundation.md](./rust-kernel-foundation.md).
- **Related memos:** [compiler-in-terminal.md](./compiler-in-terminal.md), [live-editable-system.md](./live-editable-system.md), [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md)
- **Sources:** TempleOS citations point to the `archive` branch of https://github.com/cia-foundation/TempleOS (base `https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/`), a V5.03 snapshot. ZealOS is https://github.com/Zeal-Operating-System/ZealOS (`master`). Line counts are the passes' own raw counts. TempleOS was written by Terry A. Davis (1969-2018) and is treated here as serious systems work (https://en.wikipedia.org/wiki/TempleOS).

## Conclusions

1. **Take user-experience ideas, not code or kernel architecture.** TempleOS source cannot be compiled outside TempleOS. Its kernel is defined by ring 0 only, one identity-mapped address map, cooperative scheduling and no network, and the most active fork (ZealOS) kept all of that except the networking ban. What survives rings: a terminal that compiles and runs what you type, a source link behind every symbol and address, one document model for terminal, help, editor and debugger, an always-resident debugger, simple CPU-rendered graphics, and boot speed as a design metric.
   - Three ideas matter most: one language from prompt to system, a hierarchical introspectable symbol table where every symbol resolves to its source line, and one rich document format.
   - EXODUS ran the TempleOS kernel in ring 3 on Linux, Windows and FreeBSD, so the experience does not need ring 0.

2. **HolyC: keep the REPL ergonomics, leave the type system, kernel-call model and memory assumptions.** The portable parts are small: top-level statements run in order with no `main()`; zero-argument calls need no parentheses (`Dir;`); default arguments may sit anywhere; a bare string prints; `ans` holds the last result; `#exe{}` runs code at compile time. Leave behind: no type-checking, no `typedef` or `continue`, `lock{}` its author calls "a little shoddy", stacks that cannot grow, and direct kernel calls with no syscall layer. The language is Rhai (founder decision, see [compiler-in-terminal.md](./compiler-in-terminal.md)); a command-sugar layer imitates these ergonomics only. Do not aim for HolyC source compatibility.

3. **The most valuable feature is that every symbol, address and stack frame links to its source line.** Symbols carry a `src_link`; `SrcEdLink()` turns any address into an `FL:file,line` link; stack traces print with `%P` as clickable links; `Man(sym)`, `E(_RIP)` and `Fix` open a symbol's source, the faulting instruction and the last compile error; AutoComplete jumps to source with CTRL-SHIFT-F1. ZealOS kept all of it. The mechanism for Kernel AI (host-built symbol index, DWARF line tables, source bundle) is specified in [live-editable-system.md](./live-editable-system.md). The lesson is reach: the link must appear everywhere an address or name is printed, starting with the first fault screen.

4. **DolDoc: keep the single document model and its link vocabulary; adapt it as a structured node tree.** One engine drives the editor, viewer, help browser and command line, and links target a file, a match in a file, a file line, a symbol's source or an address. Leave behind:
   - the on-disk format (binary sprite data after the terminating NUL, the cursor stored as ASCII 5, `$` escaped as `$$`), which breaks git, diff and LLM ingestion;
   - click-to-run macros (they bypass show-confirm-run);
   - widgets bound to raw addresses (meaningless across address spaces without a kernel or debugger intermediary).
   Terminal output becomes a typed node tree (styled spans, tables, images, collapsible sections, widgets bound to typed structs) with typed link targets (`src:path#L42`, `sym:name`, `task:id`, `help:topic`, `llm:turn`) and a plain-text projection for the serial log and git. LLM replies render into the same tree. Buttons insert REPL text rather than running it silently.

5. **The Adam task: keep the role, not the implementation.** Adam is the immortal parent of all tasks, holds the global API symbol table and serves a job queue (including "compile and run this source text"). Code sent to Adam becomes system-wide and immortal and Adam's heap is in effect kernel memory. In Kernel AI the role belongs to a privileged ring-3 system service (the supervisor of the live-edit memo): a system registry (name, kind, type signature, handle or address, source span, version), a compile-and-run job queue, each job in a fresh process holding only granted handles. Each REPL task's scope chains to its parent, then to the system scope; promotion into system scope needs a capability. Jobs that originate with the LLM enter the same queue flagged for confirmation.

6. **TempleOS reloads code by shadowing, and it feels live because it boots fast, not because it hot-swaps.** Re-including a file allocates new memory and shadows old symbols (existing callers keep the old code); AOT-loaded code unloads only by killing its task; changes to `/Adam` or `/Home` need a reboot, and a syntax error in a start-up file can make the partition unbootable. Keep the habit of re-running a file while editing it; build replacement, reclamation and rollback new (live-edit memo). Hot-swap mechanism: per-symbol indirection slots for REPL definitions, supervisor swap for components, rebuild and reboot for the kernel.

7. **Leave the task and scheduler model behind entirely.** Cooperative round-robin, no priorities, a task runs until `Yield()`, master/slave multicore with no migration, only Core0 tasks own windows, no process/thread distinction. A task that never yields cannot be descheduled, so there is no decision point for a policy. Kernel AI uses the preemptive, pluggable-policy scheduler of M4 and M5.

8. **Leave the memory model behind.** One identity-mapped page table of 2 MB or 1 GB pages, nothing swaps, NULL no longer faults, long sessions fragment until a reboot, stacks cannot grow. There are no per-process mappings, no 4 KB pages for a reclaim policy to choose among, and no swap device.

9. **Do not use RedSea as a writable file system.** Files are contiguous and cannot grow (deliberate, "to prevent commercialization"); a write deletes the old file, allocates, writes and records the directory entry last (a crash in between loses both versions); allocation fails when no single run fits; no bad-block table, redundancy or locking; the file manager fails past a few thousand files. Borrow only the contiguous whole-file idea for a read-only source and boot bundle. POC storage: Limine module (tar initrd) into a RAM file system, a read-only contiguous source bundle, a separate append-capable store, FAT32 later for host exchange.

10. **Graphics: keep the pipeline shape, drop the covenant.** Keep CPU-only rendering, device contexts, off-screen bitmaps and blits, a per-task `draw_it` callback driven by one compositor task, whole-frame redraw, and game primitives (a collision raster op, an ODE solver). Drop 640x480x16, BIOS modes, the single 8x8 ASCII font and Core0-only windows. Use the Limine framebuffer (32-bit, target 1024x768, software rendering) with damage tracking for text views. A full redraw at 1024x768x32 is 20 to 41 times TempleOS's frame bandwidth (about 90 MiB/s at 30 fps, 180 MiB/s at 60 fps), so measure under QEMU before fixing the rate. Use a permissively licensed Unicode-subset bitmap font. Games and the compositor are outside the POC.
    - Frame rate: local says 60 Hz tick, cloud says measure first. Both choose damage tracking; the M0 measurement sets 30 or 60.

11. **Debugger: keep the philosophy, change the blast radius.** Keep: always resident, entered by hotkey, call or any fault, command language is the REPL language, stack traces are links, registers behave as variables, live editable memory dumps, profiler and heap-leak logger. Change: a TempleOS fault enters single-user mode and a fault on a non-zero core halts it. In Kernel AI a ring-3 fault suspends only that process and attaches a debugger task through a kernel capability (symbolized backtrace with source links, registers, typed structure dumps, `Uf`-style disassembly). Kernel faults go to a panic screen, the serial log and QEMU's gdbstub (TCG advertises unlimited hardware breakpoints; use `hbreak` under KVM).

12. **Boot speed: keep it as a measured metric.** Disputed: how fast TempleOS really boots. Davis claims "two seconds" with no hardware or method stated; forum users report 0.838 s and about 0.5 s in a VM and about 0.4 s in VirtualBox (anecdotes). Resolution: neither is a target. Measure TempleOS, ZealOS and Kernel AI on the same host and set our own target. What carries over: one driver per device class (virtio), no probing beyond that, contiguous images, prebuilt binaries instead of JIT-compiling the system at boot, a fast warm reboot (`BootRAM()`-like) as the fallback when a live reload fails. Drop BIOS-only boot and recompiling the system every boot. Under 2 s to a prompt is plausible with Limine, virtio-only devices and a lazy LLM connection (estimate).

13. **Kernel AI drops the single address space and ring 0 only, for reasons TempleOS's own documents supply and outside evidence confirms.**
    - The Charter justifies no protection partly with "No networking, so malware is not an issue". Kernel AI's LLM sits across a network and its output is untrusted. TempleOS's failure model ("it will crash if you do something wrong. You quickly reboot") contradicts reload without reboot.
    - Language isolation inside one address space cannot keep secrets from untrusted code on current CPUs (Spectre, V8, Meltdown, Site Isolation). The Rust single-address-space OSes (Theseus, RedLeaf) make no security or side-channel claims and trust the compiler; rustc had 141 open soundness issues on 2026-10-14, one since 2015. Singularity kept hardware isolation as defence in depth. Tock splits language isolation (kernel capsules) and hardware isolation (processes).
    - Rings are necessary but not sufficient: on affected CPUs confidentiality also needs split kernel/user page tables and speculation-safe bounds checks. Lay out the kernel address space from M2 so split page tables can be added later (enable before any release that runs untrusted code on real hardware).

14. **Keeping rings costs directness, and design wins part of it back.** Lost: direct CALLs into any kernel function, one global symbol table any task can extend, zero mode or address-map switches (Davis noted the TLB "mostly removes the penalty for using paging"). Added: page-table management, a syscall ABI with pointer validation, CR3 switches of about 100 cycles. Recoverable: map a read-only symbol, source and documentation index into every process (vDSO-style); broad capability handles for the founder's session and minimal ones for LLM-written scripts; generated syscall stubs whose names mirror kernel functions so REPL code can still "call the kernel by name" through a checked boundary. Cost is microseconds natively, well under a millisecond under TCG (estimate: about 10 kernel calls per statement).

15. **ZealOS is the best living reference for the user experience and for the move to Limine and a framebuffer, and a warning about security.** Limine/UEFI boot with a ZealBooter prekernel, a variable-resolution framebuffer, 60 fps, a TCP/IP stack with E1000, PCNet, RTL8139 and a legacy virtio-net driver. It still keeps ring 0 and "full access to everything", while adding networking, an open OpenAI chat client PR (sanitization requested in review) and a draft TLS 1.3 PR. Last `master` commit is 2025-11-10 (verified through the GitHub API; one cloud memo's 2025-11-09 is wrong); new PRs were opened as late as 2026-09-14. TinkerOS (5.22, 2026-10-12) is the most active fork but needs legacy BIOS boot and stays close to TempleOS. None changed the ring-0 model.

16. **Reimplement ideas in Rust; copy no TempleOS code or assets.** "Public domain" rests on informal statements (the Charter, Credits, a community maintainer) and the mirror has no LICENSE file; the Credits list third-party material, including a font taken "without permission". ZealOS, TinkerOS and Shrine carry the Unlicense but derive from the same tree. The code cannot be built outside TempleOS anyway, so an ideas-only policy costs little and keeps "open source now, commercial later" clean.

17. **Governance: adopt a soft code budget and a speed metric; reject the hard cap, "no hooks" and the blanket third-party ban.** TempleOS caps itself at 100,000 lines "for all time" (81,494 shown in the Charter, 82,150 in the Welcome text, 82,100 and 82,207 in the two passes' own counts), bans third-party libraries, and settles governance by how fast the compiler compiles itself and the kernel. ZealOS shows how the cap pinches (98,756 in its Charter, 99,737 in `Define.ZC`, 97,276 in the local count that excludes its network code). Kernel AI's pluggable policy hooks contradict "no hooks" and the kernel plan depends on vetted crates. Budget first-party kernel lines and track boot-to-prompt and build time in CI.

18. **Leave the oracle behind.** The F7 "oracle" picks random words from a vocabulary or the bundled Bible using input-timing entropy; it reflects the author's devotional use and is out of scope. RDRAND/RDSEED feeding a CSPRNG supersedes its one technical idea.

## Decisions

| Decision | Status | Default or choice |
|---|---|---|
| Boot path | Decided (founder) | Limine, UEFI |
| Privilege model | Decided (founder) | Rings, per-process address spaces |
| REPL language and placement | Decided (founder) | Rhai in ring 3 under a restarting supervisor |
| POC shell | Decided (founder) | Own framebuffer terminal |
| Games | Decided (founder) | Multi-year goal outside the POC; compositor, sprites and game helpers are post-POC |
| Hot-swap mechanism | Open | Per-symbol slots for REPL definitions, supervisor swap for components, rebuild and reboot for the kernel |
| Source file format | Open | Plain UTF-8 with sidecar metadata for links, images and sprites |
| Terminal and document model | Open | Structured node tree with plain-text projection ("DolDoc-lite": colour, links, collapsible blocks; no sprites or macros at first) |
| Click-to-run links | Open | No executable links; any exception goes through show-confirm-run in a fresh process |
| HolyC behaviours the REPL imitates | Open | Ergonomics only (no `main`, paren-less calls via sugar, default arguments, implicit print, `ans`); no source compatibility; compile-time evaluation in founder-typed code only |
| Where the Adam role lives | Open | Privileged ring-3 supervisor and system service holding the registry and job queue; one process in the POC |
| Founder's shell privilege | Open | Broad handles for the founder's session, minimal handles for LLM-written scripts; revisit before any public release |
| Symbol scope | Open | Task, parent, system chain over a system registry; promotion needs a capability |
| POC storage | Open | Limine-module tar initrd plus RAM file system, read-only contiguous source bundle, separate append-capable store; FAT32 later |
| Framebuffer mode and redraw | Open | Limine framebuffer, 32-bit, target 1024x768, software rendering, damage tracking for text; 30 or 60 Hz tick set by the M0 measurement |
| Font and Unicode | Open | Bitmap font with a Unicode subset (Latin, punctuation, box drawing), replacement glyph, permissive licence |
| Debugger scope | Open | Per-process debugger for ring-3 faults; panic screen, serial and gdbstub for the kernel; no interactive in-kernel console |
| Code budget | Open | Soft budget on first-party kernel lines, reported in CI, with a dependency allowlist |
| Code reuse policy | Open | Ideas only, clean-room Rust; acknowledgements file; no copied fonts, art or data tables (regenerate opcode tables from vendor manuals) |
| Boot-speed target | Open | Record boot-to-prompt from M0; set numeric targets per accelerator after baselines |
| Speculation hardening | Open | Lay out for split kernel/user page tables from M2; enable after the POC, before untrusted code on real hardware |

Superseded by founder decision: custom boot loaders (TempleOS) as an alternative to Limine, compiler or REPL in the kernel, ring-0 live editing, a hard 100K-line cap as a rule.

**Order of work** (effort in weeks, cloud estimates for a founder who knows Rust but has not written a kernel).
1. **M0/M1.** Framebuffer terminal on a small rich-text model, 2-3 weeks over a plain text terminal. Log boot-to-prompt time from the first boot. Fault screen prints every address as a source link once the host build produces the symbol index; `man`, `edit-at`, `fix` commands, about 1 week after the index exists (terminal commands land at M6).
2. **M6/M7.** Ship the source bundle as a read-only contiguous image (about 1 week).
3. **M7.** The Adam-role service becomes the first privileged ring-3 process (1-2 weeks) and attaches the debugger to a faulting ring-3 process (3-5 weeks for the per-process debugger).
4. **After the POC.** Compositor with per-task draw callbacks (1-2 weeks), sprites in sidecar files, collision and ODE helpers for games.

## Not possible or not viable

- TempleOS or HolyC programs cannot run unmodified in ring 3: they CALL kernel functions directly, wrap critical sections in `PUSHFD`/`CLI`, and use raw port I/O. In 64-bit mode `CLI` raises #GP(0) when CPL exceeds IOPL, and `IN` does when CPL exceeds IOPL and the TSS bit blocks the port (secondary, unofficial extraction of the Intel SDM; primary text not checked).
- "Full access to everything" cannot coexist with rings.
- TempleOS source cannot be reused as code through a Rust or host toolchain. Even ZealOS builds itself only by booting itself in QEMU.
- TempleOS's boot path and VGA initialisation (BIOS INT 10h before long mode) cannot be reused under Limine/UEFI. ZealOS needed a separate prekernel and removed all legacy VGA code.
- An AI scheduling policy cannot be layered onto the TempleOS or ZealOS scheduler.
- A RedSea file cannot grow in place; appending rewrites the whole file or needs preallocation.
- Page-level reclaim and swap policies cannot be expressed in the TempleOS memory model.
- Rust language isolation in one address space cannot keep untrusted code (including LLM-written code) from reading other components' secrets on current x86 CPUs.
- Rings alone do not guarantee kernel-memory confidentiality on every x86 CPU.
- DolDoc live data widgets (DA, HX, AD links) cannot reach another process's memory without a debug capability.

### 3. HolyC and the compile-and-run terminal

- Rules: no-arg calls without parentheses, default args anywhere, strings go to `Print()`, no `main()`. No `#define` functions, no `typedef`, no type-checking, no `continue`, `lock{}` "a little shoddy", stack does not grow. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/HolyC.DD. `#exe{}` inserts text into the stream being compiled (used in https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KStart16.HC to emit the `INT 0x10` that enables VGA and to stamp the compile time). `Kernel/KStart16.HC`
- JIT versus AOT: JIT "places code and data in memory alloced from the heap"; "Do not use AOT, use JIT compiling."; "There is no way to unload except by killing the task." https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD
- `ExeCmdLine()` calls `LexStmt2Bin()` then `Call(machine_code)`; `ExeFile()` wraps a file name in `#include`. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KTask.HC, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/CMain.HC. "TempleOS compiles, doesn't interpret, and uses no byte code anywhere"; IR viewable with `PassTrace()`, assembly with `Trace()`, `U()`, `Uf()`. `Doc/FAQ.DD`
- Compiler lives in `Compiler/` (18,634 lines in the local count) with stages lexer, parser, optimizer passes, `BackA/B/C/FA/FB.HC` back end, `Asm.HC` and `UAsm.HC`; https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/StartOS.HC includes `/Adam/MakeAdam.HC`, so the 38.6K-line Adam layer is JIT-compiled every boot. Detailed compiler mechanics are in compiler-in-terminal.md.

### 4. Symbol tables, reload and Adam

- "All tasks have a heap and a sym table"; lookup falls back to the parent; "The father of all tasks has the API syms you'll need"; "No need for namespaces". `Doc/Strategy.DD`. Each task's table is `CTask.hash_table`; newer entries shadow older; map files add source-line data. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KernelA.HH, `Doc/Hash.DD`, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KHashA.HC
- Reload by shadowing: older symbols are overshadowed, duplicates allowed to re-`#include` while developing; "If you #include a file twice, it allocs more mem for it." https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/ScopingLinkage.DD, `Doc/FAQ.DD`
- "If you change code in the /Adam or your /Home directory ... you just need to reboot"; a syntax error in a start-up file makes the partition unbootable. `Doc/FAQ.DD`, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Tips.DD
- "Adam is immortal." After start-up it accepts requests; `Adam("")` compiles and runs text; `#include` sent there creates system-wide immortal code and data; "His memory is like kernel memory". `Doc/Glossary.DD`, `Doc/MemOverview.DD`. `KMain.HC` sets `adam_task=Fs`, loads the Compiler and runs `ExeFile("StartOS")`; https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Adam/MakeAdam.HC includes graphics, window manager, debugger, DolDoc and AutoComplete. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KMain.HC, `StartOS.HC`, `Adam/MakeAdam.HC`. Job types: `JOBT_TEXT_INPUT`, `JOBT_MSG`, `JOBT_EXE_STR`, `JOBT_CALL`, `JOBT_SPAWN_TASK`. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Job.HC, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Job.DD. Each core also has an immortal Seth task.
- A call to a defined function compiles to `IC_CALL tmpf->exe_addr` (a fixed address); only extern-declared functions are called through `&tmpf->exe_addr` (https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/PrsExp.HC), so only those see a redefinition.
- ZealOS: Adam became Zenith then "System Task" (07/01/21); `Sys("")` compiles and runs text; Executive replaces Seth. https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Doc/ChangeLog.DD and https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Doc/Glossary.DD

### 5. DolDoc and one-click source

- Commands are two characters plus flags and args: TX text, LK link, BT button, DA data, CB check box, LS list, MA macro, HX hex edit, TR tree, SP sprite, IB insert binary, SO song. Links: `FI:` file, `FF:` find text in file, `FL:` file and line, `FA:` anchor, `MN:` manual or symbol source, `HI:` help index, `AD:` address, `BF:` Bible verse. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/DolDocOverview.DD
- "A DolDoc in memory is a Circular Queue of cmds and graphics"; used for the editor, viewer, browser and command line; source and the command line "can have graphics, links, icons, trees, colors". https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/DolDoc.DD, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Features.DD. Implementation: 26 files, 10,204 lines in `Adam/DolDoc/` (`DocInit.HC`, `DocEd.HC`, `DocTerm.HC`, `DocForm()` from class `format` metadata); https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Boot.DD embeds its boot diagram as a sprite.
- Not plain text: binary sprite data after the NUL, cursor as ASCII 5, `$` is an escape. `Doc/FAQ.DD`, `Doc/HolyC.DD`. ZealOS needs a `sync` script to get changes out of the VM. https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/README.md
- Clicking can run code: `LM=""` sends text on left click; `+LIS` sends to `InStr()` which runs code; a PopUp flag on `MA` runs in a new task; the FAQ has a "Click Here" macro; data widgets use raw `->data` addresses. `Doc/DolDocOverview.DD`, `Doc/FAQ.DD`
- Source links: `SrcEdLink()` builds `FL:%s,%d`; `PutSrcLink()` prints it; `Man()` opens a symbol's `src_link`; export symbols and processed map files supply the source links. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/FunSeg.HC, `Doc/FAQ.DD`. `%p` prints a pointer as FunSeg+Offset, `%P` as a link; `CallerRep` prints frames with `%P`; AutoComplete's CTRL-SHIFT-F1 jumps to source. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/DbgFunSeg.DD, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KDbg.HC, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/AutoComplete.DD

### 6. Tasks, scheduler and multicore

- Round-robin; "Tasks can be switched in half a microsecond" (author's claim, no hardware or method); "A task runs until it voluntarily yields"; tasks waiting on I/O poll and yield, "pegs the CPU Load"; "Tasks have no priority". https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Sched.HC, `Doc/Welcome.DD`. "It is not preemptiove"; the timer handler returns to the interrupted task (cloud reading of the assembly). `Doc/Strategy.DD`, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KInts.HC
- "master-slave multicore instead of SMP", jobs assigned with `JobQue()`/`JobResGet()`, "does not move tasks between cores", "Only tasks on Core0 can have windows". https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MultiCore.DD. "There is no distinction between task, process or thread." `Doc/Glossary.DD`
- ZealOS keeps the model ("non-preemptive multi-tasking, ring-0-only, single-address_mapped"). https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Kernel/Sched.ZC, https://zeal-operating-system.github.io/Doc/MultiCore.DD.html, https://zeal-operating-system.github.io/Doc/Strategy.DD.html, https://zeal-operating-system.github.io/Doc/Welcome.DD.html (docs site last modified 2023-10-21)

### 7. Memory model

- "All tasks on all cores use the same page table map ... 2Meg or 1Gig page table entries ... Nothing swaps to disk." Terry first unmapped the first 4K for NULL faults, then after the 2016 uncached-alias change stopped; memory fragments over a long session. `Doc/MemOverview.DD`. "The stk does not grow because virtual mem is not used." "Generally, the last write wins." https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Quirks.DD
- Memory map: kernel module `0x7C00`-`0x36AEF` (192,239 bytes), code heap `0x10F000`-`0x7FFFFFFF`. `Doc/MemOverview.DD`

### 8. RedSea and storage

- RedSea: 64-bit, like FAT32 but with absolute block addresses, fixed 64-byte directory entries (38-character names), an allocation bitmap and no FAT; files contiguous, cannot grow; no bad-block table or redundant allocation table; partition typed as FAT32 "to fool BIOS". 635 lines in https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/BlkDev/FileSysRedSea.HC. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/RedSea.DD
- `RedSeaAllocClus` picks the smallest free run and throws `'Drv'` if none fits; `RedSeaFileWrite` deletes the old file, allocates contiguously, writes, then creates the directory entry. `Kernel/BlkDev/FileSysRedSea.HC`
- "I am intentionally crippling this operating system, making it a toy with the wisdom that this will prevent commercialization and corruption." Random access needs a size declared at `FOpen()`. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/BlkChain.DD
- "Do not have more than a few thousand files or the file manager will not function"; keep the drive to about 100 MB. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Reliability.DD. FAT32 (959 lines in `Kernel/BlkDev/FileSysFAT.HC`) exists for dual-boot exchange and skips short-name aliases. `Doc/CutCorners.DD`, `Doc/Quirks.DD`. Whole-file load makes `.Z` LZW compression easy (`Kernel/Compress.HC`). Storage is ATA PIO, no interrupts, PS/2 instead of USB. `Doc/Features.DD`, `Doc/Glossary.DD`, `Doc/Strategy.DD`
- CD/DVD uses RedSea on El Torito (`Adam/Opt/Boot/DskISORedSea.HC`, `BootDVD.HC`); ZealOS added ISO9660 in 1.13 (2022-04-16).

### 9. Graphics

- `KernelA.HH`: `WINMGR_FPS (30000.0/1001)`, `GR_WIDTH 640`, `GR_HEIGHT 480`, `COLORS_NUM 16`; `KStart16.HC` sets mode `AX=0x4F02, BX=0x12` through `INT 0x10`. VGA 4-bit planar plus an 8x8 font. `Kernel/KernelA.HH`, `Kernel/KStart16.HC`
- The window manager calls `GrUpdateScrn()` and per-task `draw_it()` at 30 fps; one window per task, Core0 only; "draw everything in the window over and over again"; `DCAlias()`, `DCNew()` and `GrBlot()`; `ROP_COLLISION` counts pixels drawn on non-background; `ODENew()` is an ODE solver. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/GraphicsOverview.DD. Text and graphics are composited in software over `gr.dc`; `GrUpdateVGAGraphics()` writes the four planes skipping unchanged bytes against `gr.scrn_image`, so it is a composited redraw, not a literal single buffer (local reading). `Adam/Gr/GrScrn.HC`. The graphics library is 13,393 lines in `Adam/Gr/`.
- "Updates whole scrn at 30 fps, optimized for full scrn games where InvalidRectangles are counter-productive"; 30 fps is not synchronized to hardware; "A 1600x1200x24 bit scrn takes 37 times more memory". `Doc/Strategy.DD`, `Doc/FAQ.DD`, `Doc/Welcome.DD`. Graphics "should be transparent, not hidden in a GPU" (Charter).
- Sprites are drawn with CTRL-r and live in source; `$IB,"",BI=1$` inserts the address of sprite data. `Doc/GraphicsOverview.DD`, `Doc/FAQ.DD`
- ZealOS: 32-bit modes set since 02/19/20 but the library stays 4-bit internally; 2.00 (11/02/22) removed legacy VGA, added framebuffer fields and always looks for a 1024x768 VBE mode; MiniGrLib rewritten for 32-bit framebuffer (03/17/23); master has `WINMGR_FPS (60000.0 / 1001)` and `COLORS_NUM 16` with 24-bit palette entries; true colour only in open PR 189 "Graphics api overhaul" (2026-07-18). https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Doc/ChangeLog.DD, https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Kernel/KernelA.HH and https://github.com/Zeal-Operating-System/ZealOS/pull/189. TinkerOS: 32-bit linear framebuffer, mostly 16 colours. https://raw.githubusercontent.com/tinkeros/TinkerOS/main/README.md
- Legacy VGA modes are disappearing from newer firmware (TinkerOS README).

### 10. Debugger

- `Dbg()` or CTRL-ALT-d enters it, also on a fault; `G()`/`G2()` continue; `U()`/`Uf()` disassemble; `D()`, `DocD()` (live, editable), `Dm()` dump memory; registers via `_RAX`, `_RBX`; `ClassRep()`, `Prof()`/`ProfRep()`, `HeapLog()`. https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/DbgOverview.DD. `B` breakpoints, `S` single step, `Dr` registers. `Adam/ADbg.HC` (270 lines), `Kernel/KDbg.HC` (652), `Compiler/UAsm.HC` (682); `Uf` at `Adam/ADbg.HC` line 254 (local count).
- `Fault2()` calls `SingleUser(ON)`, prints task, fault number, RIP, RSP and CR2; `Fault3()` on a non-zero core sends `I_MP_CRASH` to Core0 and halts; on Core0 prints "TempleOS Debugger", beeps and enters `Dbg2()`. `DbgHelp` lists `Man("Print")`, `E(_RIP)`, `Fix`. Uses `PUSHFD`/`CLI` pairs. `Kernel/KDbg.HC`. ZealOS wiki keeps the same commands. https://zeal-operating-system.github.io/ZealOS-wiki/Debugging

### 11. Boot path and speed

- "booting takes only two seconds" (no hardware or method). `Doc/Welcome.DD`. `HomeSys.HC` prints "Boot Time"; users report 0.838 s and about 0.5 s in a VM (https://trisquel.info/gl/forum/running-temple-os, posts 2021-10-20) and about 0.4 s in VirtualBox (archiveos.org TempleOS-EE page, one anecdote).
- BIOS only ("UEFI is pointless"); boot records are patched with LBAs; `Kernel.BIN.C` loads `Compiler.BIN`, which compiles `StartOS.HC` into Adam's memory; `BootRAM()` does a fast reboot. `Doc/Boot.DD`, https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/WhyNotMore.DD. Speed sources claimed: never switches privilege levels or address maps, loads whole contiguous files. `Doc/Welcome.DD`, `Doc/Features.DD`
- No PCI drivers; ISA-bus I/O ports; IRQ0 timer, IRQ1 keyboard, IRQ12 mouse; expects VMware, QEMU or VirtualBox. `Doc/WhyNotMore.DD`

### 13. Why one address space is not enough

- "we now believe that speculative vulnerabilities on today's hardware defeat all language-enforced confidentiality" (McIlroy et al.). https://arxiv.org/abs/1902.05178. V8: "The only effective mitigation is to move sensitive data out of the process's address space"; some variants "simply infeasible in software". https://v8.dev/blog/spectre. Spectre breaks OS process separation. https://arxiv.org/abs/1801.01203. Meltdown breaks address space isolation; KAISER impeded it. https://www.usenix.org/conference/usenixsecurity18/presentation/lipp. Site Isolation: boundaries "must fundamentally be preserved by the OS and hardware", 9-13% memory overhead. https://www.usenix.org/system/files/sec19-reis.pdf
- Linux PTI: "Moves to CR3 are on the order of a hundred cycles"; without PCID each CR3 write flushes the TLB; losing global pages costs under 1%. https://docs.kernel.org/arch/x86/pti.html. `array_index_nospec`. https://docs.kernel.org/staging/speculation.html
- Theseus "must trust the Rust compiler"; "we do not make claims about ... efficiency or security". https://www.usenix.org/system/files/osdi20-boos.pdf (project: https://github.com/theseus-os/Theseus). Theseus book: "Isolation should be the responsibility of software alone". https://www.theseus-os.com/Theseus/book/design/idea.html. RedLeaf trusts the compiler and "do[es] not protect against sidechannel attacks". https://www.usenix.org/system/files/osdi20-narayanan_vikram.pdf. Singularity: "hardware isolation remains valuable as a defense-in-depth". https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/osr2007_rethinkingsoftwarestack.pdf
- rust-lang/rust had 141 open `I-unsound` issues on 2026-10-14; #25860 open since 2015-05-28. https://github.com/rust-lang/rust/issues?q=is%3Aissue%20state%3Aopen%20label%3AI-unsound and https://github.com/rust-lang/rust/issues/25860. Safe Rust trusts the unsafe Rust beneath it. https://doc.rust-lang.org/nomicon/safe-unsafe-meaning.html. Tock: hardware isolation for processes, language isolation for capsules, no side-channel mitigations promised. https://book.tockos.org/doc/threat_model/threat_model
- OWASP LLM05 and LLM01: treat model output as untrusted; no fool-proof prompt-injection prevention. https://genai.owasp.org/llmrisk/llm052025-improper-output-handling/ and https://genai.owasp.org/llmrisk/llm01-prompt-injection/

### 16. Estimates and analysis

- **Frame bandwidth.** TempleOS frame: 640x480x4 bit is 153,600 bytes, about 4.6 MB/s at 30 fps. A 1024x768x32 frame is 3 MiB (20.5 times larger): about 90 MiB/s at 30 fps, 180 MiB/s at 60 fps. Full redraw at 1080p is about 500 MB/s (local), too much under QEMU. Damage tracking is the safe default for the terminal; Davis's argument against invalid rectangles is specific to full-screen games. Time cost under TCG is unmeasured.
- **Effort** (founder who knows Rust, not kernels; each assumes the milestone it depends on is done): DolDoc-lite text model 2-3 weeks; links on every printed address plus `man`/`edit-at`/`fix` about 1 week after the index exists; Adam-role service 1-2 weeks after ring 3; per-process debugger 3-5 weeks; compositor with draw callbacks 1-2 weeks; read-only contiguous source bundle about 1 week. TempleOS line counts are an upper bound for comparable scope since Kernel AI drops the sprite editor, macros and songs.
- **RedSea crash window** (inference, untested): a crash between the delete and the directory write loses both versions.
- **Stale callers after re-include** (inference): code compiled before the re-include keeps calling the old body; the compiler and live-edit memos agree on a per-symbol indirection slot.
- **Performance claims.** "Two seconds" to boot and "half a microsecond" per task switch are the author's statements with no hardware or method; ignore as targets until both systems are measured on one host.
- **Ring cost.** About 10 kernel calls per REPL statement; syscall round trip a few hundred cycles natively; assumed 10-50x slowdown under TCG (unverified).

## Open questions

1. **What does full-frame redraw cost under TCG and KVM on this host?** At M0 time a loop that fills and copies a 1024x768x32 frame 600 times at `-smp 1` and `-smp 4`, logging ms per frame to serial. Decides redraw strategy and the 30 or 60 Hz tick.
2. **What is boot-to-prompt time for Kernel AI, TempleOS and ZealOS on the same host?** Boot `TempleOS.ISO` and a ZealOS ISO, then the M0 image, timing each from QEMU start to first prompt with a serial marker. Repeat under TCG. Tests whether "two seconds" is a useful benchmark at all.
3. **How expensive are a syscall round trip and a CR3 switch under TCG and KVM?** Decides whether the vDSO-style read-only index mapping is needed in the POC. Measure a null syscall loop and a CR3 reload loop at M7.
4. **What share of LLM output for REPL and system-control prompts is outside Extended ASCII?** Decides font coverage. Run the benchmark prompts from the compiler memo and count code points above U+00FF.
5. **Can a sidecar format for links, images and sprites survive git merges and LLM edits?** Prototype one sidecar per source file keyed by symbol name, run 20 LLM-made edits and 5 merges, count broken anchors.
6. **Are live data widgets (DA, HX) worth building across address spaces?** Decide after the per-process debugger exists; if its memory view suffices, drop document-level widgets.
7. **Which parts of the Adam role belong in the system service and which in the swap supervisor?** Default: one ring-3 supervisor in the POC, split later if shared fate hurts.
8. **Will a TempleOS descendant add any protection once it ships HTTPS and USB?** Watch ZealOS PRs 188, 189, 190, 200 and its Charter every few months.
9. **Is TempleOS's half-microsecond task switch a meaningful comparison for a switch with a CR3 change?** Measure our switch with and without CR3 at M7, and `Yield()` in TempleOS under the same QEMU configuration (no code copied).
10. **Is the TempleOS public-domain statement legally effective where dedication is not recognised?** Matters only if code or assets are ever copied; under the ideas-only policy it does not arise.
11. **Which Unicode font** covers LLM output and permits commercial use? (`noto-sans-mono-bitmap` is a candidate in the foundation memo.)
12. **Where does canonical source live:** the VM with a sync script (ZealOS model), the host git repo (default), or the Mac mini?
13. **Write a network stack or adopt `smoltcp`, and how does it count against the budget?** What does the budget count: vendored crates, generated code, the REPL engine?
14. **How much kernel state can ring 3 read without weakening ASLR** if Kernel AI uses read-only introspection?
15. **Should JIT-compiled REPL code run inside the shell process or in a separate process per session?** Default: one fresh process per script (compiler memo).
16. **Should x86 opcode tables be regenerated from vendor manuals rather than transcribed?** Relevant only if a native backend is built.
