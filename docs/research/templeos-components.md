# TempleOS components: what to keep, what to leave behind

- **Date:** 2026-10-14
- **Status:** Research memo (no code)
- **Scope:** Which parts of TempleOS (HolyC, DolDoc, the Adam task, the RedSea file system, the graphics model, the debugger and boot speed) Kernel AI should carry forward as ideas, which it must leave behind, and why Kernel AI drops TempleOS's single address space and ring-0-only model, based on the TempleOS V5.03 source and the ZealOS fork.
- **Related memos:** [rust-kernel-foundation.md](./rust-kernel-foundation.md), [compiler-in-terminal.md](./compiler-in-terminal.md), [live-editable-system.md](./live-editable-system.md), [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md)

A note on sources: every TempleOS citation points to the `archive` branch of the unofficial `cia-foundation/TempleOS` mirror. That branch is a V5.03 snapshot (V5.03 was released on 2017-03-14 [E2]) whose last nightly import was authored on 2017-11-21 [E1]. `templeos.org` is now maintained by a community archivist, not by the author [E3]. Nothing recommended here depends on copying TempleOS code.

## Conclusions

1. **Take user-experience ideas from TempleOS. Do not take its code or its kernel architecture.** TempleOS source cannot be compiled outside TempleOS [E4]. The kernel is defined by ring 0 only, one identity-mapped address map, cooperative scheduling and no network [E6, E33, E34, E38], and the most active fork, ZealOS, kept all of those properties except the ban on networking [E37, E64]. What survives the move to privilege rings is the experience: a terminal that compiles and runs what you type, a source link behind every symbol and address, one document model shared by terminal, help, editor and debugger, a debugger that is always resident, a simple CPU-rendered graphics pipeline, and boot speed treated as a design metric.

2. **HolyC: keep the REPL ergonomics. Leave behind the type system, the kernel-call model and the memory assumptions.** The parts that make the terminal pleasant are small and portable. Top-level statements run in order with no `main()`. Zero-argument calls need no parentheses (`Dir;`). Default arguments may sit anywhere in the list. A bare string literal prints. `#exe{}` runs code at compile time [E12, E13]. Each typed statement is compiled to native machine code, with no bytecode, and called at once [E16, E17]. The parts to leave behind are just as clear: no type-checking, no `typedef`, no `continue`, a `lock{}` construct its author calls "a little shoddy", stacks that cannot grow [E14], and application code that CALLs kernel functions directly because no system-call layer exists [E18]. The language itself (Rhai first, a HolyC-flavoured strict subset later) is chosen in [compiler-in-terminal.md](./compiler-in-terminal.md). This memo only fixes which HolyC behaviours that language should imitate.

3. **The most valuable TempleOS feature for Kernel AI is that every symbol, address and stack frame links to its source line.** Source symbols carry a `src_link`, built from export tables and processed map files. `SrcEdLink()` turns any code address into an `FL:file,line` link. Stack traces print with `%P` as clickable links. `Man(sym)`, `E(_RIP)` and `Fix` open the source of a symbol, of the faulting instruction, and of the last compile error. The AutoComplete window jumps to source with CTRL-SHIFT-F1 and its siblings [E31, E32, E53]. ZealOS kept all of it [E54]. This is the "source one click away" decision, already working in a small OS. The mechanism for Kernel AI (a host-built symbol index, DWARF line tables and a source bundle) is specified in [live-editable-system.md](./live-editable-system.md). The TempleOS lesson is about reach: the link must appear everywhere an address or a name is printed, starting with the first fault screen.

4. **DolDoc: keep the single document model and its link vocabulary. Leave behind the on-disk format, click-to-execute macros, and widgets bound to raw memory.** One engine drives the editor, viewer, help browser and command line. Links can target a file, a text match inside a file, a file line, a symbol's source, or a memory address [E27, E28]. Three properties do not fit Kernel AI. First, source files carry binary sprite data after the terminating NUL and store the cursor position as an ASCII 5 byte [E29], which breaks git, diff and LLM ingestion. Second, clicking a macro can compile and run code, including in a new task [E30]. That would bypass the show-confirm-run path that Kernel AI plans for LLM-written code. Third, data and hex-edit widgets bind to raw addresses [E27, E30]. Once address spaces are separate, such a widget cannot reach another process's memory without a kernel or debugger intermediary (analysis A6).

5. **The Adam task: keep the role, not the implementation.** Adam is the immortal parent of all tasks. It holds the global API symbol table, and after boot it serves a job queue whose job types include "compile and run this source text" [E20, E23, E25]. Adam boots the system by JIT-compiling the graphics, window manager, debugger and DolDoc layers into itself [E24]. Code sent to Adam becomes system-wide and immortal, and Adam's heap is in effect kernel memory [E23]. ZealOS renamed it the System task and kept the role unchanged [E26]. In Kernel AI the same role should belong to a privileged ring-3 system service. It owns the symbol and source index and accepts compile-and-run jobs. It runs each job in a fresh process that holds only the capability handles granted to it [E92]. Jobs that originate with the LLM enter the same queue flagged for confirmation, because model output must be treated as untrusted input [E88, E89].

6. **TempleOS reloads code by shadowing the old symbol, leaking the old code, and rebooting for anything loaded at boot. That does not meet Kernel AI's reload-without-reboot decision.** Including a file again allocates new memory and shadows the old symbols [E21]. AOT-loaded code cannot be unloaded except by killing its task [E15]. Changes to `/Adam` or `/Home` take effect only after a reboot, and a syntax error in a start-up file makes the partition unbootable [E22]. Keep the developer experience of re-running a file from the terminal while editing it. Build the replacement, reclamation and rollback mechanism new, as [live-editable-system.md](./live-editable-system.md) specifies.

7. **Leave the TempleOS task and scheduler model behind entirely. None of it can host an AI scheduling policy.** The scheduler is cooperative round-robin with no priorities. A task runs until it calls `Yield()`, and the timer interrupt returns to the interrupted task. Multicore is master/slave with no migration, and only Core0 tasks can own windows [E33-E35]. There is no distinction between process and thread [E36]. ZealOS kept the same model [E37]. Kernel AI needs the preemptive scheduler with a pluggable policy hook planned for M3 and M4 in [rust-kernel-foundation.md](./rust-kernel-foundation.md).

8. **Leave the memory model behind. It is the opposite of what the POC's memory-policy goal needs.** All tasks on all cores share one identity-mapped page table built from 2 MB or 1 GB pages, and nothing swaps [E38]. NULL dereferences no longer fault, and long sessions can fragment memory until a reboot [E39]. Stacks cannot grow [E40]. There are no per-process mappings, no 4 KB pages for a reclaim policy to choose among, and no swap device.

9. **Do not use RedSea as Kernel AI's writable file system. Borrow only the idea of a contiguous, whole-file, read-only image for the source and boot bundle.** RedSea files are contiguous and cannot grow, and the author imposed that limit deliberately, "to prevent commercialization" [E41, E43]. A write deletes the old file, allocates new blocks, writes them, and records the directory entry last. Allocation fails when no single free run is large enough, even if total free space would suffice [E42]. There is no bad-block table, no redundant allocation table and no locking, and the file manager stops working past a few thousand files [E41, E44]. Telemetry logs, LLM transcripts and rollback history all need append. TempleOS lists "load whole contiguous files" as one of its speed sources [E57], and that idea suits a read-only bundle.

10. **Graphics: keep the pipeline shape and drop the "covenant".** Keep CPU-only rendering, device contexts with aliases, off-screen bitmaps and blits, a per-task `draw_it` callback driven by one compositor task at a fixed rate, whole-frame redraw, sprites embedded in documents, and the game-oriented primitives: a raster op that counts collisions, and an ODE solver [E47-E49]. Drop the fixed 640x480 16-colour mode, the BIOS mode set, the single 8x8 font with no Unicode, and the rule that only Core0 tasks get windows [E7, E46, E47]. ZealOS and TinkerOS both moved to 32-bit linear framebuffers, though both still draw mostly with a 16-entry palette [E51, E71]. That framebuffer is the direct analogue of the Limine GOP framebuffer in the foundation memo's M0. Whole-frame redraw at 1024x768 in 32-bit colour moves 20 to 41 times TempleOS's frame bandwidth, depending on frame rate (A3), so measure it under TCG before fixing the frame rate.

11. **Debugger: keep the philosophy and change the blast radius.** Keep these properties: always resident; entered by hotkey, by call or by any fault; the command language is the REPL language; stack traces are links; registers behave as variables; memory dumps update live and can be edited in place; a profiler and a heap-leak logger are built in [E52, E54]. Change what a fault does. A TempleOS fault switches the machine into single-user mode, and a fault on any core other than Core0 halts that core [E53]. In Kernel AI a ring-3 fault should suspend only the faulting process and open a debugger session on it while everything else keeps running. Kernel faults go to a panic screen, the serial log and QEMU's gdbstub, which under TCG advertises unlimited hardware breakpoints and watchpoints [E93].

12. **Boot speed: keep it as a measured metric, along with the techniques that carry over. Drop BIOS-only boot and recompiling the system on every boot.** The "two seconds" boot is the author's own claim, with no stated hardware or method [E55]. It rests on BIOS boot sectors patched with block addresses, one driver per device class, no PCI drivers at all, whole-file loads and a small code base [E45, E50, E56, E57]. Kernel AI boots through Limine on UEFI, so the TempleOS boot path does not apply [E56, E65]. What carries over: one driver per device class (virtio in QEMU), no probing beyond that, contiguous images, prebuilt binaries rather than JIT-compiling the system at boot, and a fast warm reboot like `BootRAM()` as the fallback when a live reload fails [E56].

13. **Kernel AI drops the single address space and the ring-0-only model for reasons TempleOS's own documents supply, and outside evidence confirms them.** The Charter justifies having no protection partly by having no network: "No networking, so malware is not an issue" [E6]. Kernel AI's LLM sits across a network, and its output must be treated as untrusted [E88, E89]. TempleOS's failure model is "it will crash if you do something wrong. You quickly reboot" [E10], which contradicts reload without reboot. Inside one address space, language-based isolation cannot keep secrets from untrusted code on current CPUs [E73, E74]. The Rust single-address-space research OSes make no security or side-channel claims and depend on the compiler having no soundness holes [E80, E82]. On 2026-10-14, rustc had 141 open soundness issues, one of them open since 2015 [E84, E85]. Even Singularity's designers, who built an OS on software isolation, kept hardware isolation as defence in depth [E83]. The Site Isolation authors state the general rule: process and user/kernel boundaries "must fundamentally be preserved by the OS and hardware and cannot be left to applications to enforce" [E77]. Theseus, the closest Rust precedent for live evolution, gets its single address space by assuming the opposite [E81], and safe Rust is only as sound as the unsafe code beneath it [E86]. Rings are necessary but not sufficient: on affected CPUs, confidentiality also needs split kernel/user page tables and speculation-safe bounds checks [E75, E76, E78, E79].

14. **Keeping rings costs TempleOS's directness, and design can win part of it back.** Lost: direct CALLs from any program into any kernel function [E18], one global symbol table that any task can extend by sending code to Adam [E20, E23], and zero mode or address-map switches [E57]. Terry himself noted that the TLB "mostly removes the penalty for using paging" [E11]. Added cost: page-table management, a syscall ABI with pointer validation, and CR3 switches of about a hundred cycles each on native hardware [E78]. Recoverable: map a read-only symbol, source and documentation index into every process, vDSO-style, so autocomplete and jump-to-source need no syscalls [E91]; give the founder's system shell broad capability handles while LLM-written scripts get minimal ones [E92]; and generate syscall stubs whose names mirror kernel functions, so REPL code can still "call the kernel by name" through a checked boundary (A4). Tock is a working Rust precedent for this split: language isolation for trusted kernel components, hardware isolation for processes [E87].

15. **ZealOS is the right living reference for the user experience and for the move to Limine and a framebuffer. It is also a warning about security.** It describes itself as a modernized TempleOS fork [E60], and its ZealC language is HolyC with fixes and additions [E19]. It is released under the Unlicense [E61]. It boots through Limine with its ZealBooter prekernel and a framebuffer [E65, E67], documents QEMU on Windows with WHPX [E68], and has a small TCP/IP stack with a legacy-interface virtio-net driver [E66]. It still keeps ring 0 and "full access to everything" [E64], even as it adds networking, an open PR for an OpenAI chat client and a draft PR for TLS 1.3 [E66, E69, E70]. Master has had no commits since 2025-11-10, but new pull requests were opened as late as 2026-09-14 [E62, E63]. TinkerOS is actively released but needs legacy BIOS boot, and Shrine is archived [E71, E72]. None of them changed the ring-0 model, so none offers a protected design to borrow.

16. **Reimplement ideas in Rust and copy no TempleOS code or assets.** TempleOS's "public domain" status rests on informal statements by the author and by a community maintainer, and the mirror has no LICENSE file [E3, E5]. The Credits list third-party material, including a font taken "without permission" [E5]. ZealOS carries a formal Unlicense [E61] but derives from the same tree. Because the code cannot be compiled outside TempleOS anyway [E4], an ideas-only policy costs Kernel AI little and keeps the "open source now, commercial later" path clean.

17. **Governance: adopt a soft code budget and a speed metric. Reject "no hooks for future changes" and the blanket third-party ban.** TempleOS caps itself at 100,000 lines for all time, bans third-party libraries, and settles every governance question by how fast the compiler compiles itself and the kernel [E8, E9]. ZealOS already sits at roughly 99,000 of its 100,000 lines after adding networking [E64]. Kernel AI's pluggable scheduler and reclaim hooks contradict "no hooks", and the foundation memo depends on vetted crates. A budget on first-party kernel lines plus boot-to-prompt and build-time metrics tracked in CI keeps the TempleOS discipline without its rules.

### Recommendation

Adopt the keep/leave map below as the project's position on TempleOS. Where a row says "specified in", that memo owns the mechanism and this memo only fixes the TempleOS-derived requirement.

Order of work, aligned with the foundation memo's milestone ladder (effort figures are estimates; see A5):

1. **With M0 (boot and harness).** Build the framebuffer terminal on a small rich-text model ("DolDoc-lite": text runs with colour, links and collapsible blocks; no sprites, no macros). Log boot-to-prompt time from the first boot. About 2 to 3 weeks on top of a plain text terminal.
2. **With M1 (CPU structures and memory).** The fault screen prints every address as a source link once the host build produces the symbol index. Add `man`, `edit-at` and `fix` commands to the terminal. About 1 week after the index exists.
3. **With M3 (preemptive scheduler and ring 3).** The Adam-role system service becomes the first privileged ring-3 process. It holds the compile-and-run job queue and attaches the debugger to a faulting ring-3 process. About 1 to 2 weeks for the service and 3 to 5 weeks for the per-process debugger.
4. **With M5 (first virtio drivers).** Ship the source bundle as a read-only contiguous image on virtio-blk, and keep writable data in a separate store. About 1 week.
5. **After the POC.** Add a compositor with per-task draw callbacks, sprites kept in sidecar files, and the collision and ODE helpers for games.

### Not possible / not viable

- **TempleOS or HolyC programs cannot run unmodified in ring 3 under Kernel AI.** They call kernel functions directly with CALL REL32 because no syscall layer exists [E18]. TempleOS code, including the debugger, wraps critical sections in PUSHFD/CLI [E53], and its drivers use raw port I/O [E50]. In 64-bit mode, CLI raises #GP(0) when CPL is greater than IOPL, and IN raises #GP(0) when CPL is greater than IOPL and the TSS I/O-permission bit for the port is set [E90]. Running such code in ring 3 requires a rewrite or an emulation layer.
- **The Charter's "full access to everything" cannot coexist with Kernel AI's privilege rings.** The Charter requires that all memory, I/O ports and instructions are never off limits and that every kernel function can be called [E6]. Rings exist to forbid exactly that from ring 3. The two are contradictory by definition.
- **TempleOS source cannot be reused as code through a Rust or host toolchain.** It is HolyC plus TempleOS assembly and "cannot be compiled outside TempleOS" [E4]. Its files are DolDoc documents with binary data after the NUL [E29]. Even ZealOS builds itself only by booting itself in QEMU [E67]. Only ideas transfer, or code must be hand-ported.
- **TempleOS's boot path and graphics initialisation cannot be reused in a Limine/UEFI kernel.** TempleOS supports only legacy BIOS boot with boot records patched with block addresses [E56], and it sets 640x480x16 through a BIOS INT 10h call in real mode before entering long mode [E46]. ZealOS needed a separate prekernel and removed all legacy VGA code to boot from Limine with a framebuffer [E65].
- **An AI scheduling policy cannot be layered onto the TempleOS or ZealOS scheduler.** A task runs until it calls `Yield()`, the timer interrupt returns to the interrupted task, there are no priorities, and tasks never move between cores [E33-E35, E37]. A task that never yields cannot be descheduled, so there is no decision point for a policy to act on.
- **A RedSea file cannot grow in place.** RedSea has only an allocation bitmap, files are contiguous, and size is fixed at creation [E41, E43]. Appending means rewriting the whole file through delete-allocate-write [E42], or preallocating a fixed-size file.
- **The TempleOS code model cannot reload code and reclaim the old version's memory.** AOT code unloads only when its task dies [E15]. Including a file again allocates new memory every time [E21]. Boot-level code needs a reboot [E22].
- **Page-level reclaim and swap policies, a POC goal, cannot be expressed in the TempleOS memory model.** It uses one identity-mapped page table with 2 MB or 1 GB pages, and "Nothing swaps to disk" [E38].
- **Rust language isolation inside one address space cannot keep untrusted code (including LLM-written code) from reading other components' secrets on current x86 CPUs.** Untrusted code can build a universal read gadget over its whole address space, and no comprehensive software mitigation exists; some Spectre variants could not be mitigated in software at all [E73, E74]. Theseus and RedLeaf make no security or side-channel claims [E80, E82].
- **Privilege rings alone do not guarantee kernel-memory confidentiality on every x86 CPU.** Meltdown read kernel memory from user mode despite rings and page-table protection on affected CPUs, and Spectre breaks OS process separation [E75, E76]. Affected CPUs need split page tables and speculation-safe index handling as well [E78, E79].

### Decisions the founder must make

### The Charter: what TempleOS optimizes for

- [E6] The Charter: "Ring-0-only. Everything runs in kernel mode, including user applications." "Full access to everything. All memory, I/O ports, instructions, and similar things must never be off limits. All functions, variables and class members will be accessible." "Single-address-map as though paging is not used. Long mode requires paging, however, so the nearest thing is keeping all memory identity-mapped." "No networking, so malware is not an issue." "No encryption or passwords. Files are compressed, not encrypted." — [Doc/Charter.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Charter.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E7] The Charter calls 640x480 16-colour graphics "a covenant" and says "even if one GPU were universal, we would still keep 640x480 16 color and not use GPU acceleration." It allows "Just one 8x8 fixed-width font. No Unicode, just Extended ASCII." — [Doc/Charter.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Charter.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E8] The Charter sets "a limit of 100,000 lines of code for all time, not including applications and demos. Code comments count", shows "Currently, there are 81,494 lines of code", and says "3rd party libraries are banned because they circumvent the intent of this limit." — [Doc/Charter.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Charter.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E9] The Charter: "The metric for resolving all TempleOS code governance issues is how fast the compiler compiles itself and the kernel with BootHDIns()." and "We do not put any hooks for future changes." — [Doc/Charter.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Charter.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E10] The failure model is crash and reboot. Welcome: "It's a kayak, not a Titanic -- it will crash if you do something wrong. You quickly reboot, however." Strategy: "TempleOS is a motorcycle -- if you lean-over too far, a motorcycle will crash." and "DOS and C64 had no memory protections and ran in ring-0, with no security. This saves an order of magnitude complexity." — [Doc/Welcome.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Welcome.DD); [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E11] Terry's own history of the memory design: "In 2003, I wanted to make a no-paging ring-0-only 64-bit operating system for super speed with simplicity and full access", while noting that "the CPU's translation look-aside buffer mostly removes the penalty for using paging." — [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)

### HolyC and the compile-and-run terminal

- [E12] HolyC REPL-friendly rules: "Function with no args, or just default args can be called without parentheses" (example `Dir;`); "Default args don't have to be on the end"; "A string with or without args is sent to Print()"; "There is no main() function. Any code outside of functions gets executed upon start-up, in order." — [Doc/HolyC.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/HolyC.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E13] "With the #exe{} feature in your src code, you can place programs that insert text into the stream of code being compiled." The kernel uses it in `Kernel/KStart16.HC`, where an `#exe` block decides at compile time whether to emit the `INT 0x10` that enables VGA, and another stamps the compile time into the binary. — [Doc/HolyC.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/HolyC.DD); [Kernel/KStart16.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KStart16.HC) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E14] HolyC's documented gaps: "No #define functions exist (I'm not a fan)", "No typedef, use class.", "No type-checking", "There is no continue stmt. Use goto.", `lock{}` "It's a little shoddy.", and "The stk does not grow because virtual mem is not used." — [Doc/HolyC.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/HolyC.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E15] Compile modes. JIT: "the compiler places code and data in memory alloced from the heap, incrementally, making them immediately ready for in-place execution. This mode is used during cmd line operations." AOT: "Do not use AOT, use JIT compiling." and "There is no way to unload except by killing the task." The Kernel module and the compiler are built AOT. — [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E16] The terminal loop `ExeCmdLine()` calls `LexStmt2Bin()` to compile one statement and then `Call(machine_code)`. `ExeFile()` wraps a file name in an `#include` statement and passes it to `ExePutS()`. — [Kernel/KTask.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KTask.HC); [Compiler/CMain.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Compiler/CMain.HC) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E17] "TempleOS compiles, doesn't interpret, and uses no byte code anywhere." The intermediate code "is rev polish stack machine in nature and can be viewed with PassTrace()", and assembly output can be viewed with `Trace()`, `U()` or `Uf()`. — [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD); [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E18] "TempleOS doesn't use software interrupts or SYSCALL insts because it never needs to change out of ring-0, even running user programs. Calls are always CALL REL32 insts." Because the compiler always uses 32-bit relative JMP and CALL, "TempleOS keeps all code in the lowest 2Gig memory addresses including what would normally be called 'the kernel'." — [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD); [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E19] "ZealC is a fork of HolyC. The only changes to Terry's HolyC compiler are reformatting, label renames, bugfixes, and additions." — [ZealOS docs: ZealC](https://zeal-operating-system.github.io/Doc/ZealC.DD.html) (Last-Modified 2023-10-21; accessed 2026-10-14)

### Symbol tables, reload and the Adam task

- [E20] "All tasks have a heap and a sym table." "If a sym is not found, the parent task's table is checked. The father of all tasks has the API syms you'll need waiting in it's table. No need to #include headers." "No need for namespaces -- scoping occurs automatically based on task symbol table hierarchy". — [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E21] Reload by shadowing: "older syms with ident names will be overshadowed if they exist", and duplicates "are allowed, by design in other cases, so that you can repeatedly #include the same file from the cmd line while developing it." The FAQ, under "Why does it leak memory?": "If you #include a file twice, it allocs more mem for it." — [Doc/ScopingLinkage.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/ScopingLinkage.DD); [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E22] "If you change code in the /Adam or your /Home directory, you don't need to recompile, you just need to reboot because those directories get recompiled when you boot." Tips: "You should have two TempleOS partitions on your hard drive because a syntax error in a start-up file will make the partition unbootable." — [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD); [Doc/Tips.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Tips.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E23] "Adam is immortal." "When created, Adam runs the file ::/StartOS.HC. When start-up is finished, the adam task enters a server mode where it accepts requests from other tasks. The Adam("") routine will make Adam compile and run text src code. #include stmts can be sent to Adam(""), creating system-wide code and data which are immortal." MemOverview: "His memory is like kernel memory in other operating systems." — [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD); [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E24] Boot sequence in code: `Kernel/KMain.HC` sets `adam_task=Fs`, runs `Load("Compiler",LDF_SILENT)`, then `try ExeFile("StartOS")` with a `catch` that calls `Dbg`. `StartOS.HC` includes the kernel and compiler headers, then `#include "/Adam/MakeAdam"`, spawns the window manager task, includes `~/MakeHome`, and ends with "After this file, the Adam task enters server mode". `Adam/MakeAdam.HC` includes, among others, `Gr/MakeGr`, `WinMgr`, `ADbg`, `DolDoc/MakeDoc` and `AutoComplete/MakeAC`. — [Kernel/KMain.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KMain.HC); [StartOS.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/StartOS.HC); [Adam/MakeAdam.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Adam/MakeAdam.HC) (all V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E25] `Adam()` submits a job with `TaskExe(adam_task,Fs,buf,...)`. The five job types are `JOBT_TEXT_INPUT` (feed stdin), `JOBT_MSG` (post a message), `JOBT_EXE_STR` ("Compile & execute src code text"), `JOBT_CALL` ("Tell MP to call function") and `JOBT_SPAWN_TASK`. — [Kernel/Job.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Job.HC); [Doc/Job.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Job.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E26] In the ZealOS line, Adam became the Zenith task in ZenithOS and then the "System Task" (ChangeLog entry 07/01/21, "Zenith Task --> System Task"). The ZealOS glossary: "The System task is immortal", it "enters a server mode where it accepts requests from other tasks", and "The Sys("") routine will make the System task compile and run text src code." Each core has an immortal "Executive" task, the successor of TempleOS's Seth tasks. — [ZealOS src/Doc/ChangeLog.DD](https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Doc/ChangeLog.DD); [ZealOS src/Doc/Glossary.DD](https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Doc/Glossary.DD) (master, last repo commit 2025-11-10; accessed 2026-10-14)

### Tasks, scheduler and multicore

- [E33] `Sched.HC` header: "The scheduler is round-robin." "Tasks can be switched in half a microsecond." "A task runs until it voluntarily yields ctrl" with `Yield()`; tasks waiting on I/O poll and yield, which "pegs the CPU Load". Welcome: "Tasks have no priority and are never removed from the queue." — [Kernel/Sched.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/Sched.HC); [Doc/Welcome.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Welcome.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E34] Strategy: the scheduler "is for home systems. It is not preemptiove. Disk requests are not broken-up, so sharing is bad." The timer handler `IRQ_TIMER` saves context, increments `total_jiffies`, calls the profiler hook and (on Core0) `IntCore0TimerHndlr`, then jumps to `RESTORE_RSI_TASK`, the interrupted task, unless that task is the idle task (my reading of the assembly). — [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD); [Kernel/KInts.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KInts.HC) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E35] "TempleOS does master-slave multicore instead of SMP. Core0 is the master." Applications assign jobs to other cores explicitly with `JobQue()`/`JobResGet()`, "the TempleOS scheduler does not move tasks between cores", and "Only tasks on Core0 can have windows". "Adam is the Seth Task on Core0." — [Doc/MultiCore.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MultiCore.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E36] "There is no distinction between task, process or thread." "Since there is not friendly disk sharing and all tasks have the same address map, it might be accurate to call TempleOS, 'multi-thread/single-process'." — [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E37] ZealOS keeps the model. `Sched.ZC`: "The scheduler is round-robin" and "A task runs until it voluntarily yields ctrl". MultiCore: "ZealOS does master-slave multicore instead of SMP" and the scheduler "does not move tasks between cores". Strategy: "It is not preemptive." Welcome: ZealOS is a "non-preemptive multi-tasking, ring-0-only, single-address_mapped (identity-mapped), operating system". — [ZealOS src/Kernel/Sched.ZC](https://raw.githubusercontent.com/Zeal-Operating-System/ZealOS/master/src/Kernel/Sched.ZC) (master, last repo commit 2025-11-10; accessed 2026-10-14); [MultiCore](https://zeal-operating-system.github.io/Doc/MultiCore.DD.html), [Strategy](https://zeal-operating-system.github.io/Doc/Strategy.DD.html), [Welcome](https://zeal-operating-system.github.io/Doc/Welcome.DD.html) (ZealOS docs site, Last-Modified 2023-10-21; accessed 2026-10-14)

### Memory model

- [E38] "All tasks on all cores use the same page table map, just as though all addresses are physical addresses. 2Meg or 1Gig page table entries are used. Nothing swaps to disk." — [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E39] Terry first "unmapped the first 4K to cause a fault when dereferencing NULL"; after the 2016 change to uncached aliases, "I also no longer cause a fault when dereferencing NULL." "During an extended powered-on session of TempleOS, in theory, memory will become fragmented, requiring a reboot." — [Doc/MemOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/MemOverview.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E40] Quirks: "The stk does not grow because virtual mem is not used." and there is no file sharing or locking: "Generally, the last write wins." — [Doc/Quirks.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Quirks.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)

### RedSea and storage

- [E41] RedSea "is a simple, 64-bit, file system which is similar to FAT32, but with absolute block addresses instead of clus, fixed-sized 64-byte directory entries and no FAT table, just an allocation bitmap." "Files are stored in contiguous blocks and cannot grow in size." `CDIR_FILENAME_LEN` is 38 including the terminator. "RedSea file system has no bad block table and no redundant allocation table." The partition is typed as FAT32 "to fool BIOS", with signature 0x88 to distinguish it. — [Doc/RedSea.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/RedSea.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E42] `RedSeaAllocClus` picks the smallest free run that fits and throws `'Drv'` if none fits. `RedSeaFileWrite` calls `RedSeaFilesDel` on the existing name, then `ClusAlloc(... ,TRUE)` ("Always contiguous"), then `BlkWrite`, and only then `RedSeaDirNew`. — [Kernel/BlkDev/FileSysRedSea.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/BlkDev/FileSysRedSea.HC) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E43] "The RedSea file system does not allow files to grow because it only has an allocation bitmap and not a FAT table. This 'flaw' is by design. I am intentionally crippling this operating system, making it a toy with the wisdom that this will prevent commercialization and corruption." Random access works if "you ... declare the desired file size when you create it with FOpen() and cannot change it." — [Doc/BlkChain.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/BlkChain.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E44] Reliability: "Obviously, we don't do bad block tables, or redundant FATs." "Do not have more than a few thousand files or the file manager will not function." Users are encouraged to keep the drive to "maybe, 100 Meg of files". Quirks: on FAT32, "TempleOS does not generate unique short-entry names" and "Do not access FAT32 drives not dedicated to TempleOS." — [Doc/Reliability.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Reliability.DD); [Doc/Quirks.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Quirks.DD) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E45] Storage support is "ATA PIO Hard drives, support for FAT32 and RedSea file systems with file compression" plus "ATAPI PIO CD/DVD support". Files whose names end in `.Z` "are automatically compressed or uncompresses files when read or written." Strategy: "Disk code does not use interrupts, avoiding compatibility risks. PS/2 keyboard/mouse is used instead of USB". — [Doc/Features.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Features.DD); [Doc/Glossary.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Glossary.DD); [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD) (all V5.03 snapshot 2017-11-21; accessed 2026-10-14)

### Graphics

- [E46] `KernelA.HH` defines `WINMGR_FPS (30000.0/1001)`, `GR_WIDTH 640`, `GR_HEIGHT 480` and `COLORS_NUM 16`. Real-mode boot code in `KStart16.HC` loads `AX=0x4F02`, `BX=0x12` ("640x480 16 color") and emits `INT 0x10` through an `#exe` block. — [Kernel/KernelA.HH](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KernelA.HH); [Kernel/KStart16.HC](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Kernel/KStart16.HC) (both V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E47] The window manager task calls `GrUpdateScrn()`, `GrUpdateTasks()` and `GrUpdateTaskWin()` at 30 fps and invokes each task's `draw_it()` callback. "Only tasks on Core0 are allowed to have windows. There is one window per task, no child windows." Programs "draw everything in the window over and over again." Device contexts: `DCAlias()` makes a private context; `DCNew()` makes an off-screen bitmap that can be blitted with `GrBlot()`. `ROP_COLLISION` "counts the num of pixs drawn on non-background locations". `CMathODE` with `ODENew()` provides an ODE solver for "realistic physics". — [Doc/GraphicsOverview.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/GraphicsOverview.DD) (V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E48] Strategy: "Updates whole scrn at 30 fps, optimized for full scrn games where InvalidRectangles are counter-productive." "Text and graphic layers done in software". The FAQ: 30 fps "is how often TempleOS updates scrn mem. It is not syncronized to the hardware." Welcome: "A 1600x1200x24 bit scrn takes 37 times more memory, implying 37 times the CPU power." — [Doc/Strategy.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Strategy.DD); [Doc/FAQ.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/FAQ.DD); [Doc/Welcome.DD](https://raw.githubusercontent.com/cia-foundation/TempleOS/archive/Doc/Welcome.DD) (all V5.03 snapshot 2017-11-21; accessed 2026-10-14)
- [E49] Sprites are drawn in the editor with CTRL-r and live inside source files; `$IB,"",BI=1$` in source inserts "the addr of sprite binary data item #1". ### Why one address space is not enough

- [E73] McIlroy et al.: "we now believe that speculative vulnerabilities on today's hardware defeat all language-enforced confidentiality with no known comprehensive software mitigations, as we have discovered that untrusted code can construct a universal read gadget to read all memory in the same address space through side-channels. In the face of this reality, we have shifted the security model of the Chrome web browser and V8 to process isolation." — [arXiv:1902.05178, "Spectre is here to stay"](https://arxiv.org/abs/1902.05178) (submitted 2019-02-14; accessed 2026-10-14)
- [E74] V8 team: "software mitigation of all possible leaks due to Spectre was infeasible"; some variants, "particularly variant 4", were "simply infeasible in software"; "The only effective mitigation is to move sensitive data out of the process's address space"; "Chrome's security model no longer assumes language-enforced confidentiality within a renderer process." — [A year with Spectre: a V8 perspective](https://v8.dev/blog/spectre) (published 2019-04-23; accessed 2026-10-14)
- [E75] Kocher et al.: speculative execution implementations "violate the security assumptions underpinning numerous software security mechanisms, including operating system process separation, ... just-in-time (JIT) compilation", and "sound solutions will require fixes to processor designs as well as updates to instruction set architectures". — [arXiv:1801.01203, "Spectre Attacks"](https://arxiv.org/abs/1801.01203) (submitted 2018-01-03; accessed 2026-10-14)
- [E76] Lipp et al.: "Meltdown breaks all security guarantees provided by address space isolation as well as paravirtualized environments", and "the KAISER defense mechanism for KASLR has the important (but inadvertent) side effect of impeding Meltdown." — [Meltdown, 27th USENIX Security Symposium](https://www.usenix.org/conference/usenixsecurity18/presentation/lipp) (2018; accessed 2026-10-14)
- [E77] Reis, Moshchuk and Oskov: "Ultimately, cross-process and user/kernel boundaries must fundamentally be preserved by the OS and hardware and cannot be left to applications to enforce." Site Isolation "incurs a total memory overhead of 9-13% in practice and increases page load latency by less than 2.25%". — [Site Isolation, USENIX Security 2019](https://www.usenix.org/system/files/sec19-reis.pdf) (August 14-16, 2019; accessed 2026-10-14)
- [E78] Linux page-table isolation: "Moves to CR3 are on the order of a hundred cycles, and are required at every entry and exit." "On systems without PCID support, each CR3 write flushes the entire TLB." Losing global pages for kernel structures costs "never exceeding 1%". — [Linux kernel docs: Page Table Isolation](https://docs.kernel.org/arch/x86/pti.html) (Last-Modified 2026-10-13; accessed 2026-10-14)
- [E79] "in the presence of branch prediction, it is possible for bounds checks to be ignored by code which is speculatively executed"; "array_index_nospec(index, size) returns a sanitized index value that is bounded to [0, size) even under cpu speculation conditions." — [Linux kernel docs: Speculation](https://docs.kernel.org/staging/speculation.html) (Last-Modified 2026-10-13; accessed 2026-10-14)
- [E80] Theseus (OSDI 2020): "Theseus must trust the Rust compiler and its core/alloc libraries to uphold safety without soundness holes"; "unsafe languages require hardware protection or dynamic interposition on memory accesses (à la SFI) if isolation was desired"; "we do not make claims about certain OS aspects, e.g., efficiency or security"; the code base has "72 unsafe code blocks or statements across 21 crates". — [Boos et al., OSDI 2020](https://www.usenix.org/system/files/osdi20-boos.pdf) (November 4-6, 2020; accessed 2026-10-14)
- [E81] The Theseus book: "Isolation should be the responsibility of software alone", and Theseus "completely foregoes hardware privilege levels (x86's Ring 0 vs. Ring 3 distinction) and multiple address spaces." — [Theseus book: design idea](https://www.theseus-os.com/Theseus/book/design/idea.html) (Last-Modified 2024-09-22; accessed 2026-10-14)
- [E82] RedLeaf (OSDI 2020): "we trust (1) the Rust compiler to implement language safety correctly, and (2) Rust core libraries that use unsafe code", and "we do not protect against sidechannel attacks". — [Narayanan et al., OSDI 2020](https://www.usenix.org/system/files/osdi20-narayanan_vikram.pdf) (November 4-6, 2020; accessed 2026-10-14)

### Estimates and analysis

Everything in this subsection is my own analysis. Each item states its method or assumptions.

- **[A1] Size of TempleOS by component (measured by me, method stated).** Method: `wc -l` over `*.HC`, `*.HH` and `*.PRJ` in a shallow clone of the `archive` branch at commit c26482b. Some `.HC` files carry binary sprite data after the NUL [E29], so counts may be slightly high. Results: Kernel 24,509; Compiler 18,680; Adam layer 38,619; root files 399; total 82,207, which agrees with the in-tree figure of 82,150 [E58]. Apps and Demo add 40,474 lines outside the cap. Components: RedSea driver 635; FAT32 driver 959; scheduler 325; kernel debugger (`KDbg.HC`) 652 plus `Adam/ADbg.HC` 270; source-link code (`FunSeg.HC`) 360; window manager 863; AutoComplete 945; DolDoc engine about 10,204; graphics library about 13,393. The Adam layer, which is JIT-compiled at every boot [E56], is about 47% of the core.
- **[A2] Kernel image size.** From the memory map [E59], the kernel module spans `0x36AEF - 0x7C00` = 192,239 bytes, about 188 KiB. Assumption: the cached defines match the snapshot's build.
- **[A3] Frame bandwidth.** TempleOS's frame is 640x480 at 4 bits per pixel, 153,600 bytes; at 30 fps that is about 4.6 MB/s. A 1024x768 frame at 32 bits per pixel is 3 MiB, 20.5 times larger; full redraw costs about 90 MiB/s at 30 fps and 180 MiB/s at 60 fps, 20 to 41 times TempleOS's rate. Terry's own "37 times" figure for 1600x1200x24 [E48] uses the same arithmetic. Natively this is trivial. Under QEMU TCG on Windows, how much of one emulated vCPU it consumes is unmeasured (open question 1). For the terminal, damage tracking is the safe default; Terry's argument against invalid rectangles [E48] is specific to full-screen games.
- **[A4] Cost of rings for the REPL.** Assumptions: about 10 kernel calls per REPL statement; a syscall round trip of a few hundred cycles natively, based on the PTI figure of about a hundred cycles per CR3 move [E78]; a 10 to 50 times slowdown under TCG (assumed, not measured). Result: microseconds natively and well under a millisecond under TCG, invisible at typing speed. Generated syscall stubs that mirror kernel function names would let REPL code "call the kernel by name" with the same syntax TempleOS uses, but every call is checked and may be refused. The cost matters only on hot paths, and the scheduler hot path runs in the kernel anyway.
- **[A5] Effort for the TempleOS-derived pieces (estimates for a founder who knows Rust but has not written a kernel; each assumes the foundation milestone it depends on is done).** DolDoc-lite text model with colours, links and collapsible blocks in the framebuffer terminal: 2 to 3 weeks. Links on every printed address and the `man`/`edit-at`/`fix` commands, once the symbol index exists: about 1 week. Adam-role system service with a job queue: 1 to 2 weeks after ring 3. Per-process debugger (attach on fault, registers as variables, memory dump, source-linked backtrace): 3 to 5 weeks. Compositor with per-task draw callbacks: 1 to 2 weeks. Read-only contiguous source bundle: about 1 week. The TempleOS line counts in A1 are an upper bound for comparable scope, since Kernel AI drops the sprite editor, macros and songs.
- **[A6] DolDoc widgets across address spaces (inference).** DA, CB and HX entries and AD links refer to raw addresses in the one shared address map [E27, E30, E38]. Under per-process page tables, an address is meaningful only in its own process. A live data widget then needs either a kernel call that reads another process's memory under a debug capability, or the debugger as an intermediary. Both are possible; neither is the TempleOS mechanism.
- **[A7] RedSea crash window (inference).** `RedSeaFileWrite` deletes the old file before it allocates, writes, and finally creates the new directory entry [E42]. A crash between the delete and the directory write loses both the old and new versions. No journal or copy-on-write protects that window. I did not test this.
- **[A8] Stale callers after re-include (inference).** Calls are always CALL REL32 to a fixed address [E18], and a re-included symbol only shadows the old one [E21]. Code compiled before the re-include therefore keeps calling the old body. [compiler-in-terminal.md](./compiler-in-terminal.md) reaches the same conclusion, and both memos choose a per-symbol indirection slot for Kernel AI.
- **[A9] Performance claims.** "Two seconds" to boot [E55] and "half a microsecond" per task switch [E33, E57] are the author's statements with no stated hardware or method. I found no independent measurement and ran nothing. Do not use them as targets without measuring both systems on the same host (open questions 2 and 9).

## Open questions

1. **What does full-frame redraw cost under QEMU TCG and WHPX on the founder's Windows 11 host?** Why it matters: it decides D7 (frame rate, and damage tracking or full redraw) and whether the compositor competes with the synthetic workloads for the emulated CPU. How to resolve: at M0, time a loop that fills and copies a 1024x768x32 frame 600 times, under TCG and WHPX, at `-smp 1` and `-smp 4`, and log ms per frame to serial.
2. **What is boot-to-prompt time for Kernel AI, and for TempleOS and ZealOS, on the same host?** Why it matters: it sets the D12 target and tests whether TempleOS's "two seconds" claim [E55] is a useful benchmark at all. How to resolve: boot `TempleOS.ISO` [E3] and a ZealOS ISO with the wiki's WHPX command line [E68], then the Kernel AI M0 image, and time each from QEMU start to first prompt with a serial marker or a screen capture. Repeat under TCG.
3. **How expensive is a syscall round trip and a CR3 switch under TCG and WHPX?** Why it matters: it decides whether the vDSO-style read-only index mapping [E91] is needed in the POC or can wait, and it tests estimate A4. How to resolve: at M3, measure a null syscall loop and a CR3 reload loop with TSC timestamps under each accelerator.
4. **What share of the LLM's output for REPL and system-control prompts is outside Extended ASCII?** Why it matters: it decides D8 (font coverage). How to resolve: run the benchmark prompts from [compiler-in-terminal.md](./compiler-in-terminal.md) against the Mac mini server, count code points outside U+0000 to U+00FF, and list the most frequent ones.
5. **Can a sidecar format for links, images and sprites survive git merges and LLM edits?** Why it matters: D1 trades TempleOS richness for plain-text tooling; if sidecars drift from the source they describe, links break. How to resolve: prototype one sidecar per source file keyed by symbol name rather than line number, then run 20 LLM-made edits and 5 branch merges and count broken anchors.
6. **Are live data widgets (TempleOS's DA and HX) worth building across address spaces?** Why it matters: live, editable memory views were part of what made the TempleOS debugger and documents feel direct [E52], but they need a debug capability (A6). How to resolve: decide after the per-process debugger exists; if the debugger's memory view meets the need, drop document-level data widgets.
7. **Which parts of the Adam role belong in the system service, and which in the swap orchestrator from [live-editable-system.md](./live-editable-system.md)?** Why it matters: both hold system-wide state, and splitting it wrongly puts a restartable ring-3 service on the critical path of a kernel component swap. How to resolve: a design review once the orchestrator's interface exists, with the rule that the orchestrator never depends on the system service.
8. **Will a TempleOS descendant add any protection once it ships HTTPS and USB?** Why it matters: if ZealOS adopts rings or address spaces, its design becomes a closer reference; if not, its network code remains a cautionary example [E64, E70].
