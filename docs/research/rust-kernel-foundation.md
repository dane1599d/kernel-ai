# Rust kernel foundation: rust-osdev from scratch vs Asterinas OSTD

- **Date:** 2026-10-14
- **Status:** Research memo (no code)
- **Scope:** A comparison of two foundations for the Kernel AI x86_64 kernel, (A) a from-scratch kernel on Limine and rust-osdev crates and (B) Asterinas OSTD/OSDK, covering licensing, scheduler and memory-manager control, core kernel subsystems, first virtio drivers, QEMU on a Windows 11 host, the test harness, CI and an M0-M6 milestone ladder for each path.
- **Related memos:** [compiler-in-terminal.md](./compiler-in-terminal.md), [live-editable-system.md](./live-editable-system.md), [llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md), [templeos-components.md](./templeos-components.md)

## Conclusions

1. **Build Kernel AI on Path A (Limine plus rust-osdev crates). Copy Path B's interface designs, not its code.** The fixed live-editable requirement needs control over kernel address-space mappings and code loading. OSTD keeps both crate-private and has no module loader [E78, E80]. Path A uses only permissive licences [E2, E9, E21, E26, E36] and already has Windows-host QEMU CI precedent [E129, E130]. Path B reaches a first scheduling demo sooner. Most of that lead disappears once the OSTD fork and the upgrade costs are counted (see the ladders below).

2. **Path A works with maintained, permissively licensed crates for everything except the APIC. Every mechanism the POC is about will be our own code.** The supported stack is: Limine 12.9.3, the `limine` crate 0.6.5, `x86_64` 0.15.5, `acpi` 6.1.1, `raw-cpuid`, `uart_16550`, `talc` or `linked_list_allocator`, `spin`, `pci_types`, `virtio-drivers` 0.13.0 and `smoltcp` [E1, E9, E21, E24-E27, E30, E34, E36, E42]. The rust-osdev `apic` repository is a 2020 stub that was never published. The only maintained alternative, `x2apic` 0.5.0, calls itself experimental and QEMU-tested only. Plan to own the LAPIC and IOAPIC code [E28, E29]. The scheduler, the SMP data structures, ring 3, demand paging and reclaim have no crate on either path.

3. **Boot with Limine. `bootloader` 0.11 and `uefi-rs` are the wrong tools for this job.** Limine starts the APs on request and provides a higher-half direct map (HHDM), the framebuffer, the RSDP, modules and a TSC-frequency hint. It also ships a Windows host tool [E3-E8]. `bootloader` 0.11 needs nightly plus unstable bindeps and does not start APs [E11]. `uefi` 0.41 is designed for writing UEFI images and loaders, not for skipping that layer [E12]. Two traps: from base revision 3 the HHDM does not cover device MMIO, so the kernel must map the LAPIC, IOAPIC and ECAM itself [E7]. Limine's own Rust template still pins the old `limine` 0.5 API, so the founder has to translate it to 0.6 [E9, E10].

4. **Path A needs a pinned, dated nightly today. Stable Rust is possible only by forking or replacing the `limine` and `acpi` crates.** The `x86_64-unknown-none` target ships a prebuilt `core`/`alloc`. Allocation failure panics without a nightly handler. Naked functions are stable and can replace the x86-interrupt ABI [E14-E16, E20]. But two recommended crates turn on unstable features unconditionally. `limine` 0.6.5 declares `#![feature(ptr_metadata)]` (src/lib.rs line 6) and `acpi` 6.1.1 declares `#![feature(allocator_api)]` (src/lib.rs line 35). Both APIs are still nightly-only — [limine 0.6.5 source](https://docs.rs/crate/limine/0.6.5/source/src/lib.rs), [acpi 6.1.1 source](https://docs.rs/crate/acpi/6.1.1/source/src/lib.rs) (published crate sources; checked 2026-10-14). On top of that, the `x86_64` crate's `nightly` feature, which is on by default, uses `abi_x86_interrupt` for the safe `set_handler_fn`, and our own tests use `custom_test_frameworks` [E17-E19]. Pin `x86_64` to 0.15.5, because 0.16.0-rc.0 breaks `OffsetPageTable` and raises the MSRV to 1.98 [E21].

5. **Paging and the heap are the best-supported parts of Path A. Use 4-level paging over Limine's HHDM with the `x86_64` crate's `OffsetPageTable`, and put `talc` or `linked_list_allocator` behind `spin` locks.** Limine enters the kernel with 4-level paging and NX enabled. 5-level paging is opt-in, and CR4.LA57 cannot be changed once IA-32e paging is on, so choose 4-level and keep it [E4, E6, E23]. `x86_64` 0.15.5 provides the page-table types and mappers [E22]. `talc` is built for kernels, with `lock_api` locking and multiple heaps [E24, E25]. Per-process page tables, guard pages and demand paging are our own code on Path A. On Path B, OSTD owns all page tables and exposes only `VmSpace` for user space [E77, E78].

6. **Path B (OSTD/OSDK 0.19.0) supplies most of the M1-M4 mechanism, plus exactly the scheduler and allocator hooks the POC needs.** OSTD owns the context switch, the timers, IRQ lines, AP boot, page tables and DMA. It takes the scheduler (`Scheduler` and `LocalRunQueue`), the frame allocator (`GlobalFrameAllocator`) and the slab allocator (`GlobalHeapAllocator`) as safe-Rust policies [E68, E69, E75, E81]. Kernel AI would control where tasks are placed when enqueued, the order of each per-CPU queue, the preempt decision on every tick, frame and slab policy, and all user-space paging, using `VmSpace` cursors with ACCESSED/DIRTY bits [E69, E76, E77]. It would not control the context-switch mechanism, the tick rate (a 1000 Hz constant), the points where preemption can happen, or kernel-space mappings [E71-E73, E78].

7. **Unless we fork OSTD, Path B rules out ring-0 live editing and a ring-0 JIT.** OSTD's kernel page table and kernel virtual areas are `pub(crate)` [E78]. Asterinas has no module loader and says it will never load Linux kernel modules [E80]. `inject_scheduler` can be called only once, and the allocators are fixed at link time [E70, E75]. JIT output in ring 3 is supported through `VmSpace` with `PageFlags::X` [E77]. Any OSTD edit that adds kernel code loading is an MPL "Modification" and has to be published when we distribute [E95].

8. **On Path B the timer preempts only user-mode code, so every synthetic workload must run in ring 3.** `enable_preemption_on_cpu` documents preemption only for tasks executing in user mode. In ostd 0.19.0, `might_preempt()` is called only in the return-to-user loop, `halt_cpu`, task spawn and the guest-VM loop [E71, E72]. The default FIFO scheduler puts every task on the bootstrap CPU and never preempts on a tick [E70]. Asterinas's own scheduler picks a CPU only at spawn and does not migrate tasks afterwards (source reading) [E74].

9. **Path B cannot be developed natively on Windows 11 and cannot be built on stable Rust.** `cargo-osdk` imports `std::os::unix` unconditionally and is documented for x86_64 Ubuntu only [E84, E85]. OSTD enables nine unstable features, and OSDK uses `-Zbuild-std`. `cargo osdk new` refuses any toolchain other than `nightly-2026-07-21` [E86]. OSTD boots through GRUB with Multiboot/Multiboot2, the Linux boot protocol or PVH, never Limine [E82, E83]. The OSDK template's `kernel-irqchip=split` is rejected by WHPX [E87, E107]. The API breaks between minor releases [E59-E61], and crates.io shows no third-party users of `ostd` [E66].

10. **MPL-2.0 is compatible with "open source now, possibly commercial later", but every OSTD edit becomes permanently public.** MPL copyleft applies file by file: our own new files can carry any licence, including a proprietary one [E95, E96]. Shipping a binary obliges us to make available the source of every MPL file it contains, modified or not [E95]. Asterinas chose the MPL precisely so that proprietary code can link against it [E97]. The catch is that the edits Kernel AI is most likely to need (ring-0 code loading, a different preemption or tick model) are all OSTD file edits. Pasting OSTD code into our own file also makes that file MPL [E95].

11. **Design interrupts and timers for QEMU TCG, which has no TSC-deadline timer, no invariant TSC and no PCID.** TCG's CPUID lists TSC-deadline and PCID as missing and exposes no invariant TSC [E110]. Its LAPIC model runs on QEMU's virtual clock and has no TSC-deadline path [E111]. Use LAPIC one-shot or periodic mode, calibrated against the HPET, the ACPI PM timer (both found through the `acpi` crate) or the PIT. Treat Limine's TSC frequency as a hint only [E8, E27, E31, E32]. x2APIC exists under both TCG and WHPX [E107, E110]. Detect every feature at runtime with `raw-cpuid` [E30].

12. **On Path A, starting the APs is cheap because Limine does it. The hard SMP work is per-CPU state, IPIs and TLB shootdown, and no tutorial covers it.** The Limine MP request replaces the INIT-SIPI-SIPI trampoline and its 10 ms and 200 µs delays [E5, E33]. blog_os has no APIC, SMP or preemptive scheduling posts [E135]. For those parts, read Redox, Hermit, Theseus and OSTD [E43, E138].

13. **Build the scheduler policy hook as an OSTD-shaped trait, swappable at runtime the way Theseus does it, with a sched_ext-style watchdog fallback. The LLM only picks pre-built policies or writes bounded parameters.** OSTD's enqueue/update_current/pick_next shape is a proven hot-path interface [E69]. Theseus's `set_policy` drains tasks into a new policy at runtime [E43]. sched_ext and ghOSt both fall back to the default scheduler on error or stall [E44-E46]. Scheduling decisions take nanoseconds to microseconds [E46, E50], while the LLM emits one token every 50 ms. LumOS's stage/commit/revert and AKTS's "index into a pre-verified table" are the right control-plane shapes [E50, E51]. Reimplement scx ideas only: its code is GPL-2.0-only [E48].

14. **Pluggable memory reclaim is new work on both paths. Shape it like DAMOS schemes running over a kernel-owned mechanism.** Asterinas has no swap and no eviction under memory pressure [E79]. OSTD gives only the page-table bits (ACCESSED/DIRTY) to build on [E77]. DAMOS (access pattern, action, quota, goal, watermarks), MGLRU's refault feedback loop and PageFlex's "delegate only non-critical policy" rule together define a safe hook [E53-E55].

15. **For the first virtio drivers, use rcore's `virtio-drivers` on the q35 machine with ECAM. Keep the terminal on a linear GOP framebuffer from `-vga std` or `virtio-vga`. virtio-gpu comes later.** `virtio-drivers` covers block, net, console, GPU and more in `no_std`, but only over memory-mapped PCI config space (ECAM), which on x86 QEMU exists only on q35 [E36-E38]. A plain `virtio-gpu-pci` device gives OVMF only a Blt-only GOP, so it provides no linear framebuffer [E39, E40]. On Path B, OSTD has no virtio drivers. Asterinas's own drivers are in-tree MPL crates with a long dependency chain and no GPU driver [E92]. rcore's `unsafe trait Hal` also collides with the framekernel `#![deny(unsafe_code)]` lint [E37, E63]. Either way, we program the MSI-X table ourselves [E34, E35].

16. **Make QEMU TCG the reference platform and WHPX an optional fast mode. Install QEMU 11.1.2 from MSYS2.** MSYS2 ships 11.1.2 with the edk2 firmware. Stefan Weil's installers are labelled experimental, stop at 11.1.0 and have no point releases [E100, E101]. WHPX is maintained (with a Microsoft co-maintainer) but changed heavily in 2026 [E104]. gdb has worked with WHPX only since 11.0.0 [E105]. WHPX has no hardware watchpoints, and whether its breakpoints work is unverified [E106]. Its open bugs include reboot hangs and virtio-net hangs [E108]. icount and record/replay never work with WHPX [E115, E116].

17. **Run policy comparisons in a deterministic measurement mode and report relative numbers, not absolute ones.** The mode is single-threaded TCG with `-icount shift=N,sleep=off` and `-rtc clock=vm` [E114, E117]. Without icount, guest time is host wall-clock time, while the amount of guest work done per unit of that time depends on translation speed and host load [E113]. Even with icount, QEMU is not cycle-accurate [E114]. icount also forces all vCPUs onto one host thread [E112, E114].

18. **One test harness serves both paths: isa-debug-exit at port 0xf4, serial on stdio, a fresh QEMU process per test, and gdb under TCG.** isa-debug-exit exits QEMU with status `(v<<1)|1`, which is always odd, so the runner must map, for example, 33 (written value 0x10) to "pass" [E119, E120]. OSDK already implements this pattern with 0x10 and 0x20 [E89]. Avoid `system_reset` under WHPX and `pipe:` chardevs on Windows, because both have open hang or deadlock bugs [E108, E109].

19. **CI fits in free GitHub-hosted runners with three jobs: a Linux TCG job (authoritative), an optional Linux KVM job for speed, and a Windows smoke job.** Linux runners expose `/dev/kvm` once a udev rule is added, and they are free for public repositories [E125, E126]. QEMU is not preinstalled [E127, E128]. uefi-rs and bootloader already run QEMU tests on `windows-latest` with Chocolatey-installed QEMU [E129, E130]. On Path B we would run CI inside the `asterinas/osdk-dev` container, as Asterinas itself does [E91].

20. **blog_os takes the founder to roughly M2. After that the guides are the Intel SDM, the Limine spec, OSTD's design and readable kernels.** blog_os has 12 posts, ending with cooperative async/await in 2020. The promised APIC and preemption posts never appeared, and the 3rd edition is a set of unpublished drafts [E134, E135, E137]. Its code samples are MIT/Apache, but its prose is CC BY-NC [E98].

21. **Estimated effort to M6: Path A about 22-45 focused person-weeks. Path B about 16-36, plus 3-8 for an OSTD fork if ring-0 live editing stays in scope, plus 1-2 for each OSTD minor release.** These are estimates, not measurements. The assumptions are in the ladders below and in "Estimates and analysis".

### Milestone ladders (M0-M6)

Assumptions (estimates, not measurements):
- The developer works solo, knows Rust well and is writing a first kernel.
- One focused person-week is 30-35 hours of deep work.
- The ranges include debugging under QEMU TCG and WHPX on Windows and are roughly ±50%, because first-kernel debugging dominates.
- The ranges exclude the LLM network client and control-plane service ([llm-in-a-from-scratch-os.md](./llm-in-a-from-scratch-os.md)), the REPL and compiler ([compiler-in-terminal.md](./compiler-in-terminal.md)), and live-edit tooling ([live-editable-system.md](./live-editable-system.md)). The hooks these pieces need are included.
- Both ladders share the same milestone goals, so the totals are comparable.
- The founder's weekly hours are not known yet (Open question 1).

### Recommendation

Choose **Path A**. Concretely:

1. **Run a 2-4 day spike before committing.** Install QEMU 11.1.2 from MSYS2 on the founder's Windows 11 machine. Boot a Limine "hello" kernel under OVMF on q35 in TCG and in WHPX, with `-smp 4`. Check whether gdb `break` and `stepi` work under each accelerator. The result decides whether WHPX is part of the daily workflow (Open questions 2 and 3).
2. **Toolchain:** pin a dated nightly in `rust-toolchain.toml` (no older than `nightly-2026-07-10`, which `x86_64` 0.15.5's `nightly` feature requires [E21]). In Kernel AI's own crates, allow only two unstable features, `abi_x86_interrupt` and `custom_test_frameworks`, so the code stays close to blog_os through M2. The nightly must also satisfy `ptr_metadata` (in `limine`) and `allocator_api` (in `acpi`) (conclusion 4). Stable Rust is off the table until those crates gate the features. This is a founder decision (decision 2 below).
3. **Borrow designs and write the code fresh:**
   - OSTD's `Scheduler`/`LocalRunQueue` and `GlobalFrameAllocator` shapes [E69, E75].
   - Theseus's runtime `set_policy` [E43].
   - sched_ext's stall watchdog and bypass slice [E44, E45].
   - DAMOS's scheme/quota/goal/watermark structure [E53].
   - LumOS's stage/commit/revert [E51].
   - AKTS's index into pre-built policies [E50].

   Do not paste OSTD code (MPL) or scx code (GPL-2.0-only) into Kernel AI files [E48, E95].
4. **Keep Path B as a documented fallback, not a parallel track.** Re-evaluate only if Path A's M3 runs past twice its estimate. At that point a one-week OSTD spike under WSL2 settles the question.
5. **Do not fork the whole Asterinas kernel** to get its Linux ABI and its ready-made schbench/hackbench runs [E139]. That would make Kernel AI a derivative of a large MPL kernel built around Linux compatibility, which is the opposite of a TempleOS-style system. See [templeos-components.md](./templeos-components.md).

### Not possible / not viable

- **The x86-interrupt ABI cannot be used on stable Rust,** and neither can the `x86_64` crate's safe `set_handler_fn`. Both need the unstable `abi_x86_interrupt` feature (tracking issue #40180). On stable, use naked-function or `global_asm!` stubs with the unsafe `set_handler_addr` [E16-E18].
- **In-kernel `cargo test` through `#[test_case]`/`#![test_runner]` is impossible on stable.** `custom_test_frameworks` is unstable [E19].
- **Path B cannot be built on stable Rust.** OSTD enables nine `#![feature]` attributes, OSDK passes `-Zbuild-std`, and `cargo osdk new` exits on any toolchain other than `nightly-2026-07-21` [E86].
- **`cargo-osdk` cannot run natively on Windows.** It imports `std::os::unix` unconditionally, and that module exists only on Unix [E85]. Path B requires WSL2, a Linux container or a Linux VM.
- **Under QEMU TCG, the guest cannot use the LAPIC TSC-deadline mode, PCID or invariant TSC** [E110, E111]. The kernel must work with one-shot or periodic LAPIC mode plus calibration.
- **icount, record/replay and reverse debugging cannot be combined with WHPX** (QEMU refuses to start) **or with multi-threaded TCG** [E114-E116].
- **QEMU cannot give cycle-accurate timing.** Absolute latencies measured in the VM do not transfer to hardware [E113, E114].
- **A guest cannot make QEMU exit with status 0 through isa-debug-exit.** The status is always `(v<<1)|1` [E119].
- **On unmodified OSTD 0.19.0, a client kernel cannot map executable kernel pages.** It therefore cannot load ring-0 modules, hot-swap ring-0 code or JIT into ring 0 [E78, E80].
- **On OSTD 0.19.0, the timer cannot preempt kernel-mode code** [E71, E72].
- **OSTD's scheduler cannot be replaced at runtime through `inject_scheduler`, and its frame and heap allocators cannot be replaced after link time** [E70, E75]. Runtime swaps have to happen inside our own injected object.
- **A distributed binary that contains modified OSTD or Asterinas files cannot keep those files closed** (MPL 2.0 §1.10 and §3.2) [E95].
- **`virtio-drivers` cannot use legacy port-I/O PCI configuration (0xCF8/0xCFC) out of the box.** It needs ECAM, which on x86 QEMU means `-machine q35` [E36, E38]. The alternative is to implement its `ConfigurationAccess` trait over port I/O ourselves [E37].
- **A plain `-device virtio-gpu-pci` under OVMF gives no linear framebuffer** (its GOP is `PixelBltOnly`) [E39].
- **WHPX cannot run with `kernel-irqchip=split`,** so OSDK's default QEMU arguments fail unchanged under WHPX [E87, E107].
- **WHPX cannot do gdb debugging on QEMU releases before 11.0.0,** and it cannot provide hardware watchpoints on any release [E105, E106].
- **The `pty` chardev is not available on Windows hosts** [E122].
- **No Stefan Weil installer exists for QEMU point releases such as 11.1.2** [E100].
- **blog_os cannot carry the founder past about M2.** It has no APIC, SMP, preemption, user-mode, ACPI or virtio posts [E134, E135].
- **schbench, rt-app and stress-ng cannot run on a Path A kernel** until it has a Linux/POSIX ABI. Synthetic workloads must be written natively [E139].
- **The Linux BPF verifier cannot be reused as a policy-safety mechanism in a from-scratch kernel.** The Rust `rbpf` VM offers only an interpreter under `no_std`, with a verifier its README calls "nothing close" to Linux's [E52].
- **The LLM cannot sit on the scheduler hot path.** This is already a fixed decision, and the numbers confirm it: about 50 ms per token against decisions measured at 0.27-5.7 µs [E46, E50].

### Decisions the founder must make

| # | Decision | Options | Recommended default |
|---|---|---|---|
| 1 | Kernel base | A: Limine plus rust-osdev; B: OSTD/OSDK | **A** (conclusion 1) |
| 2 | Rust toolchain | A pinned dated nightly (required by `limine` 0.6.5 and `acpi` 6.1.1); or stable 1.99, only after forking or replacing `limine` and `acpi` and using naked-function stubs plus a hand-rolled test runner | **Pinned nightly.** Our own crates are limited to `abi_x86_interrupt` and `custom_test_frameworks` |
| 3 | Firmware target | UEFI only (OVMF); or UEFI plus legacy BIOS | **UEFI only.** Limine supports both, but BIOS doubles the test matrix [E3] |
| 4 | Kernel preemption model | Preempt only on return to ring 3 plus explicit yield points (the OSTD model); or a fully preemptible kernel with a preempt count | **Ring-3 preemption plus yield points for the POC.** Synthetic workloads run in ring 3 |
| 5 | Timer model | Fixed tick (for example 1 kHz); or a one-shot LAPIC timer programmed from the policy's slice, with a slow watchdog tick | **One-shot from the policy's slice.** The slice length becomes a tunable policy output (analysis) |
| 6 | Daily QEMU backend | TCG only; WHPX for interactive work plus TCG with icount for measurements | **Decide after the spike.** TCG plus icount is always the source of record |
| 7 | QEMU distribution on Windows | MSYS2 UCRT64 package (11.1.2); Stefan Weil installer (11.1.0) | **MSYS2** [E100, E101] |

### Memory reclaim prior art

- [E53] A DAMOS scheme pairs a target access pattern (size, frequency, age) with an action (pageout, cold, lru_prio/deprio, stat, and others), applied every `apply_interval`. Quotas cap the time and bytes spent, weighted by priority. Goal-based auto-tuning tracks a target metric, including a `user_input` metric fed from userspace. ### Asterinas OSTD: scheduler and memory control

- [E68] "Three complex policy components — task scheduler, frame allocator, and slab allocator — are implemented outside OSTD in safe Rust and injected via safe trait interfaces." A buggy safe-Rust policy "cannot cause UB". — [Asterinas Book: safe policy injection](https://raw.githubusercontent.com/asterinas/asterinas/main/book/src/ostd/soundness/safe-policy-injection.md) (undated)
- [E69] `Scheduler<T>` requires `enqueue(Arc<T>, EnqueueFlags) -> Option<CpuId>`, where the returned CPU gets preempted, plus `local_rq_with` and `mut_local_rq_with`. `LocalRunQueue<T>` requires `current`, `update_current(UpdateFlags) -> bool`, `try_pick_next` and `dequeue_current`. `EnqueueFlags` covers Spawn and Wake; `UpdateFlags` covers Tick, Wait, Yield and Exit. — [ostd 0.19.0 LocalRunQueue](https://asterinas.github.io/api-docs/0.19.0/ostd/task/scheduler/trait.LocalRunQueue.html) (2026-10-12); [ostd 0.19.0 Scheduler](https://asterinas.github.io/api-docs/0.19.0/ostd/task/scheduler/trait.Scheduler.html) (2026-10-12)
- [E70] `inject_scheduler` "can only be called once". It panics if a scheduler was already injected, either explicitly or through the lazily created default FIFO scheduler. The default FIFO scheduler sends every task to the bootstrap CPU and never preempts on a tick. — [ostd scheduler/mod.rs](https://raw.githubusercontent.com/asterinas/asterinas/main/ostd/src/task/scheduler/mod.rs) (main, undated; same text in the 0.19.0 crate); [fifo_scheduler.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/ostd/src/task/scheduler/fifo_scheduler.rs) (2026-10-14)
- [E71] After `enable_preemption_on_cpu`, "a task that is executing in the user mode may get preempted". Preemption is driven by a per-CPU timer callback, and `TIMER_FREQ` is the constant 1000. — [ostd 0.19.0 enable_preemption_on_cpu](https://asterinas.github.io/api-docs/0.19.0/ostd/task/scheduler/fn.enable_preemption_on_cpu.html) (2026-10-12); [ostd 0.19.0 crate, src/timer/mod.rs](https://crates.io/api/v1/crates/ostd/0.19.0/download) (2026-10-12)
- [E72] Source reading of ostd 0.19.0, verified in this session: `might_preempt()` is called in the `UserMode` execute loop of each architecture, in `halt_cpu`, in `run_new_task` and in the guest-mode VM loop. Dropping `DisabledPreemptGuard` only decrements a counter, and the x86 kernel-mode trap path does not reschedule. This was not tested at runtime. — [ostd 0.19.0 crate download](https://crates.io/api/v1/crates/ostd/0.19.0/download) (2026-10-12)
- [E73] OSTD's x86 APIC timer uses TSC-deadline mode when the CPU supports it. Otherwise it uses periodic mode calibrated against the PIT. — [ostd arch/x86/timer/apic.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/ostd/src/arch/x86/timer/apic.rs) (2026-10-14)
- [E74] Asterinas injects a `ClassScheduler` with stop, real-time, fair and idle class run queues. It picks a CPU only when a task first spawns; after that a task is re-enqueued on its last CPU. No migration code was found (source reading). — [kernel sched_class/mod.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/kernel/core/src/sched/sched_class/mod.rs) (2026-10-14)
- [E75] `GlobalFrameAllocator` provides `alloc(Layout) -> Option<Paddr>`, `dealloc` and `add_free_memory`. `GlobalHeapAllocator` provides `alloc(Layout) -> Result<HeapSlot, AllocError>` and `dealloc`. Both are selected through attributes. OSDK's generated base crate links default buddy and slab allocators as weak symbols, which a kernel overrides at link time. — [ostd 0.19.0 GlobalFrameAllocator](https://asterinas.github.io/api-docs/0.19.0/ostd/mm/frame/allocator/trait.GlobalFrameAllocator.html) (2026-10-12); [ostd 0.19.0 GlobalHeapAllocator](https://asterinas.github.io/api-docs/0.19.0/ostd/mm/heap/trait.GlobalHeapAllocator.html) (2026-10-12); [OSDK base crate template @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/osdk/src/base_crate/main.rs.template) (2026-10-14)
- [E76] Kernel-mode page faults on kernel addresses panic. Faults on user addresses go to a handler set through `inject_user_page_fault_handler` ("may be called only once; subsequent calls take no effect"). Exceptions in user mode return to the kernel's `UserMode` loop. — [ostd mm/fault/mod.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/ostd/src/mm/fault/mod.rs) (2026-10-14)
- [E77] `VmSpace` cursors offer map, unmap, query and `protect_next`. `PageFlags` includes `X`, `ACCESSED` and `DIRTY`. — [ostd mm/page_prop.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/ostd/src/mm/page_prop.rs) (2026-10-14)
- [E78] In ostd 0.19.0, `kspace` and `page_table` are `pub(crate)` modules and `KVirtArea` is a `pub(crate)` struct (verified in this session). The public mapping API, `VmSpace`, is documented as "A virtual address space for user-mode tasks". — [ostd mm/kspace/mod.rs @01acaa7](https://raw.githubusercontent.com/asterinas/asterinas/01acaa7eeed755a32fc658e7d732b080061b4872/ostd/src/mm/kspace/mod.rs) (2026-10-14); [ostd 0.19.0 crate download](https://crates.io/api/v1/crates/ostd/0.19.0/download) (2026-10-12)
- [E79] Asterinas `/proc/meminfo`: "Currently, no pages can be evicted when memory is allocated", and `SwapTotal` is 0 kB. — [procfs meminfo.rs](https://raw.githubusercontent.com/asterinas/asterinas/main/kernel/core/src/fs/fs_impls/procfs/meminfo.rs) (main, undated)
- [E80] Asterinas "does not, nor will it in the future, support the loading of Linux kernel modules"; `init_module` and `finit_module` are unsupported. — [Asterinas Book: Linux compatibility](https://asterinas.github.io/book/kernel/linux-compatibility/index.html) (undated)

- [E111] QEMU's emulated LAPIC supports x2APIC mode, and its timer runs on `QEMU_CLOCK_VIRTUAL`. It has no TSC-deadline code path. — [QEMU hw/intc/apic.c](https://gitlab.com/qemu-project/qemu/-/raw/master/hw/intc/apic.c) (2026-06-18)
- [E112] Multi-threaded TCG (one host thread per vCPU) is the default for x86 unless icount or record/replay is enabled. With those, QEMU falls back to single-threaded round-robin. — [QEMU accel/tcg/tcg-all.c](https://gitlab.com/qemu-project/qemu/-/raw/master/accel/tcg/tcg-all.c) (2026-09-08); [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html) (2026-09-11)
- [E113] Without icount, the guest's virtual clock is the host monotonic clock and guest RDTSC follows host CPU ticks. With icount, both are derived from the count of executed instructions. — [QEMU system/cpu-timers.c](https://gitlab.com/qemu-project/qemu/-/raw/master/system/cpu-timers.c) (2025-09-17)
- [E114] `-icount shift=N` runs one instruction every 2^N ns of virtual time. `sleep=off` jumps virtual time to the next timer deadline, which "gives deterministic execution times from the guest point of view". The feature "does not provide cycle accurate emulation", is system-emulation only, and "is incompatible with multi-threaded TCG". — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html) (2026-09-11); [QEMU TCG instruction counting](https://www.qemu.org/docs/master/devel/tcg-icount.html) (undated)
- [E115] QEMU exits with "-icount is not allowed with hardware virtualization" whenever icount is enabled without TCG (verified in this session). — [QEMU system/vl.c](https://gitlab.com/qemu-project/qemu/-/raw/master/system/vl.c) (2026-09-17)
- [E116] Record/replay requires icount and supports x86_64. Reverse debugging (`reverse-stepi`, `reverse-continue`) is available. The documented device examples use `ide-hd` with blkreplay and `rtl8139`, not virtio. — [QEMU record/replay docs](https://www.qemu.org/docs/master/system/replay.html) (2026-01-22)
- [E117] `-rtc clock=vm` is recommended in icount mode to preserve determinism. — [QEMU invocation docs](https://www.qemu.org/docs/master/system/invocation.html) (2026-09-11)
- [E118] On Windows 11, WSL2's `nestedVirtualization` setting defaults to true. Microsoft's WSL2 kernel config builds `CONFIG_KVM=m`. Microsoft says non-Microsoft virtualization on Hyper-V "isn't supported". Under default NAT networking, WSL2 reaches Windows services through the host IP, not localhost. — [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config) (2026-09-16); [WSL2 kernel config-wsl](https://raw.githubusercontent.com/microsoft/WSL2-Linux-Kernel/linux-msft-wsl-6.18.y/arch/x86/configs/config-wsl) (undated); [Hyper-V nested virtualization](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/nested-virtualization) (2025-06-10); [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking) (2026-06-02)

### Estimates and analysis

Everything in this subsection is analysis or estimation, not sourced fact.

- **Effort assumptions.** The developer works solo, knows Rust well and is writing a first kernel. A focused person-week is 30-35 hours of deep work. Ranges include QEMU debugging on Windows and are about ±50% wide. The ladders deliberately give both paths the same milestone goals, so differences come from what each base already provides.
  - Path A's M3 and M6 carry the most uncertainty: the first context switch and the first reclaim path tend to be where first kernels stall.
  - Path B's M5 range is wide because vendoring `aster-virtio` (low end) and writing drivers on OSTD's DMA/IoMem APIs (high end) are very different jobs.
- **Calendar time.** Calendar weeks ≈ person-weeks × 35 ÷ focused hours per week. Example: Path A's midpoint of about 33 person-weeks at 15 focused hours per week is about 77 calendar weeks, roughly 18 months. At 30 hours per week it is about 39 weeks.
- **The Path B fork cost (+3-8 person-weeks)** assumes a minimal OSTD patch exposing an executable kernel-mapping API and a module-loading hook, plus keeping the TCB reasoning sound. A rebase per OSTD minor release (+1-2 each) follows from observed breakage: `UserMode::execute`, logging, DMA, PCI [E60]. The OSTD release cadence is a minor version every 4-6 months, with patch releases every 1-3 months [E59].
- **Code size.**
  - Path A's own code to reach M6 is likely 15-30k lines of Rust plus a few hundred lines of assembly.
  - Path B's client-kernel code to reach M6 is likely 8-20k lines on top of the 49k-line `ostd` crate [E64].
  - A researcher in this workflow counted the full Asterinas `kernel/` tree at about 148k non-blank, non-comment lines at commit 01acaa7. That is the scale of the "fork all of Asterinas" option rejected above.
- **TCG speed.** CPU-bound integer kernel code under x86-on-x86 TCG is probably 5-20x slower than native. No primary benchmark was found, so measure it in the spike. Under WHPX, CPU-bound code should run near native speed, but each MMIO or port-I/O exit costs on the order of microseconds and timing is perturbed by the Windows scheduler.
- **Hot-path gap.** At 20 tokens/s one token takes 50 ms, about 10^4 to 10^5 times a 0.27-5.7 µs scheduling decision [E46]. A full JSON decision of about 100 tokens is about 10^6 times slower. The LLM therefore acts on phase changes that last tens of seconds to minutes.
- **Watchdog threshold.** For interactive synthetic workloads with about 16.7 ms frames, a stall threshold of 100-500 ms that reverts to the default policy is reasonable. sched_ext's 30 s maximum is a server-oriented ceiling, not a target [E45].
- **Virtio interrupts on q35.** Legacy INTx for PCI devices is routed through the ACPI `_PRT`, which means evaluating AML (`acpi::aml` has `pci_routing` [E27]). MSI-X avoids AML entirely. With `pci_types` exposing the capability and the virtio spec defining the vector registers [E34, E35], MSI-X is likely the shorter path after polling.
- **Timer choice.** A one-shot LAPIC timer armed per scheduling decision makes the slice length (`slice_ns`, as in [E48]) a direct policy output, which suits AI-tuned scheduling. A fixed 1 kHz tick (OSTD [E71]) quantizes slices to 1 ms.
- **Ring-0 vs ring-3 preemption.** Preempting only on return to ring 3, plus explicit kernel yield points, avoids a large class of lock-ordering and preempt-count bugs in a first kernel. It works for the POC because synthetic workloads run in ring 3. A fully preemptible kernel can come later if the REPL runs long jobs in ring 0, which [compiler-in-terminal.md](./compiler-in-terminal.md) should decide.
- **Synthetic workloads on Path A.** schbench, rt-app and stress-ng are Linux/POSIX programs [E139]. On Path A their workload shapes (CPU hogs, periodic interactive tasks, request/response, IPC storms, memory working-set sweeps) must be reimplemented as native ring-3 programs. Budget for this is inside M6.
- **Licensing beyond the MPL.** If Kernel AI accepts outside contributions under an open-source licence, relicensing them for a commercial product later needs either those contributors' permission or a contributor agreement set up in advance. This is general practice, not legal advice. Have counsel review it before the first external contribution and before any commercial release.

## Open questions

1. **How many focused hours per week can the founder commit?** Every estimate above is in person-weeks, so calendar planning depends on this number. Resolve it by having the founder state a weekly budget and logging actual hours through M0.
2. **Does WHPX on the founder's machine boot OVMF plus Limine reliably at `-smp 4`, and does it expose TSC-deadline and x2APIC to the guest?** This decides whether WHPX is part of the daily loop. Resolve it in the spike: QEMU 11.1.2 from MSYS2, q35, `-accel whpx`, a Limine kernel that prints CPUID leaf 01H and the AP count, run 20 times.
3. **Do gdb `break` and `stepi` work under WHPX in QEMU 11.1.2?** The source shows no gdbstub breakpoint hook for WHPX [E106]. Resolve it in the spike by setting a breakpoint on a kernel function under TCG and under WHPX and comparing the results.
4. **What is the founder's host CPU vendor and model, and which Windows 11 build is it?** Several open WHPX bugs and the nested-virtualization rules depend on the CPU [E108, E118]. Resolve it by recording both in the repo's developer notes.
5. **Where will live-editable code run: ring-0 modules, ring-3 servers, or WASM?** This is the deciding factor between Path A and Path B [E78, E80]. Resolve it through [live-editable-system.md](./live-editable-system.md). If the answer is "ring 3 only", Path B's main blocker goes away, and the base decision should be re-checked.
6. **Would Asterinas maintainers accept an upstream API for executable kernel mappings or kernel-mode preemption?** If they would, Path B would no longer need a permanent fork. Resolve it by asking in an Asterinas GitHub discussion or RFC before choosing Path B.
7. **Are OSDK-generated files (the base crate's `main.rs`, linker scripts) and OSTD macro expansions MPL "Modifications" that a commercial binary must ship in source form?** This determines Path B's compliance burden [E75, E95]. Resolve it with counsel, before any commercial distribution on Path B.
8. **Does the OSDK QEMU configuration run under TCG and WHPX on Windows once `kernel-irqchip=split` is removed?** The Icelake-Server CPU model and the two-pflash OVMF setup are the open points [E87, E107, E108]. Resolve it only if Path B is reconsidered: boot the OSDK ISO with native Windows QEMU under both accelerators.
9. **Which icount `shift` value and `-smp` count define the canonical measurement mode, and are single-threaded TCG results representative enough for SMP policy comparisons?** The answer determines how much results can be trusted [E112, E114]. Resolve it at M6 by running the same policy pair under icount and under WHPX, and checking that the ranking agrees.
10. **Do virtio-blk and virtio-net work under record/replay?** The replay docs show only `ide-hd` and `rtl8139` [E116]. Resolve it at M5 with a short replay test. If it fails, fall back to plain icount without replay.
11. **Which OVMF build should the project pin once QEMU 11.2 drops `edk2-i386-vars.fd`?** Without a pin, the firmware could change under the harness [E102]. Resolve it by vendoring OVMF through `ovmf-prebuilt` and recording the edk2 tag [E13].
12. **Is WHPX or nested virtualization available on GitHub-hosted `windows-latest` runners?** Only a 2020 secondary source says no [E133]. Resolve it with a one-off CI job that enables HypervisorPlatform and tries `-accel whpx`. If it fails, the Windows job stays TCG-only.
13. **When can the kernel move to stable Rust?** This is mostly answered: no, as long as it depends on `limine` 0.6.5 (`ptr_metadata`) and `acpi` 6.1.1 (`allocator_api`) (conclusion 4). Watch both crates for releases that gate these features, then re-test with a stable build in CI.
14. **How fast is TCG compared with WHPX on the founder's machine?** The 5-20x figure is an unverified estimate. Resolve it in the spike by timing a fixed CPU-bound loop in the guest under both accelerators.
